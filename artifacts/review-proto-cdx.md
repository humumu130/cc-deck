# V8 原型多维评审（CDX）

> 评审对象：`docs/mockups/v8-ui-interactive-v2.html`
>
> 评审范围：桌面团队域 / 项目域 / 通知 / 验收单，手机团队主页与详情 / 项目主页与详情 / 通知 / 验收单，及其与现网 IA 的差异。
>
> 评审日期：2026-10-14

## 结论先行

这版不应直接进入像素级冻结。视觉骨架可以保留，但产品语义仍是“单团队任务看板演示”，还不是多团队、多项目、无人值守编排平台的控制面。v8.5 先修状态机、行动队列、无人值守可见性、现网 IA 补全和跨端任务边界；玻璃拟态、阴影、卡片密度等视觉收口应随后跟进。

三个必须先拍板的产品原则：

1. **颜色只表达一个维度**：成员状态灯表达 liveness，泳道表达任务状态，通知红黄灰表达行动优先级，三套语义不能复用同一颜色而不加第二编码。
2. **所有需 PM 决策的事情进入一个行动队列**：验收回填、待确认、派单失败、worker 阻塞 / 失联、上下文风险不能继续散落在消息、看板、成员和通知四处。
3. **验收单是唯一闭环对象**：消息卡、看板卡、项目聚合、通知和手机入口都必须带同一个 acceptance id，并能回到来源；“装机看效果”不能再像第二套验收流程。

## 取证基线

- 原型桌面团队详情在 `docs/mockups/v8-ui-interactive-v2.html:1188-1320`，只有“消息 / 看板 / 成员 / 活动”四 Tab；看板仍显示“待验收 / 就绪待装机”。
- 原型桌面项目聚合在 `docs/mockups/v8-ui-interactive-v2.html:1551-1611`，有会话 / 团队 / 输出物 / 验收单四段，但多数“全部 ↗”仍是占位交互。
- 原型桌面通知是 rail 铃铛浮层，见 `docs/mockups/v8-ui-interactive-v2.html:1174-1184`；手机通知是二级页，见 `docs/mockups/v8-ui-interactive-v2.html:2230-2247`。
- 原型验收单主体在 `docs/mockups/v8-ui-interactive-v2.html:1616-1645`，手机对应 `docs/mockups/v8-ui-interactive-v2.html:2251-2269`。
- 现网桌面团队域已经是六面：“对话 / 看板 / 成员 / 活动 / 经验 / 铁律”，见 `web-console/index-005.html:6539-6546`；经验和铁律的数据、写入约束分别在 `web-console/index-005.html:6560-6563`、`web-console/index-005.html:6937-7045`。
- 现网通知不是单一浮层，而是通知队列 + 来源详情的两列域，见 `web-console/index-005.html:8335-8337`、`web-console/index-005.html:8505-8521`；手机现网通知是底部 sheet，见 `expo-app/src/screens/NotifCenterPage.tsx:157-205`。
- 现网手机团队详情已经是七节纵向消费面（确认、看板、编制、活动、经验、铁律及相关只读信息），见 `expo-app/src/screens/TeamDetailPage.tsx:502-560`；这与原型的“对话 / 看板 / 成员 + ⋯ 活动”不同。
- 截图证据目录：`artifacts/proto-review-cdx-shots/`。包含桌面团队看板 / 成员 / 活动、项目详情、通知浮层，以及手机团队 / 项目 / 通知 / 验收单关键帧。

## 一、UI 设计

### U-01 · P1 · 三套颜色语义互相抢占

- **问题**：看板进度条使用蓝 / 绿 / 橙 / 黄，成员卡又使用绿 / 黄表达在线、失联、滞留，通知再用红 / 黄 / 灰表达行动级别；同一颗颜色在不同区域被读成不同事实。原型 token 还把 `--working` 注释为“待装机 / 警示”，没有体现用户已定的“黄闪 = 工作中”。
- **位置**：桌面 `#tboard` 的总览条和泳道、`#tcrew` 成员状态胶囊、桌面 `#notifpanel` 与手机 `#ph-pnotif`；证据见 `desktop-team-board.png`、`desktop-team-members.png`、`mobile-notifications.png`。
- **改法**：状态灯单独建立五态 token：黄闪工作中、绿空闲、橙阻塞、红出错、灰关闭；看板泳道改用中性底色 + 固定顺序 + 文字，不再借用灯色；通知保留红 / 黄 / 灰但必须同时显示“需你行动 / 注意 / 动态”文字。
- **严重度**：P1，错误颜色会直接导致错误决策。

### U-02 · P1 · 原型词表未跟随已冻结状态机

- **问题**：原型使用“待验收”“就绪待装机”“待装机”，现网和用户定版词表是“待认领 / 进行中 / 待审查 / 待收单 / 完成”。手机和桌面还出现“待验收”与“就绪待装机”两套说法。
- **位置**：桌面 `#tboard` `docs/mockups/v8-ui-interactive-v2.html:1265-1301`，手机 `#p3b` `docs/mockups/v8-ui-interactive-v2.html:2099-2145`。
- **改法**：v8.5 原型所有显示点统一调用一份显示词典；存储状态可保留兼容映射，但展示、筛选、通知标题、项目统计、验收单步骤一律使用五态定版词表。迁移兼容时在开发注释里说明旧值，不把旧词带到画面。
- **严重度**：P1，状态名错误会破坏 PM 对“AI 自验完成”和“PM 收单完成”的边界理解。

### U-03 · P1 · 单团队小样本掩盖真实密度问题

- **问题**：桌面五列卡片在 9 张示例卡时仍使用较宽卡面、较大的空隙和较长副文案；真实是几十张卡、十几张会话、多个团队并行，卡片会变成横向滚动和纵向长跑。手机泳道则把所有卡纵排，用户很难判断“我现在正在看哪一组”。
- **位置**：桌面 `#tboard .bcols`，手机 `#p3b .plane`；证据见 `desktop-team-board.png`、`mobile-team-detail-board.png`。
- **改法**：增加“标准 / 紧凑”密度档；桌面列头固定、卡片只留标题 / owner / 最近动作 / 风险，全文放 hover 或详情；手机总览吸顶保留，但增加“只看需行动 / 只看阻塞 / 只看我负责”筛选和泳道跳转后的当前组标题。
- **严重度**：P1，实际密度下核心控制面不可用。

### U-04 · P2 · 玻璃拟态层级没有可复用规则

- **问题**：原型在外壳、卡片、浮层、警示卡上同时使用深底、描边、阴影和颜色边框，演示画面很有层次，但“什么是容器、什么是可操作卡、什么是临时浮层”没有稳定层级。现网页面已有自己的 `surface1 / surface2 / line / small-shadow` 体系，直接把原型的发光边框全量套过去会造成双重边界。
- **位置**：桌面壳、`#notifpanel`、看板卡、手机 `.screen` 内的 `.pcard` / `.nrow`。
- **改法**：v8.5 先定义三层 token：页面底 / 工作面 / 临时浮层；常规卡只用细边 + 轻阴影，只有“需你行动”使用语义边框；通知浮层和验收单使用玻璃背景，经验 / 铁律使用普通工作面。浅色主题同步校验对比度，避免透明层叠导致文字发灰。
- **严重度**：P2，属于视觉系统债务，但会放大信息优先级混乱。

### U-05 · P1 · 关键动作藏在弱链接和卡内角落

- **问题**：`验收单 ↗`、`反馈问题`、`换厂商接替` 都是小型 inline action；“新建任务卡”在原型里只是演示占位，用户看不出哪里能派单、哪里能调整 owner、哪里能把阻塞交给系统恢复。
- **位置**：看板卡 `T-13`、消息 ready card、成员卡底部 action row、项目聚合四个“全部 ↗”。
- **改法**：每个工作面提供一处主动作位：看板头部“派单”、需收单列“打开验收单”、阻塞卡“恢复 / 接替”、项目页“打开行动队列”。卡内链接降级为同一动作的快捷入口，并显示目标对象名称。
- **严重度**：P1，信息存在但操作发现性不足。

### U-06 · P1 · 成员状态灯与上下文水位的视觉表达不够可行动

- **问题**：成员卡能看到 61% / 47% 等水位，但没有阈值、更新时间、影响和下一步；“失联”和“滞留”也没有同时显示心跳 / 日志两个信号。仅显示百分比会让 PM 误以为水位本身就是故障。
- **位置**：桌面 `#tcrew`、手机 `#p3c` 成员卡；证据见 `desktop-team-members.png`、`mobile-team-detail-members.png`。
- **改法**：水位分为安全 / 注意 / 临界三档，显示“上下文 61% · 3 分钟前”；达到阈值给“压缩 / 观察 / 接替”动作。成员状态区固定显示五态灯 + 心跳 / 日志双信号，二者不再混成一个“在线”胶囊。
- **严重度**：P1。

### U-07 · P1 · 桌面和手机的导航层级不等价

- **问题**：桌面团队详情把活动作为第四个 Tab、手机把活动收进 ⋯；手机又保留了对话 Tab，但现网手机 TeamDetailPage 是以看板为主的七节纵向页，并没有独立团队对话页。用户从桌面切到手机后，无法预测同一功能会在哪里。
- **位置**：桌面 `#detail-team .dtabs`、手机 `#ph-pteamd .ptabs`，对照 `expo-app/src/screens/TeamDetailPage.tsx:8-9`。
- **改法**：建立跨端功能矩阵：桌面保留六面 IA；手机详情采用“看板默认 + 确认 / 编制 / 活动 / 经验 / 铁律折叠节”，对话通过成员 / Leader 深链进入，不再为了对齐桌面而造一个空对话 Tab。手机只保留低频入口到 ⋯，但在页面目录中显示可用节数。
- **严重度**：P1，属于跨端导航断裂。

### U-08 · P1 · 通知浮层不是高事件量下的可读布局

- **问题**：桌面 rail 浮层固定在左下，通知行只给标题、短副文案和动作；多团队、多项目时没有团队 / 项目 / relay 来源，用户无法知道同名 T-13 属于哪个上下文。手机页面则拉长为全量列表，和现网的底部 sheet / 已处理折叠形态不一致。
- **位置**：`#notifpanel`、`#ph-pnotif`；证据见 `desktop-notification-overlay.png`、`mobile-notifications.png`。
- **改法**：rail 只做“最近三条 + 需行动计数”的快览；增加完整通知域，左列按行动 / 注意 / 动态分组，右列显示来源详情、团队、项目、时间、处理动作。手机采用底部 sheet 快速处理，进入详情时保留来源上下文。
- **严重度**：P1。

## 二、功能对照

### F-01 · P0 · 看板缺少真正的派单入口和派单状态

- **问题**：看板是编排核心，但原型只有“＋ 新建任务卡”演示位，没有派单表单、目标成员 / 角色、验收点、项目锚点、派单中 / 成功 / 失败回执，也没有重试或转派。
- **位置**：桌面 `#tboard` 的 `待认领` 列 `＋ 新建任务卡`，手机 `#p3b` 没有派单入口。
- **改法**：看板头部增加“派单”主动作；表单至少包含标题、项目、目标角色 / 成员、验收点、优先级、上下文限制。提交后进入“派单中”回执态，失败必须落到需你行动并提供重试 / 换人；建卡文本走 `normalizeBoardCardText` 单口，避免派单页制造杂物卡。
- **严重度**：P0，核心旅程“开团 → 派单”在原型上断开。

### F-02 · P0 · “需要你”没有成为跨域一等视图

- **问题**：验收回填、worker 卡住、派单失败、组织确认、waiting_request、上下文临界分别散在通知、消息、看板、成员和设置。原型右上角 badge 只数两个 alert，不能告诉 PM 今天到底有多少决策要做。
- **位置**：桌面 rail badge、团队四 Tab、项目聚合、手机四 Tab / 通知页。
- **改法**：新增全局“需要你”入口，按“验收 / 决策 / 阻塞 / 派单 / 系统风险”分组，每条显示来源和下一动作；团队、项目页只显示同一账本的局部投影。处理后由权威事件收敛，不由 UI 删除假装完成。
- **严重度**：P0，直接影响无人值守产品的接管面。

### F-03 · P0 · 五态看板缺列，导致 AI 自验和 PM 收单混成一条线

- **问题**：原型的“待验收 / 就绪待装机”无法表达“worker 自测提交后等独立审查”和“审查通过后等 PM 收单”的差异；`T-13` 已回填 2/3，却仍处于旧词泳道。
- **位置**：桌面 `#tboard` 总览和泳道、手机 `#p3b` 总览及 `T-14 / T-13` 卡。
- **改法**：固定五列“待认领 / 进行中 / 待审查 / 待收单 / 完成”。AI 自验只在卡内作为证据点，不替代泳道；独立验收通过后迁入待收单；PM 收单才进入完成。
- **严重度**：P0，状态机和验收闭环的共同地基错误。

### F-04 · P1 · 验收单三入口没有显式绑定同一对象

- **问题**：看板、通知、项目详情都能显示“验收单 ↗”，但画面没有 acceptance id、来源卡、原项目 / 团队和返回位置。用户无法判断多个同版本产物是否同一张单；“装机看效果”又制造了一个看似独立的验收动作。
- **位置**：消息 ready card `docs/mockups/v8-ui-interactive-v2.html:1252-1255`，看板 `T-13`，项目验收段和通知 `al1`。
- **改法**：所有入口显示“验收单 · A-xxxx”或短 id，进入后头部显示“来源：团队 / 项目 / 原卡”；关闭或提交后回到来源页并保留滚动位置。将“装机看效果”改成“打开验收单”，若确实是安装预览，另设“查看产物”而不是验收动作。
- **严重度**：P1。

### F-05 · P1 · 通知的关闭、已处理、已解决语义没有分开

- **问题**：原型写“红条常驻、手动关闭”，同时每条有 `×`；这会让 PM 以为关闭等于解决。现网通知已经有 `handled / dismissed / resolved` 投影和来源详情，原型没有把这套生命周期呈现出来。
- **位置**：桌面 `#notifpanel .x`、手机 `#ph-pnotif .x`，对照 `web-console/index-005.html:8358-8362`、`8623-8659`。
- **改法**：红色 actionable 只能通过来源动作或“标记已处理”改变状态；`×` 只代表隐藏本条，不改变权威账。已处理消息移入折叠历史区，解决状态来自来源域事件。按钮文案分别用“处理 / 标记已处理 / 隐藏”，不再统一叫关闭。
- **严重度**：P1。

### F-06 · P1 · 活动流、通知账、值守账本三者关系未定义

- **问题**：活动页既展示 `notify 已推手机`、watchdog、接替，也像任务审计日志；通知页又展示相同事件，用户不知道哪个是全量事实、哪个是需行动投影、哪个会被清理。几百条事件下，重复和漏看都会发生。
- **位置**：桌面 `#tfeed`、`#notifpanel`、项目聚合；现网通知来源卡在 `web-console/index-005.html:8505-8521`。
- **改法**：在原型中明确三层：活动 = 不可变审计时间线；通知 = actionable projection；值守摘要 = 最近健康和未决风险。三层都显示 event id / 时间 / 来源，通知处理后活动仍保留；同一事件只在行动队列占一条。
- **严重度**：P1。

### F-07 · P0 · pmwake、巡检、激活器、liveness 只在文案里出现

- **问题**：原型有“watchdog 已通知 Leader”“自动接替”文字，但没有 pmwake 是否触发、最近巡检、激活器拉活次数、心跳 / 日志双信号、当前门禁状态。无人值守是产品护城河，却被画成静态事件。
- **位置**：成员卡、通知 warn、团队标题行；证据见 `desktop-team-members.png`。
- **改法**：团队标题增加“值守健康”摘要：最近巡检、pmwake 最近触发、激活器状态、未决风险数。成员卡显示双信号和自动恢复状态；阻塞卡可展开“系统已尝试什么 / 下一次何时尝试 / 你可否接管”。
- **严重度**：P0，产品定位无法被用户感知和信任。

### F-08 · P1 · 五色成员状态词表没有落到原型

- **问题**：原型用“在线 / 失联 / 滞留”，没有“黄闪工作中 / 绿空闲 / 橙阻塞 / 红出错 / 灰关闭”，且工作中不闪。用户无法区别“正在忙”“卡住了”“进程挂了”“团队主动关闭”。
- **位置**：桌面 `#tcrew`、手机 `#p3c` 和团队主页卡点。
- **改法**：所有成员 / 团队入口使用同一状态灯组件；仅 working 闪烁，其他状态静态；文字和灯始终同时出现。通知严重度不复用成员状态灯。
- **严重度**：P1。

### F-09 · P1 · 项目聚合是漂亮的目录，不是项目控制面

- **问题**：项目详情展示“6 会话 / 1 团队 / 输出物 46 / 验收单 3 张”，但只列两条代表项；“全部 ↗”多数未展开，也没有按团队、会话、产物、验收单筛选、排序、来源、最后同步时间。`2 需行动` 没有解释来源。
- **位置**：桌面 `#dt-proj`、手机 `#ph-pprojd`；证据见 `desktop-project-detail.png`、`mobile-project-detail.png`。
- **改法**：项目头部显示目录锚点、relay/source、最后事件时间、行动数；四段都支持“全部 / 需行动 / 最近更新”，列表行显示所属团队 / 会话和可追溯 id。项目页只做聚合和导航，不复制一套独立状态机。
- **严重度**：P1。

### F-10 · P1 · 修复卡与原卡的状态关系容易产生假进展

- **问题**：`T-20` 在“就绪待装机”里同时标“修复中”，`T-21` 又在“进行中”；用户可能误以为 T-20 仍可装机。修复卡和原卡虽有“属 T-20”，但没有明确父子状态、阻断关系和重新验收入口。
- **位置**：桌面 `#tboard` `T-20 / T-21`，手机 `#p3b` 同样结构。
- **改法**：修复启动后原卡显示“被修复卡阻塞”，从待收单移入“待审查”或专门的阻塞子态；修复完成后回到同一 acceptance sheet 的失败行，不新建第二张验收单。卡面显示 parent / repair id 和下一闸口。
- **严重度**：P1。

### F-11 · P1 · 现网经验 / 铁律完全缺席，造成 IA 断层

- **问题**：原型只画四 Tab，现网已有经验库和铁律管理，且铁律是 `RULES_UPDATED` / 确认卡体系的实际控制面。没有这两面，用户无法理解团队如何积累经验、规则如何注入、为何某条派单被拦截。
- **位置**：原型 `#detail-team .dtabs`，现网 `web-console/index-005.html:6542`、`6937-7045`。
- **改法**：桌面 v8.5 在“活动”后补“经验 / 铁律”两 Tab；经验默认按项目组 + 全局过滤，支持只读检索和来源；铁律显示受众、范围、在役 / 已退役 / 已替代及审计链，写操作沿用现网两步确认和批量导入。手机详情补为只读折叠节，新增 / 替代 / 退役回电脑端或走确认卡。
- **严重度**：P1，属于现网 IA 缺页，不是装饰问题。

### F-12 · P1 · 团队生命周期和确认队列缺失

- **问题**：原型团队侧栏只有“进行中 / 已收团”，没有待确认、已挂起、待复活等真实状态；而现网组织状态包含 pending / active / parked / archived，手机团队主页实际把“待你确认”队列置顶。
- **位置**：桌面 `#side-team`、手机 `#ph-pteam`；对照 `expo-app/src/screens/OrgTabs.tsx:73-92` 和现网团队脚本 `web-console/index-005.html:6550-6558`。
- **改法**：团队列表增加行动分组和生命周期筛选；待确认卡置顶并显示决议类型、影响范围、来源 relay；已挂起团队显示冻结原因和复活动作。团队卡统计不要只显示运行数量，还要显示未决确认数。
- **严重度**：P1。

## 三、产品定位

### P-01 · P0 · 画面表达成“AI 任务板”，没有表达“无人值守控制面”

- **问题**：主视线被卡片、聊天和进度条占据；pmwake、巡检哨兵、激活器、liveness 门没有稳定入口。用户看到的是“我来盯着 worker”，不是“系统替我盯着 worker”。
- **位置**：团队标题区、团队主页、通知和成员页的首屏。
- **改法**：团队首屏重排为“值守健康 + 需要你 + 看板摘要 + 成员风险”；把健康摘要做成可展开的事实卡，而不是演示字幕。只有真正需要 PM 接管的异常才进入行动队列。
- **严重度**：P0，直接偏离产品护城河。

### P-02 · P1 · PM 的授权闸口没有统一心智模型

- **问题**：组织确认、waiting_request、验收回填 / 收单、派单失败处理、换厂商接替都属于“系统已经做了准备，等待 PM 决策”，但原型把它们分散在不同页面、不同按钮语言中。
- **位置**：消息确认条、通知 alert、验收单主按钮、成员接替按钮、项目聚合。
- **改法**：统一为“决策卡”模型：事实、风险、建议、影响范围、主按钮、拒绝 / 稍后处理、来源和审计记录。不同域只提供专用字段，不再各造一套确认样式。
- **严重度**：P1。

### P-03 · P1 · 证据和来源不足以支撑真实验收

- **问题**：卡面有 AI 自验圆点，验收单有“证据 ↗”，但原型没有展示证据类型、时间、执行者、产物版本、命令 / 截图归属。`AI 自验全过` 容易被误读为用户已经验收。
- **位置**：看板卡 `.vpg`、验收单行 `.sev`、项目输出物段。
- **改法**：卡面明确“AI 自验 N/M”；验收单每行显示“谁在何时以何证据完成”；AI 代验、桌面回填、手机回填分组展示。证据链接回到源会话 / 产物，不只弹 toast。
- **严重度**：P1。

### P-04 · P1 · 接替 / resume 的产品承诺没有被做成可验证状态

- **问题**：原型把“接替 = 同身份重 spawn，板 + git 是记忆”写在页脚或 toast，用户看不到是否真的保留身份、上下文、水位、分支和任务锁，也没有区分自动接替与 PM 手动接替。
- **位置**：成员卡“接替”、通知自动接替、手机通知页。
- **改法**：接替完成后显示“同身份 resume 成功 / 新进程 / 继承源 / 当前任务”；失败显示原因和下一步。成员时间线记录自动接替，通知只在需要 PM 选择厂商或确认风险时打扰。
- **严重度**：P1。

### P-05 · P1 · 多 relay / 多源能力没有进入产品模型

- **问题**：真实现网有 source / relay 维度，现网通知和团队页也需要来源标签；原型只画一个本机团队、一个项目、一个 relay。多源同名团队 / 项目会产生歧义。
- **位置**：团队列表、项目列表、通知行、成员卡和验收单头部。
- **改法**：团队 / 项目 / 通知所有聚合行显示 source badge；列表提供“全部源 / 单源”筛选，计数说明是单源还是跨源；验收单记录出单源和回填端，禁止跨源误合并。
- **严重度**：P1。

## 四、真实用户场景

### S-01 · P0 · 早晨同时巡检多个团队

- **问题**：PM 打开产品的第一任务是找出“今天需要我做什么”，但原型默认进入单个团队，侧栏只有一个进行中团队和一个已收团团队，没有跨团队行动总览。
- **位置**：桌面默认团队域、手机团队主页、rail badge。
- **改法**：默认首屏增加跨团队行动摘要；团队列表支持按需行动 / 阻塞 / 工作中筛选，点击行动直接打开对应验收单 / 决策卡，并保留团队上下文。
- **严重度**：P0。

### S-02 · P1 · 一天几百条事件后寻找一次异常

- **问题**：活动页只有“全部 / 输出物 / 状态流转 / 异常”四个静态 chips，没有时间范围、团队 / 项目 / 成员筛选、关键词、去重、分页和摘要；用户只能从头滚动。
- **位置**：`#tfeed`、手机活动低频入口、通知动态区。
- **改法**：活动页改为可检索事件账本：时间轴 + 类型 / 源 / 团队 / 项目过滤，支持“只看影响状态的事件”和按分钟合并重复心跳；通知只承接未决行动，不复制全量活动。
- **严重度**：P1。

### S-03 · P0 · worker 卡住且没有人盯终端

- **问题**：真实场景是心跳还在但日志停了、日志有输出但进程失联、上下文耗尽或激活失败。原型只给“滞留 25 分 / watchdog 已通知”一行文字，PM 无法判断系统已尝试什么、现在该接替还是等待。
- **位置**：成员卡、通知 warn、活动流。
- **改法**：成员风险卡展示双信号、最后心跳 / 最后日志、自动恢复尝试次数、下一次巡检时间，并提供“继续观察 / 接替 / 打开会话”三个明确动作。
- **严重度**：P0。

### S-04 · P0 · PM 在手机上完成验收闭环

- **问题**：验收单的“两步同屏”方向正确，但手机行内输入、证据、主按钮和“他端只读”没有解释谁能改、提交后谁负责收单；通知跳入后也没有回到原团队 / 项目位置。
- **位置**：`#ph-psheet`，证据见 `mobile-acceptance-sheet.png`。
- **改法**：手机验收单头部显示来源团队 / 项目 / 卡 id；每行显示可编辑端和证据责任；提交回填后按钮明确变为“确认收单”，失败项变为“已通知修复 · 查看修复卡”；完成后回来源页并刷新同一事件流。
- **严重度**：P0。

### S-05 · P0 · 派单失败或目标 worker 不可用

- **问题**：PM 需要知道任务是未派出、排队、已启动还是失败；原型直接把任务卡放进泳道，没有派单回执和失败处理。真实的派单失败会变成“看板上有卡但没人干”。
- **位置**：待认领 / 进行中列、成员编制、通知 alert。
- **改法**：卡片显示 dispatch id 和状态；派单失败进入行动队列，给“换成员 / 重试 / 暂缓”；成功后显示认领时间、分支 / worktree 和当前 liveness。
- **严重度**：P0。

### S-06 · P1 · PM 中断后回来重新建立上下文

- **问题**：页面有上下文百分比、活动时间和历史补洞，但没有“上次我离开时发生了什么”的项目 / 团队摘要，也没有将最近事件、未决决策、恢复动作按一次接管任务收拢。
- **位置**：团队标题、成员水位、活动页、会话列表。
- **改法**：增加“自上次查看以来”摘要：完成、失败、自动接替、待决策、验收变化；点击摘要定位到事件或卡，并标记已查看而不改变通知账。
- **严重度**：P1。

### S-07 · P1 · 团队规则或经验改变后验证影响

- **问题**：现网支持经验与铁律，原型没有入口；PM 无法看到某条规则覆盖谁、何时生效、是否替代旧规则，也无法把反馈沉淀为可检索经验。
- **位置**：团队详情缺失的经验 / 铁律页、设置和确认卡。
- **改法**：补经验 / 铁律页，显示 scope、audience、状态和来源；规则变更通过确认卡；从派单或验收失败反馈可跳到“申报经验 / 提议规则”，但必须区分建议与已生效规则。
- **严重度**：P1。

### S-08 · P1 · 桌面准备、手机执行、网页只读三端协作

- **问题**：验收单示例已经包含手机端、桌面端、网页端三组检查，但三端回填责任、冲突处理、端间同步时间没有显式规则；同一条未测项可能被两个端同时编辑。
- **位置**：验收单三分节 `#dt-sheet` / `#ph-psheet`。
- **改法**：验收单行增加“责任端 / 编辑锁 / 最后写入”；他端只读时显示谁持有编辑权和证据链接；冲突走判定记录，不静默覆盖。桌面、手机、网页都只消费同一 acceptance event stream。
- **严重度**：P1。

## 现网 IA 补全与视觉套用方案

### 桌面团队域

1. 保留“消息 / 看板 / 成员 / 活动”，将“经验 / 铁律”补在活动之后；默认仍进看板，但标题区显示“待你确认 N · 阻塞 N · 值守风险 N”。
2. `经验`页沿用现网已有筛选：范围（团队 / 项目 / 全局）+ 状态（在役 / 已退役 / 全部），原型视觉用工作面卡 + 胶囊徽章，不使用红色警示边框表达普通条目。
3. `铁律`页沿用现网两步退役 / 替代 / 批量导入逻辑；只把操作按钮改成原型的轻量 ghost / primary 语言，不改变权限和 append-only 审计语义。
4. “成员与派单”应从右侧辅助区上升为团队详情的稳定控制面：待确认、编制、最近回执、值守健康四组；不能只在看板卡里暗示有派单。

### 手机团队域

1. 不照搬桌面四 / 六 Tab；以现网 `TeamDetailPage` 的七节消费面为基线：待确认置顶、看板默认、编制折叠、活动、经验、铁律、熟手池 / 相关只读信息。
2. 顶部保留“看板总览吸顶联动”，但总览词表改为五态；活动、经验、铁律在目录或折叠头部可达，不藏到无法发现的 ⋯。
3. 手机只开放必要写动作：验收回填 / 收单、通知处理、反馈问题、接替确认；派单、规则批量导入、经验归组等高风险写面回电脑端，并在手机上明确写边界。

### 通知域

1. 桌面 rail 铃铛降级为 quick preview：只显示未决数和最近三条，不承载完整通知账。
2. v8.5 补全现网两列通知域：左侧轻列表 / 分组，右侧来源详情；详情必须带团队、项目、会话、事件时间、验收 / 决策 id 和回来源动作。
3. 手机沿用底部 sheet 的高频处理形态；进入来源详情后采用全屏二级页。已处理折叠保留，不把 `×` 当成解决。

### 玻璃拟态 / 阴影体系

- `surface0`：页面和壳底，禁止业务卡再加重阴影。
- `surface1`：工作区容器和普通卡，细边 + 低强度阴影。
- `surface2`：当前选中 / 可交互卡，品牌色只用于焦点线或主按钮。
- `glass-popover`：通知浮层、低频菜单、验收来源详情；使用半透明底和 `shadow-pop`，不用于所有卡片。
- `semantic-border`：只给 actionable / error / blocked；经验、铁律、动态事件不使用同样的强色边框。

## v8.5 原型修订优先级表

| 优先级 | 先做什么 | 验收标准 |
|---|---|---|
| **P0：先改再还原** | 五态看板词表；看板派单入口 + 回执；全局“需要你”；验收单统一 id / 回源；值守健康 / liveness / 自动恢复可见；多团队行动摘要。 | PM 能从首屏找到所有未决事项；能从看板派单并看到成功 / 失败；三入口打开同一张验收单；一个 worker 卡住时能看懂系统做过什么并接管。 |
| **P1：v8.5 产品化批** | 经验 / 铁律两面；通知完整两列域；通知生命周期；活动检索与三账关系；项目聚合筛选 / 来源 / 新鲜度；修复卡父子状态；跨端读写矩阵；五色状态灯。 | 与现网六面 IA 对齐；手机、桌面、网页对同一对象给出一致状态和来源；高事件量下能按团队 / 项目 / 类型 / 时间找事件。 |
| **随像素还原批收口** | 三层 surface / glass token；卡片密度档；字体、间距、边框、阴影；图标和焦点态；桌面 / 手机截图对齐。 | 视觉还原不改变状态语义；普通卡不再全量发光；行动卡、错误卡、动态卡能一眼分层。 |
