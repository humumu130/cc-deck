# C 路审查回执：多机编排域 PRD v0.1（产品+运维视角）

> 审查对象：`docs/specs/multi-device-orchestration-prd.md` ｜ 审查者：C 路（产品运维）｜ 2026-10-29
> 方法：以 1029 真实旅程（公司侧 Claude 想组队→PM 位被投影占用→不知入队口→fallback subagent→困惑靠用户传话）为基准走查 §4.2/§4.5/§4.6/§4.7，对照代码实证（org.ts / ccops.mjs / ~/.cc-deck/bin/org / README env 表 / pipeline-audit L-1029-4）。
> 断点编号 J-1~J-8，供 PM v0.2 修订逐条对照。

---

## 一、总评

PRD 对 1029 四痛点的**归因准确、范围诚实**：把「跨机传声筒=用户」定位为路由类型扩展而非新基建、接收侧零新逻辑面（§4.3）是正确的简化纪律、部署顺序引 #28 教训、§9 开放问题清单敢于自曝（含 leader 模式缺口）。投影 id 遮挡（§4.1 origin_sid 前置）的自我发现尤其有价值。

**但按本 PRD 落地后重放 1029 旅程，最后一公里仍然断裂**，而且是结构性断裂：PRD 把 **A→B（PM 派出）方向设计得很完备**，而 1029 的真实痛点恰好集中在**回程腿**——公司会话的反馈/回执怎么回到家里 PM。具体三处：L3 白名单在 per-relay 编制模型下跨机不可判定（J-4）、xmsg 帧没有回信地址（J-5）、痛点 D 的发送方向不在三口发送面里（J-6）。§2.1 声明「D 随 G1 解决」目前不成立。运维面上，设计复刻了 L-1029-4「静默失败三兄弟」（失败不分流/无告警/表面正常）约 6 处，需在 X1 就内置可观测性而非 X2 补。

结论：**方向通过，v0.2 修订后可立项**；修订焦点=回程腿闭环（J-4/5/6）+ 运维三件（O-1/2/3）。

## 二、旅程走查：公司侧 Claude 拿到 test.75 后的实际体验路径

按 PRD 全量落地（X1-X3）后的假想旅程逐步走：

| 步 | 动作 | 结果 | 断点 |
|---|---|---|---|
| 0 | 公司会话想组队，怎么知道有 `org join`？ | **不知道**。org CLAUDE.md 引导只随 Leader 会话 cwd 种子加载（org.ts:211 注释自证），外部会话的项目目录无任何指引；`~/.cc-deck/bin/org` 虽由 relay 启动物化（session-manager.ts:3554 ensureOrgCli）但不在 PATH、无发现面。1029 那个会话能跑 org status 靠的是用户口头指路。 | **J-1 发现面缺失** |
| 1 | 它跑 `org join <gid>`，relay 怎么知道「谁」在入队？ | **无法判定**。org CLI 是裸 HTTP POST + token（bin/org 头部自证），无调用方身份通道；现有 member-add 是 Leader 显式传 sid，join 的自荐语义要求系统识别调用会话，PRD 未定义机制。 | **J-2 归属面未定义** |
| 2 | join 成功——但它加入的是**公司机本机编制**，而用户心智是「加入家里那个团队」 | §4.5 原则「PM 是编制内角色不是机器属性」+ 各机编制独立 → join 只能进本机 org。跨机组队要靠家里 PM `org dispatch --remote` 打到公司 relay、由公司侧自己的编制消化。若公司机没建制/没 PM → `rejected:no-org-capability`，**然后呢？**B 机编制冷启动（谁 org create、谁当 B 机 PM）无旅程设计，PRD 止步于错误码。 | **J-3 冷启动无旅程** |
| 3 | 家里 PM 派任务书过来，公司会话收到注入，干活 | 此段通（§4.3 复用本机注入链，设计干净）。但任务书>8KB 会被红线拒（§4.4 长度上限 8KB）——现行派单任务书普遍带背景/验收点，实测经常超 8KB；文件走 artifact 链是**本机的**，跨机文件传输被 §2.2 列为非目标 → 超限任务书**没有任何通道**。 | **J-7 任务书运力缺口** |
| 4 | 干完活，回执怎么回？ | 两条路都断：a) §9.1 建议的「B 机收割后摘要回」——摘要仍是 xmsg，从公司 PM 会话发往家 relay，**家侧 L3 白名单按本机编制判定，公司会话不在任何本机编制账上 → 默认全拒**；b) 公司 worker 直接回 → 同样被 L3 拒。「编制内 PM 会话」的编制是 per-relay 本地数据（§2.2 非目标明示不全局化），**L3 的判定依据在检查侧根本不存在**——这是本 PRD 内部两节（§4.4 vs §2.2）的结构性矛盾。 | **J-4 回程腿结构性断裂**（P1 首） |
| 5 | 1029 的原始场景：公司会话**主动**想把困惑反馈给家里 PM | 发送面三口（§4.2）：ccops send（标注 PM 用）/ org dispatch --remote（编排面）/ 会话卡按钮（人工面）。**没有一口是「普通会话→远端 PM」**。L3 默认下该会话无发送权（除非用户逐会话显式授权——恰是 1029 里没人知道要做的事）。 | **J-6 痛点 D 方向缺发送口** |
| 6 | 收到消息的会话想回信 | xmsg 帧（§3.2）只有 `from: <dev>`，**无 source_session / reply-to**。收端会话看到一段注入文本，不知道发件会话是谁、在哪个 dev、用什么命令回。§8.2「双向闭环」验收无实现路径。 | **J-5 帧缺回信地址** |
| 7 | 家里 PM 想给公司某会话发消息，sid 从哪来？ | 投影卡透出 origin_sid 是 §4.1 前置，但**不在任何批次交付清单里**（X1 只列帧协议+接收口+ccops --dev）。X1 的 PM 只能手抄 sid。 | **J-8 X1 缺自身使能件** |

**走查结论**：7 步中 0-2 步（发现→归属→入对编制）与 4-6 步（回程三连断）仍断。1029 旅程的「用户当传声筒」环节，落地后**大概率依旧靠用户传话**（J-6）或退化成「用户显式授权每个会话」的新负担。

### 各设计节点单独评价

- **§4.2 发送面**：三口覆盖 PM→远端、编排→远端、人→远端，缺「会话→远端」（J-6）。三口全走本机既有命令鉴权是对的。
- **§4.5 PM 语义**：「远端 PM 段」直接消解 1029 的「查到不认识的 leader id」困惑，好。但与 §2.2 各机编制独立合起来产生了 J-4 的白名单判定矛盾，v0.2 必须显式调和。
- **§4.6 自检**：探测指令「列 subagent/工具清单，30s 无响应降级」——**探测的返回通道未定义**（目标会话用什么命令回报？回报给谁？）、探测注入会打断正在干活的会话（时机无设计）、「台账记因」给谁看（PM 派单响应里带降级原因吗？若只在台账=又一个无人看的账本，L-1029-1 同族）。
- **§4.7 入队口**：「待确认+确认卡」防混入是对的，「人话指引」好评；但见 J-1/J-2，命令存在≠旅程可用。

## 三、运维缺口（对照 L-1029-4 静默失败族「失败不分流/无告警/表面正常」三特征普查）

本设计内同族风险点 **6 处**：

| # | 缺口 | L-1029-4 对应特征 |
|---|---|---|
| O-1 | **xack 终态发送方看不见**：`ccops send` 现实现是 ws.send 即返（bin/ccops.mjs:29-36），xack 的 `rejected:<reason>` 回到 relay 后若无落点（ccops 已退出/PM 会话非同步等待），拒绝原因蒸发。最高频的 rejected:no-such-session（投影 id 与 origin sid 混用，J-8 未解前必高发）会变成「发了没反应」——与「9 分钟无回流无通知」同款体感 | 失败不分流+无告警 |
| O-2 | **outbox 积压与 TTL 过期无观测面**：§4.8 断线落盘排队 24h、过期入 loss 账——无 `ccops outbox` 查询口、无面板域、无巡检项。公司机隔夜关机是常态，早晨看什么？loss 账是 L-1029-1 已实证的「无人看的账本」 | 无告警+表面正常 |
| O-3 | **ack_req 默认值未定义**：若默认 false，多数流量零终态回传=系统性静默 | 无告警（制度性） |
| O-4 | **CCR_XMSG 关=清空 outbox（§5）是破坏性操作**：排障场景下用户关开关会静默销毁在途消息，与 §8.4「无重无丢」精神矛盾 | 失败不分流 |
| O-5 | **探测降级「台账记因」无消费面**（§4.6，同上） | 表面正常 |
| O-6 | **CCR_XMSG 无文档面**：README.md:205-211 已有 env 表是既定落点，PRD 未提；灰度只两台=开关知识只活在 PM 脑里，下次排障时「这功能到底开没开」要翻代码 | 表面正常 |

**建议的最小运维三件（X1 就带，不进 X2）**：① ccops send 同步等待终态或落本机通知（rejected 人话映射：no-such-session →「可能是投影 id，需 origin sid」）；② outbox 水位入面板+patrol 必报项（沿 #268 诊断面板先例）；③ ack_req 缺省 true（PM 面）。

## 四、P1（必修于 v0.2，否则立项即返工）

1. **J-4：定版跨机白名单权威**。三选一需 PM 拍板：(a) join 确认卡放行=双机互认的 L3 授权（用户点 ✓ 这个动作同时完成授权，最顺 1029 心智）；(b) RouterDO 维度做配对级「可互通编制」登记；(c) 回执腿不走 xmsg 而走系统帧（xack 扩展）豁免 L3。不定版，§8.2/§8.5 两条验收结构上无法通过。
2. **J-5+J-6：帧补 `source_session`/reply-to，发送面补第四口**（普通会话→远端 PM，或明确「join 放行即获反馈通道权」的叙事）。否则「D 随 G1 解决」的声明要删掉，痛点 D 依旧靠用户传话。
3. **运维三件进 X1**（O-1/2/3）——静默失败族必须在首个灰度批就可见，L-1029-4 刚花过一次全链学费。
4. **J-1：入队口可发现性最小件**。最低成本组合：面板/投影卡加「复制入队指令」一键（生成 `~/.cc-deck/bin/org join <gid>` 全路径命令）；org join 无参/无 gid 时的人话指引（PRD 已有）保留。
5. **J-8：origin_sid 透出列入 X1**（SNAPSHOT/投影帧加一字段，工作量小），否则 X1 的「最小闭环」两机手测都要手抄 sid，闭环不闭。

## 五、P2（随批修或入施工任务书）

1. J-2：org join 显式身份参数（`org join <gid> --sid <self>` 或读会话环境变量），别让 relay 猜调用者。
2. J-3：`rejected:no-org-capability` 附人话下一步指引（「公司机需先建制：org create + member-add」，或指向文档）。
3. J-7：8KB 上限与任务书实测体量对表；超限任务书定义降级编码（截断+摘要）或提高 dispatch 信封上限。
4. O-4：开关关闭时 outbox 保留待确认而非直接清空。
5. O-6：CCR_XMSG 进 README env 表 + 灰度设备清单写进 PRD 附录。
6. §4.6：定义探测指令内容、回报通道、探测时机（目标忙时 defer）。
7. 限速（每对 dev ≤2/s）标注执行点（发送侧 or RouterDO）；幂等 10min 窗口外的重复投递语义补一句。

## 六、分期与验收意见

**§6 分期**：
- 排序大方向认可（先窄口闭环再安全再编排）。两处调整建议：
  - **痛点 B/C 升格为 X0 与 X1 并行**：二者纯本地、零跨机风险，而 C（org join）是 1029 旅程里性价比最高的单件——不等 X3。PRD 已注明「可并行提前」，建议从括号备注升为批次决策，避免施工时被当注脚忽略。
  - X1 未含 origin_sid（J-8/P1-5）且无 L3/outbox（安全面 B 路会重点打）——若 X1 维持现状范围，须在批次卡明示「X1 期两机手测需手抄 sid、无白名单、无断线排队」三条已知裸奔项，防手测结论误当生产可用。
- **X1 对用户可感知吗**：半可感知——「家里 PM 能戳公司会话」是真价值，但发送 sid 手抄（J-8）+ 回执不可见（O-1）会让首体验像「发了封不知道到没到的信」。按 P1-3/P1-5 修后 X1 才有可演示的完整体感。

**§8 验收点**：
- 第 5 条（E2E）**当前不可判**：依赖 §9.1（回执方向）未拍板 + J-4 白名单未定——它自己的开放问题卡着自己的验收。且「公司侧 Claude 实测」是开放式的 AI 行为步骤，需改成断言式证据三元组，例如：
  - join：公司会话跑 org join → 家侧面板出现确认卡（证据：卡 id）→ ✓ 后编制含该会话（证据：org status 输出）
  - 派单：PM org dispatch --remote → 公司会话注入队列出现任务书帧（证据：events.ndjson 条目 + xack injected）
  - 回执：**回执条目出现在 A 机 PM 可见面**（证据面按 §9.1 拍板结果定）——「干活」质量不入判据，判据=回执到达
  - 另需补一条运维验收：rejected 场景发送方在 30s 内看到人话原因（O-1 的验收化）。
- 第 1-4、6 条可判性良好；建议第 4 条补「outbox 水位在面板可见」作为附带断言。

**施工锚点缺口**（worker 做偏风险点，PRD 自称非任务书，但以下缺了会做偏）：
- 接收挂点文件未指：cloud-client.ts 帧分发处、ext-input-queue 结构与消费口、SNAPSHOT/投影帧生成处、确认卡通道复用点——PRD 全文只有一个代码锚（router.ts:141）。建议 v0.2 附「代码锚点五件」清单。
- join 调用方身份、探测回报通道（P1-1/P2-6 同源）未定义，worker 会各自发明。

## 七、一句话结论

PRD 把「去程」设计到位了，但 1029 买家的痛点在「回程」——v0.2 把 J-4（白名单权威）、J-5/J-6（回信地址+第四口）、O-1/2/3（运维三件）三组修掉，这个域就真正接住了它立项所引的那份实证。
