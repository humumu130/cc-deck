## 一、总评

v0.2 的租户方向（D3 一步到位·协议层）与存储分层（桥 DO 权威+relay 单表）是对的骨架，G6 的分层红线（自动连上≠自动可注入）是好纪律。但**以「迁移者」视角走查，PRD 写的是终态，藏的是过渡**：

1. **存量迁移没有旅程，只有一句话**。§4.5-③「已配对设备由桥主面批量导入租户（一次性，无逐台重配）」——但 22 台设备的身份账本在两台 relay 的 cloud-peers.json 里，**桥上一无所有**（router.ts 纯内存，A 路纠错⑤自证）；桥主面「设备列表」这个 UI 的数据源在当前架构下不存在。且验收 7「未入租户设备对桥内任何 dev 不可见不可达」若按字面在 register/路由层实施，**桥发版瞬间全部存量连接断掉**，直到导入完成+设备侧拿到凭证——迁移窗口的连续性语义完全未定义。
2. **G6「点选即连零配对码」与 relay 现信任模型正面冲突**。relay 今天丢弃一切未配对设备的帧（cloud-client.ts:759），配对=本机用户亲手授权。「自动连接同租户 relay」要求信任根从「本机配对」转移到「租户凭证背书」——这是 G6 最重要的架构决定，§4.4 C 层一句「租户凭证+wss」没有点破，两种落地体验与安全差异巨大。
3. **「n=1 零特判代码路径」≠「n=1 零新增步骤」**。自部署用户 T1 后从「什么都不做」变成「成为桥主→生成租户码→每设备输码」，这段用户旅程差距被协议中立性叙述盖住了；公共桥（cc.humumu.online 默认 URL）上的陌生存量用户更是全程无叙事。
4. **桥主面最小版不可施工**。web-console 是静态页，DO storage 无 HTTP 面可达；「首个 relay 即桥主」在 register 收任意 dev 的桥上无法判定。T1 三个交付件（桥主面/注册码/存量导入）全部悬空。

结论：**租户骨架通过，T1 施工前必须补一轮迁移与链路定版**（J-9/10/11/15/16/18 六条 P1），否则 T1 做出来即是「新设备能用、存量用户受伤、桥主面点不动」的半成品。

## 二、断点清单（J-9 起，续 C1）

### 专项 1：存量迁移旅程（22 台已配对设备 + 2 relay）

**J-9（P1）批量导入的数据源不存在——桥侧缺「设备登记表」**
桥主面要「设备列表（踢出）+ 批量导入存量入租户」，但桥零持久化：在线时有 connOf/keyOf（内存，DO 休眠即失），离线设备的 dev id/公钥桥根本不知道。22 台设备的权威账在两台 relay 的 cloud-peers.json（各知一半：家 relay 知家里手机/手表/网页，公司 relay 知公司侧），PRD §4.5 存储模型只列「租户表/tenantOf/注册码/踢出名单」四样，**没有设备表**——踢出名单要踢的对象、导入要导的主体、互信审计的分组维度全挂在这张缺表上。
**修订建议**：T1 增第五张桥侧表「设备登记表」（dev/pubkey/last_seen/tenant，首次 register 落 DO storage），桥主面设备列表与批量导入以它为源（勾选 N 台一键入租户）；或明示批量导入=向导式从各在线 relay 拉 peers 合并（画出数据流+relay 侧授权方式）。二选一必须进 PRD。

**J-10（P1）迁移窗口连续性未定义——验收 7 字面语义=升级即全断**
验收 7「未入租户设备对桥内任何 dev 不可见不可达」没有说**在哪一层实施**：若在 register/定向路由层，桥发版瞬间（tenantOf 为空）22 台存量+公共桥陌生设备全部不可达，直到桥主完成批量导入**且每台设备侧拿到租户凭证**（手机还要升级 App——见 J-11）；若只在 disc/pair_req 广播层，存量 rd 直连存活、新配对死亡。PRD 两处口径还自相矛盾：§4.5-③ 说存量「一次性批量导入」，§5 说「租户注册码首版仅用户两台设备（桥主+首设备）」——到底是 22 台一次迁还是先迁 2 台？迁移时序（先发桥版→导入→再启用过滤？）零字。
**修订建议**：定版过滤生效边界为「**租户过滤只对已绑租户的设备生效，tenantOf 为空/未绑定的 dev 走兼容模式（定向路由照旧、disc 不列）**」；§5 与 §4.5 口径统一（建议：桥发版当天全量导入 22 台，灰度开关管的是 xmsg 不是租户）；补一条迁移验收（见 §四）。

**J-11（P1）存量手机端旅程空白——旧 App 无邀请码入口，「远程源」生死未卜**
「配对码退役为桥主邀请码」意味着：旧版 App（无输租户码 UI）的**新设备配对路径消失**；存量手机升级 App 后，租户码在哪输（CloudPairInfo 加字段？独立的全局身份页？）、输完之前已有的 cloud 条目（rd 直连）是否继续工作——PRD 全空白。验收 9 只测「新绑租户的手机」，22 台存量手机（含手表 wt-*、网页 wb-*）的升级旅程一条没有。
**修订建议**：① 明示「存量已配对条目终身有效，rd 直连不受租户过滤影响」（与 J-10 联动）；② App 侧改造清单进 T1 批次卡：租户凭证存储位置、输码入口（建议挂在现有「配对码」入口的原位改造而非新页面，规避 §2.2 非目标）；③ 手表 wt-*（wan 明文通道）在租户过滤下的地位一句话定版（滤不滤）。

**J-12（P2）版本兼容矩阵缺两格**
验收 6 只覆盖「旧 relay×新桥」；缺「旧手机×新桥」（旧 App 的 disc 收到租户过滤后的 RELAYS=空列表时呈现什么？配对码入口还在吗？）与「新手机×旧桥」（租户凭证发给不支持租户的桥会怎样）。C1 对 v0.1 混跑只关注了 relay 侧，端侧混跑是 T1 特有的新面。
**修订建议**：PRD 附 2×2 矩阵（桥新旧×端新旧）各格行为一句话；旧 App 建议降级路径=「列表为空时提示升级」而非静默空白。

### 专项 2：开源自部署零回归

**J-13（P2）「n=1 零特判」藏住了用户新增步骤——README 旅程无人改**
今天 README 场景：wrangler deploy（4 条命令）→ relay 设 CCR_CLOUD_URL/TOKEN → 手机重新配对一次，**零租户零管理面**。T1 后同一用户：部署桥→**成为桥主（怎么 claim？见 J-18）**→进桥主面生成首租户码→每台设备输码。代码路径零特判是真的，用户旅程多了两三步也是真的，而 PRD 用「单租户是 n=1 特例」一句把这段盖住；README（n=1 用户唯一旅程文档）的改造未列入任何批次。
**修订建议**：PRD 附「自部署 n=1 旅程对照表」（今天 3 步 vs T1 后 N 步，每步在哪个面做）；把「首 relay 自动建租户+自动打印首枚注册码」（零人工桥主面操作）列为 T1 验收项——只有做到这条，「零回归」声明才成立；README 增补列入 T1 批次卡。

**J-14（P2）公共桥陌生存量用户无叙事——他们正是痛点 E 的人群**
README 默认 CCR_CLOUD_URL=wss://cc.humumu.online/cloud（公共 token 人尽皆知）：没自部署的开源用户今天全挂在这座桥上，互可见（disc 列全桥）。T1 租户化后他们的归属未定义——自动入某租户？找谁领码？还是落入验收 7 的「不可见不可达」静默锁死？§4.5 只写了「自部署用户=自己当桥主」视角，公共桥多租户的发放策略（申请制/自服务/停收新设备引导自部署）零字。
**修订建议**：§4.5 增「公共桥租户发放」一段，v1 哪怕定「公共桥冻结新陌生设备+存量陌生设备归入独立 sandbox 租户互不可见，引导自部署」也要定版；否则 T1 上线对这批用户是静默断连（L-1029-4 静默失败族同款，发生在协议层）。

### 专项 3：G6 自动互联的真实体验

**J-15（P1）「点选即连零配对码」与 relay 信任模型冲突未定版——G6 的核心架构决定没做**
relay 今天对一切 peers 表外设备的帧直接丢弃（cloud-client.ts:759+notifyUnpaired），手机连 relay 的前提=本机用户亲手配过对（peers 里有手机公钥）。G6 要求「绑租户后点选即连、鉴权=租户凭证+设备密钥、无 per-relay 配对码」——这只有两条路：(a) **保留 peers 校验**：自动连接不成立，点选后被 drop，G6 验收 9 结构性不可过；(b) **peers 校验让位租户背书**：relay 接受「桥背书的同租户陌生设备」自动 addPeer——信任根从「本机用户亲自授权」变成「持租户码者皆可连我全部 relay」，租户码泄露的爆炸半径从一座桥扩大到 N 台 relay（风险表「码泄露=中」的评级在此落地方式下偏低）。§4.4 C 层「租户凭证+wss」没有点破这个选择。
**修订建议**：§4.4 增小节「租户背书设备的 relay 侧准入」定版，建议走 (b) 的收窄版：桥侧 tenant 背书下发+relay 自动 addPeer（entry 标注 `source:"tenant"`、可一键按来源批量移除），并在风险表更新泄露半径；同时定手机侧租户凭证与多桥（CCR_CLOUD_URL 逗号多桥）的对应关系。

**J-16（P1）验收 9 跨批依赖——T1 验收引用 X1 的件**
first-contact 确认卡是 X1 交付件，G6 塞在 T1；验收 9 后半句「首条 xmsg 仍弹 first-contact 确认卡」在 T1 期无 xmsg 链路可验。C1 已指出过 v0.1「开放问题卡住自己验收」的同族问题，v0.2 换了个形态复发。另 T1 的「端侧自动发现」依赖 App 发版（expo OTA/整包+碎片期），批次卡无此交付面标注。
**修订建议**：验收点逐条标注归属批（9a 自动发现归 T1、9b 分层红线归 X1——X1 验收再跑首条 xmsg 弹卡）；T1 批次卡注明含 App 端发版依赖与最低支持版本。

**J-17（P2）§2.2 非目标「手机端新增 UI」与 T1 内容自相矛盾**
「远程源列表自动出现同租户 relay」= 手机源列表行为改造（租户凭证存储/disc 逻辑/新条目生成），是实打实的 App 代码+发版。非目标表述需精确化，否则施工侧拿它当挡箭牌漏做 App 面。
**修订建议**：§2.2 改为「手机端不新增管理页面 UI；源列表/凭证行为的协议适配随 T 批」。

### 专项 4：桥主面最小版的链路空白

**J-18（P1）桥主面→DO storage 通道未定义 +「首个 relay 即桥主」不可实现**
两个叠加的空白：① web-console 是四处部署的静态页（cc-plugins/Nova/relay/CF assets），运行时连 relay（同源 ?token=）或直连云桥（BAKED_BRIDGE_TOKEN——这是**全体设备共享的连接凭证**，不能当 admin 凭证）；CF worker 现 HTTP 面只有 //app //view/ //dl/ /health，**DO storage 没有任何面可达**。桥主面操作租户表的三条可能路径（worker 新 /admin HTTP 口+独立 admin 凭证／桥 ws admin 帧+桥主设备身份／relay 代理转发）PRD 一条没选，T1「桥主面最小版」不可施工；运维排障（踢了没生效？码发不出？）无日志无观测面。② 「首个 relay 即桥主」在 register 收任意 dev 的无状态桥上无法判定「首个」，桥主身份需要 bootstrap 凭证（如 wrangler secret ADMIN_KEY、首个持钥者 claim），PRD 未定义。
**修订建议**：定版通道——建议 worker 增 /admin/* HTTP 路由+ADMIN_KEY（wrangler secret 部署期设定，首个持 ADMIN_KEY 的会话 claim 桥主、此后 admin 面用它鉴权），桥主面由 CF assets 同域承载（免 CORS 免新静态部署位）；桥主操作全量入 DO storage 审计日志+`/admin/audit` 只读口，运维排障有账可查。

**J-19（P2）踢设备的 enforce 层悬空——验收 8 不可施工**
踢出名单存 DO，但被踢设备仍持有效 CLOUD_TOKEN（公共桥上人尽皆知）可再 register 任意 dev——包括**冒名顶替租内在租 dev**（register 同 dev 顶替机制 close 4000 会被武器化成顶替 DoS，把真设备踢下线）。E2E 密封保内容不保在线权。验收 8「被踢设备后续帧全拒」在现状架构下没有实施位置。
**修订建议**：T1 定版「register 时校验 dev↔tenantOf+踢名单按 pubkey 而非 dev 字符串」；冒名顶替（同 dev 抢占）在桥层的裁决归置与 B 路冒名面合并处理（建议 register 携带设备密钥签名，桥验签再落座）。

### 专项 5：T2 前注册码当账号的体验债

**J-20（P2）多码记忆债与找回路径**
多桥并存（公共桥+自建桥，CCR_CLOUD_URL 原生支持）=多套租户码多套设备身份，码的保管责任全在用户；码丢失=新设备进不了租户（桥主可重发——但前提是 J-18 的桥主面真实可达）；自部署用户的桥主凭证（ADMIN_KEY）丢失只剩 wrangler 后门（有服务器权限=可接受，但要写明）。这些 T2 前的过渡约定 PRD 零字。
**修订建议**：§4.5 增「T2 前过渡约定」三条：码可随时重发且旧码即废（消除「码丢了=租户丢了」恐惧）；relay 侧 cloud-peers.json+租户身份纳入既有导出备份（importPeers API 已在，补租户字段）；README 写明「码=房钥匙」保管口径。

**J-21（P2）互信表审计视图的聚合链路又一处 J-18 同族空白 + 存储表述失配**
桥主面承诺「互信表审计视图」，互信表却 per-relay 本地（device_trust）；聚合视图需跨 relay 拉取，通道未定义（与 J-18 同根）。且「桥侧映射不复制到 relay」纪律下 relay 无从预知同租户 dev，审计聚合要么运行时向桥查、要么降级分片显示。另外 §4.5 说 relay 侧「SQLite 仅加一张 device_trust」——现状 peers 是 cloud-peers.json 文件不是 SQLite，表述与仓库事实失配（小，但施工会照抄开错文件）。
**修订建议**：桥主面 v1 互信审计降格为「按 relay 分组只读视图（经 relay ws 拉取）」或明示范围仅桥侧账；存储表述改为「relay 侧新增 device_trust 表（SQLite）；既有 cloud-peers.json 维持文件形态不迁移」。

## 三、验收 7-9 可判性

| 验收 | 判 |
|---|---|
| 7（未入租户不可见不可达） | **当前不可判**：实施层未定（J-10），且字面语义与存量迁移正面冲突——按字面实施=升级即断 22 台。建议改为「未入租户的**新注册**设备」+另立迁移验收（下条）。 |
| 8（桥主面踢设备生效） | **不可施工**：桥无设备表（J-9）+enforce 层未定（J-19）。两 P1/P2 定版后补断言「被踢设备以新 dev 再 register 也被拒」。 |
| 9（G6 自动发现+分层红线） | 前半句 T1 可验但依赖 J-15 定版（否则点选即连不成立）；后半句（first-contact 弹卡）是 X1 的件（J-16）——拆 9a/9b 归批。 |
| **缺失** | 全文无一条迁移连续性验收。建议补：**「存量已配对手机（未升级 App）在 T1 桥发版+批量导入后，既有远程源连接不断、快照正常」**——这是 22 台用户（=用户本人）最关心的一条，比任何新功能验收都优先。另补自部署 n=1 全链回归验收（J-13）。 |

## 四、修订优先级汇总

- **P1（T1 施工前必须定版，共 6）**：J-9（桥侧设备登记表/导入数据流）、J-10（过滤生效边界+迁移时序+两处口径统一）、J-11（存量手机端旅程+旧条目终身有效）、J-15（租户背书准入规则=G6 核心架构决定）、J-16（验收 9 拆批归属）、J-18（桥主面通道+桥主 bootstrap）。
- **P2（随批修）**：J-12（兼容矩阵）、J-13（n=1 旅程对照+自动建租）、J-14（公共桥陌生用户策略）、J-17（非目标表述）、J-19（踢出 enforce）、J-20（过渡约定三件）、J-21（互信审计降格+存储表述）。

## 五、一句话结论

PRD 把租户的终态画对了，但 T1 是一次**带着 22 台活设备过桥**的手术——桥主面三个交付件悬在未定义的链路上（J-18），迁移窗口的连续性没定（J-10），G6 的核心信任决定没做（J-15）；这三刀补上，「一步到位」才不会变成「一步到位断一片」。

— C2 路（租户体验与迁移专项），2026-10-29
