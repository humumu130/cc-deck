## 一、总评：五个攻击者模型 vs PRD 覆盖度

| 攻击者模型 | PRD 覆盖 | 判定 |
|---|---|---|
| 1. 持注册码的陌生设备（半信任成员） | §4.5「绑定租户」+ G6「自动互联」——**入租户即得什么权力，PRD 未定义**。现状 peers 表语义=全权（COMMAND_TYPES :45-84 含 EXT_INPUT/ORG_CONFIRM/PERM/DISPATCH），G6 明文「无 per-relay 配对码，点选即连」 | 断言缺失，见 P0-1 |
| 2. 被踢设备（残留凭证/重放） | 验收 8「被踢设备后续帧全拒」一句——活连接/互信表/同钥重入/legacy 旁路四缺口全空白 | 见 P1-4 |
| 3. 恶意租户（跨租户） | §4.5「跨租户帧=ROUTE_MISS」+ 验收 7「不可见不可达」——方向对，但与验收 6（旧 relay 零影响）直接冲突，null-tenant 路由语义未定义=旁路常开 | 见 P1-5 |
| 4. 桥主面（谁能当桥主/提权/XSS） | §4.5「首个 relay 即桥主」「v1=web-console 管理页」——**鉴权设计一个字没有**；且 §1-E 自陈动机就是「桥被多用户共享」，共享桥上首连即桥主=接管原语 | 见 P0-3 |
| 5. DO storage 直接攻击（Worker API 打 tenantOf） | §4.5 存储模型只写了「权威单点」，无 API 面鉴权/限流/审计/容量防护设计 | 见 P0-2/P2-8 |

一个贯穿性事实先立住：**现状设备权力的真正边界是 relay 本地 cloud-peers.json（per-relay 配对码换 addPeer），桥上没有任何权力**。G5/G6 做的事是把信任根从「每台 relay 的配对码」整体搬到「桥侧 tenantOf + 注册码」——信任根搬家没问题，问题是 v0.2 只搬了根，没搬「根上长什么叶子」：成员设备拿到的是哪一档权力，从全权的 COMMAND_TYPES 里裁掉了什么，PRD 一个字没写。T1 施工时工程只好看现状 peers 语义照抄——那就是 P0-1。

## 二、P0（不补设计不立项 T1）

### P0-1 G6 自动互联=注入人闸整体旁路：租户成员一步拿到的是「全权 peer」而不是「连接」

**PRD 原文**（§4.5-G6②）：「端绑租户后远程源列表自动出现同租户 relay，点选即连（鉴权=租户凭证+设备密钥，**无 per-relay 配对码**）」；分层红线只写在 xmsg 上：「注入层 first-contact 人闸不随之放开」。

**代码事实**：relay 侧对一个「已配对 peer」的放行面是 COMMAND_TYPES 白名单（cloud-client.ts:45-84），里面有——
- `COMMAND_EXT_INPUT`（**直接注入 CLI 输入框，bridge.extInput 同一条链**）
- `COMMAND_ORG_CONFIRM`（**批准待决确认卡**——P81 语义「勾选跳过权限确认=授权本身」，peer 可批规则追加/派单类卡）
- `COMMAND_PERM`（改权限模式）、`COMMAND_DISPATCH`（派单）、`COMMAND_LOGIN_GRANT`（引擎登录授予）、`COMMAND_PEER_KICK`/`COMMAND_PEERS_IMPORT`、`COMMAND_SETTINGS_UPDATE`
- hello/ping 即回 **SNAPSHOT 全量投影**（cloud-client.ts:455-530）：sessions（含逐会话日志，预算内最多 700KB）+ deliverables + acceptances + allow_rules + 员工家设置 + projects + org_confirms（待决卡内容）+ boards（任务板全文）+ experience + rules + notifications

即：**今天一条 per-relay 配对码（10 分钟一次性）换到的全权，G6 之后一份注册码换到、且对租户内全部 relay 同时换到。**「first-contact 人闸」只管新发的 xmsg 通道，管不着既有的 Command 通道——而 Command 通道里的 EXT_INPUT 就是注入原语。分层红线拦的是新门，旧门整个没锁。

**攻击链（攻击者模型 1，半信任成员；步骤化）**：
1. 从队友聊天记录/截图拿到注册码（泄露场景见 P0-2），输码入租户——桥侧 tenantOf 落一行，零人审（PRD 未规定入租户需桥主确认）；
2. G6②：远程源列表自动出现全部同租户 relay，逐台「点选即连」——relay 无法本地验证租户（§4.5 纪律：桥侧映射不复制到 relay），只能信桥只路由同租户帧，即**成员资格=peer 资格**（或施工时直接 addPeer，语义等价）；
3. 对每台 relay 发 hello → 收 SNAPSHOT：全部会话标题/模型/状态/逐会话日志、待决确认卡全文、任务板、通知、交付物路径——** fleets 级泄密，无需任何注入**（验收 9 恰好验证了这个「正常功能」）；
4. 发 `COMMAND_EXT_INPUT` → 走既有密封 Command 链直落目标会话输入框——**first-contact 人闸不存在于这条链上**，注入完成；
5. 发 `COMMAND_ORG_CONFIRM` 批掉目标 relay 上挂着的确认卡（规则追加卡/高风险派单卡）→ 治理面失守；
6. 既有补偿告警失效路径：`PAIRED_DEVICE` 通知（cloud-client.ts:707-712）设计意图是「新设备获得全权的瞬间告警持有者」——自动互联下每个成员都走这条路，告警常态化=告警死亡；若 T1 实现「自动互联不动 peers 表」则告警干脆不响，注入却已通过（步骤 4 的 Command 链只要 peers 表里有条目就通——设计若不新增成员档位，施工唯一选择就是 addPeer）。

**爆炸半径**：一台半信任设备 = 租户内全部 relay 的读全量 + 注入 + 审批。比 B1 路七步链更短——B1 链还需要先攻陷一台机器读 bridge-token，这条链只需要一个注册码。

**缓解设计（成员档位制，建议入 PRD §4.5 为 normative）**：
- 拆三档，自动互联只授最低档：**T-conn**（可达/在线可见/xmsg 可发——受 first-contact 人闸）/ **T-proj**（SNAPSHOT 投影，需**目标 relay 侧**确认卡逐台授予）/ **T-control**（Command 通道，保持现状配对语义或显式授予，绝不随租户身份自动获得）；
- G6② 的「点选即连」改语义：点选发出的是 T-proj 申请卡，弹在**被连 relay 的持有者**面板——现在 PRD 里点选的动作方是成员设备用户，被连方无感知，这个同意方向必须倒过来；
- COMMAND_EXT_INPUT/ORG_CONFIRM/PERM/LOGIN_GRANT 四类在 relay 侧增加「peer 来源=租户自动互联」时拒绝的断言（T-control 未授即拒），测试锚定验收 9 扩展版（见 §四）。

### P0-2 注册码生命周期：一句话撑不起信任根（生成/熵/时效/次数/防爆破/入租户审批全缺）

PRD 全部相关文本=§4.5「桥 admin 生成租户注册码 → 新设备输码」+ §7「码短时效+桥主可吊销+踢设备」。以注册码现在的设计地位（=整个租户的入场券，泄漏后果=P0-1 整链），这个规格量级差三个数量级。

**缺口清单与对应攻击**：
1. **熵与形态未定**：若沿用配对码 6 位数字风格（10^6 空间），桥侧 enrollment 无任何码尝试预算——Worker 层 /cloud 建连**无 per-IP 连接频率限制**（worker.ts:338-360 只有容量门禁；rateOk 只管建连后的帧 :624 与 poll POST :479）。攻击者分布式 IP 反复建连爆破：30 次窗口预算是 relay 侧 pair_req 才有的（cloud-client.ts:684-696），桥侧 enrollment 是全新面，照抄现状=零预算。「码短时效」在无尝试预算下只延长爆破时长，不封死；
2. **使用次数未定**：一个码能入几台设备？PRD「新设备输码」复数语义+「桥主可吊销」暗示长期多用途码。多用途=一次泄露无限入场；还有容量 DoS（P2-8）；
3. **吊销的止损边界未定**：吊销码是否连带踢出该码入场的设备？PRD 分开写「吊销码」「踢设备」两个动作=不连带。即码泄露后，止损需要桥主在设备列表里**人工认出**哪些是恶意设备——半信任场景下恶意设备和正常同事设备在列表里同形（dev/名字皆自报）；
4. **入租户无审批闸**：输码即入（对照：relay 配对至少要持有者开码+10 分钟时效+一次性）。注册码=「知道即成员」，且成员资格立即兑现 P0-1 的全权面（若不修）；
5. **凭证呈现位置未定**：现有建连凭证（token）走 URL query（worker.ts:341，B1 P1-1 已裁）。T1 若照抄把注册码放进 /cloud 的 query——它就进了 CF 访问日志和 TLS 中间盒，等于把租户入场券写进日志系统。

**缓解设计（建议 PRD §4.5 增「凭证规范」节）**：码熵 ≥128-bit 随机（不可枚举形态，Base32 至少 26 字符）；TTL 默认 24h 可按次缩短；**一码一设备**（入场即耗尽）+ 入场需桥主确认卡（半信任模型下这是唯一人闸，与 G6 分层红线同构：连接层自动≠入租户自动）；桥侧 per-IP + per-code 双尝试预算（照 relay pairBudget 先例 :684-696）；码走鉴权后首帧/ header，禁 URL query；enrollment 全量入审计（谁/何时/哪个码/IP）。

### P0-3 桥主面零鉴权设计：「首个 relay 即桥主」+ 管理页落在无 CSP 资产面上

T1 施工项含「桥主面最小版」，PRD 对它的全部设计=「首个 relay 即桥主」「v1=web-console 管理页：生成/吊销注册码、设备列表（踢出即吊销密钥）、互信表审计」。桥主面的权力=租户根权力（发码=招成员、踢设备=断生产、看互信表=看全部信任关系）。三个叠加缺口：

**（a）桥主身份无凭证**。共享桥场景（§1-E 自陈动机：开源用户/团队共用一座桥）下「首个 relay 即桥主」=**谁先连谁称帝**：公共桥 PUBLIC_TOKEN 选项在场（worker.ts:11）时入场无门槛，攻击者在对等场景抢首连即获得对他租户设备的踢出权与全桥设备列表。即使私有桥，DO storage 丢失/重置（§7 只给了「桥主导出备份」的手工兜底）后下一台连上的 relay 即接管——**桥主必须持有独立于设备身份的 owner credential**（首启生成、展示一次、可轮换），不能是「首连者」这种时序性身份；
**（b）管理 API 鉴权形态未定，现状惯例是灾难**。桥上现有 HTTP 面的鉴权惯例：token 进 URL query（/cloud）或全局共享 Bearer（/view/ results :185 用 CLOUD_TOKEN）。管理 API 若沿用任一：query 惯例=注册码/token 进日志；CLOUD_TOKEN 惯例=**22 台设备+所有手机+（PUBLIC_TOKEN 桥上）任何人是管理员**——踢设备这个动作本身可以被被踢者调用（「吊销该设备密钥」的 API 被持 token 者拿来吊销别人的）。必须独立 admin token + Bearer header + 独立限流 + 操作审计；
**（c）管理页 XSS=全租户沦陷，而资产面明确无 CSP**。worker.ts:37-39 注释自证：严格 CSP「故意不上」因为 web-console 是内联脚本单文件应用——桥主面 v1 就要落在同一资产面上。设备名/meta 是攻击者可控字符串（sanitizePeerMeta 只裁长度到 120 字符，内容任意，cloud-client.ts:58-76），恶意成员注册一个 `<img src=x onerror=…>` 名字的设备，桥主打开设备列表即中招 → 管理页会话里拿着 admin token → 发码/踢设备/读互信表全链路可用。缓解：桥主面独立路由+严格 CSP（管理页是新写的，没有历史包袱，可以按 nonce-CSP 起步）+ 设备名/meta 在管理页按纯文本渲染的强制断言。

## 三、P1（进 v0.2 设计，T1 施工前定稿）

### P1-4 踢设备的生效性：四个各自独立的缺口（验收 8 断言不足）

验收 8 只断言「被踢设备后续帧全拒」。逐面推演：
1. **活连接**：踢出是否立即 close 该 dev 的现存 wss/长轮询会话？DO 侧需主动遍历 close（现状只有顶替语义会踢旧连接 :509-516，没有管理性踢线）。不踢活线=「后续帧全拒」仅指新帧，已建立连接上的帧若无每帧租户校验则照收；
2. **互信表残留**：踢出只动桥侧 tenantOf/吊销名单；relay 侧 device_trust（§4.5 存储模型②）不动——**同钥重入**：被踢设备稍后用正常流程重新入租户（新注册码、同 keypair 同 dev），relay 的 device_trust 里旧条目还在 → first-contact 人闸不再弹（「首次收到陌生 dev」不成立）→ 注入权即刻恢复。踢出必须联动：桥侧踢出时向租户内 relay 广播吊销帧、relay 清 device_trust 对应条目（这需要一条桥→relay 的下行控制帧，PRD 未设计；「桥侧映射不复制到 relay」纪律下这是唯一的联动通道，属必要例外，需明确写进协议）；
3. **全局 token 不随踢失效**：B1 已裁 L2 层 CLOUD_TOKEN 是全员共享（import-push 条目自带 token，B1 引 session-manager.ts:182）。被踢设备手里的 token 依然有效 → 以新随机 ph-/wb- keypair 重连（wb-/ph-/wt- 无持钥证明，worker.ts:24 注释自证「顶替 DoS 面为协议固有」）——它作为 null-tenant 设备能干什么取决于 P1-5 的 null-tenant 语义：若宽松即踢出旁路，若严格则至少保留容量占用/枚举面。**租户模型不接管 token 层，踢出就永远有后门**；v0.2 至少要声明：踢出后该设备的所有已发凭证（token 副本/密封旧帧）在新模型下均不可达数据面，token 层收口列入 T2 账号体系的前置义务；
4. **验收 8 改写**（见 §四）。

### P1-5 双轨窗口与验收 6/7 的正面冲突：null-tenant 语义未定义

验收 7「未入租户设备对桥内任何 dev 不可见不可达」 vs 验收 6「旧 relay 在网（未升级设备）全功能零影响」——**未升级 relay 就是最典型的未入租户设备**，两条不可同时成立，除非定义一个未定义的第三态。桥侧帧过滤矩阵必须显式给出（PRD 一格都没有）：

| 帧 | 发送方 null-tenant | 接收方 null-tenant | 建议语义 |
|---|---|---|---|
| 定向 {to,data} | → tenant 设备 | tenant → null | 双向 ROUTE_MISS（legacy zone 内互访除外，见下） |
| disc → RELAYS | 列表回？空？ | — | 空（不可探测）+ 预留 legacy zone |
| pair_req 广播（router.ts:134-142） | 全桥 rl- 转发？ | — | 只发同租户+legacy zone |
| relay-online（router.ts:66-72） | 全体连接广播 | — | **PRD 只列了 RELAYS 过滤（G6①），此帧漏在清单外**——跨租户 relay 存活性/dev id 元数据持续外泄 |

可选解法是 legacy zone（所有未入租户设备共享一个隐式域，互相全功能）：私有桥上它恰好=用户自己的存量设备（体验无损），共享桥上它=陌生人互见（§1-E 痛点对存量设备永久存活）。若走 legacy zone 必须写明：它是兼容性债务、有 sunset（T2 后关闭）、且**踢出设备永不落入 legacy zone**（吊销名单优先于 legacy 放行——否则被踢 relay 换个「未升级」身份回来）。
**22 台批量导入的数据源矛盾**：§4.5-G6③「已配对设备由桥主面批量导入租户」——桥上没有配对表（B1 已裁：配对在 relay 本地 cloud-peers.json，桥只见过瞬时在线者）。桥主面要么从当前在线 devs 抓（**离线设备漏导入**→严格模式下被锁在自己的 relay 外），要么新增「relay 上报关名单」通道（违反「桥侧映射不复制到 relay」的单向纪律？不——反向 relay→桥上报是允许的，但 PRD 没设计这条）。另需定义 cutover 时刻对**已建连接**的处理：DO 休眠唤醒 rehydrate（:609-617）不携带租户，存量连接全部是 null-tenant——严格模式当场断全部存量（可用性事故），宽松模式=legacy zone 开张。建议：T1 上线时 DO 主动 4000 全量踢线强制带租户重连（顶替语义现成，:509-516）。

### P1-6 relay 侧无法验证租户：连接层信任 100% 押在桥的过滤正确性上 + ph-/wb- 顶替同族

「桥侧映射不复制到 relay」纪律（对，防三账失真）意味着 relay 收到任何帧时无法独立判断发送方是否仍在租户内/是否被踢——它只能信「桥只把同租户帧路由给我」。两个后果：
1. 桥侧过滤矩阵（P1-5）任何一格写错/漏掉（relay-online 就是活例），relay 侧零防御纵深。建议 relay 侧加一条**廉价锚**：密封帧解封后明文体里的 tenant 字段与自身 tenant 比对（cloud-identity 单值即可，无需建表）——非权威，但把桥侧配置错误从静默泄密变成可告警的协议错；
2. **租户绑定对 ph-/wb-/wt- 无持钥证明**：rl- 注册有 dev↔rk 派生校验（worker.ts:349-355），wb-/ph-/wt- 没有（固有顶替面）。若 tenantOf 绑定只按 dev 字符串，攻击者可先冒名注册受害手机的 dev 再输码入租户——把受害者身份种进租户。绑定动作必须要求**全部设备类**的 dev=公钥派生值（enrollment 时交 rk，桥验派生），把 #29 的 rl- 修复推广到租户面。G6④「LAN 直连同权」在同一定义下有洞：LAN 直连不经桥=发送方租户资格未经桥过滤=relay 又验不了——LAN 直连的信任源必须仍是 per-relay 显式互信（device_trust），不能「信任来自租户凭证」，此句建议删改。

### P1-7 投影泄密面：租户内 SNAPSHOT 对全成员可见，无 per-device/per-project 收口

即使按 P0-1 做了档位制，T-proj 档本身也要回答：成员设备能看到租户内**全部** relay 的全部会话日志/待决卡/任务板/通知（SNAPSHOT 载荷清单见 P0-1 引证），还是只有被授权的项目/设备？PRD 的团队叙事（§1-E 开源用户/团队）下，「为某个项目入队的承包商」能读全组所有机器的会话日志——这在多数团队是不可接受的默认。v0.2 至少声明默认最小投影（会话列表元数据级）+ 逐级显式放开；boards/org_confirms 含任务内容与治理卡，默认应划出 T-proj 第一档。

## 四、P2（随批修）

### P2-8 DO storage 面的滥用与韧性
多用途注册码（若 P0-2 未按一码一设备收口）→ 灌 MAX_DEVS=400（worker.ts:366）垃圾设备占满容量门禁 → 合法设备 429（容量 DoS）；enrollment/admin 操作审计未定义（桥主面是全租户最高权力面，操作必须全量入账：发码/踢出/吊销/导出）；DO storage 是全部租户路由的根，「桥主导出备份」为手工兜底——建议入库定期快照 + 丢失恢复流程写明「恢复后首连不再即桥主」（owner credential 随快照保存）。

### P2-9 pair_req 广播的存量窗口与元数据骚扰
T1 上线前 pair_req 广播全桥 rl- 可见（router.ts:134-142）：私有桥低危（单租户），共享桥上=持续向全体租户 relay 投放爆破计数消耗（每台 relay 都为陌生码烧 per-dev fail budget 与全局预算，cloud-client.ts:684-696）+ sighting 表项污染；T1 后此面收进 P1-5 过滤矩阵。relayed 帧不解析（桥纪律）意味着过滤只能按**发送方**租户做——G6 设计正确利用了这一点，但要把「按发送方过滤」写成 normative（按接收方过滤需要解析 data.t，违反桥透明纪律）。

## 五、验收 7-9 改写建议

- **验收 7（改）**：未入租户设备：disc 得空列表、定向帧双向 ROUTE_MISS、pair_req 不达任何租户 relay、relay-online 不可见——四断言分开写（现在一句「不可见不可达」测不出 relay-online 漏网）；并增「legacy zone 语义」验证（若有）。
- **验收 8（改）**：踢出后五断言——①活连接 ≤Ns 内被 close；②新连注册被拒（含换 keypair 重试）；③定向/xmsg/pair_req 全拒；④租户内 relay 的 device_trust 同步清空（**同钥重入弹 first-contact 卡**为通过标准）；⑤被踢设备以旧 token 重连仅得 null-tenant 语义（不达任何租户设备）。
- **验收 9（改）**：在现有两条后追加——③自动互联后、T-proj/T-control 未授予前：成员设备发 `COMMAND_EXT_INPUT`/`COMMAND_ORG_CONFIRM` 被拒+审计（**P0-1 的回归锚**）；④SNAPSHOT 对未授 T-proj 的成员不发送（泄密面回归锚）。
- 新增**验收 10（桥主面）**：无 owner credential 的请求对全部管理 API 401；设备名含 HTML 字符在管理页纯文本渲染（XSS 锚）。

## 六、给 PM 的一句话立场

租户模型方向（协议一等公民/桥侧权威/分层红线）三条都对，但 v0.2 把三件大事写成了三句话：注册码该有一节规范、成员权力该有一张档位表、桥主面该有一套鉴权设计——补齐这三处（P0-1 档位制 / P0-2 凭证规范 / P0-3 owner credential+管理面 CSP），T1 可以立项；不补，T1 上线的每一天都是「一个注册码=整个租户」的状态。
