# 通知域 IA 分析：通知中心还是行动中枢

结论先行：推荐 **B+ 折中**——通知域不复制完整工作台；允许可判定的轻动作内联完成，但所有写入仍调用来源域的唯一命令入口。验收回填、确认收单、失联接替和编制确认均跳回原域处理。

## 1. 两案对比

### A：通知域内嵌处理工作台（现状）

1. **摩擦最低**：点击「需你行动」即可看到证据并完成高频动作，符合 Command Bridge 的行动队列气质，也适合手机收件箱直达处理。
2. **上下文集中**：通知卡、状态、动作和反馈在同一主区，用户不必先理解来源域的导航结构。
3. **实现与审计代价高**：验收、接替、编制等流程要在通知域复制表单、状态机和权限校验；若通知域形成第二写面，极易出现状态同步、返回栈、审计归属不一致。

### B：通知只做卡片，点击跳原域

1. **写面唯一**：会话/团队是实体状态唯一拥有者，项目保持只读聚合；动作、权限、审计和事件回放天然复用原域。
2. **实现稳定**：通知只负责 alert 展示、计数和 `sourceContext`，不复制验收工作台、任务板或接替流程，跨端行为更一致。
3. **操作摩擦增加**：高频轻动作多一次跳转；手机需要记住通知来源并正确返回，若上下文定位不准会让用户觉得“通知只是中转站”。

## 2. 推荐案与判定规则

采用 **B+**：通知卡可以提供一个轻动作按钮，但按钮只是来源域命令的快捷入口，不在通知域维护第二份实体状态；成功后更新 alert 状态并保留“已处理 / 查看来源”的结果。

判定规则固定如下：

- **轻动作**：单一、幂等、无表单/证据/分支、一次点击即可完成，且失败可安全重试。例如标记已读、暂停提醒、确认已知。
- **重流程**：涉及证据填写、成员/引擎选择、确认卡、多个实体变更、不可逆操作，或需要审计说明/二次确认。重流程一律跳来源域。

因此「验收回填/确认收单」是重流程；「失联接替」是重流程；「编制确认」是重流程。通知卡可展示摘要和主动作，但主动作文案应为「去会话验收」「去团队接替」「去团队确认」，而不是在通知域内直接提交完整表单。

## 3. 验收工作台归属与入口

- **归属**：验收工作台归会话或团队原始域；项目域只读聚合，不产生验收第二写面；通知域只持有 alert 与来源上下文。
- **桌面路径**：域栏铃铛 →「0.6.0-test.19 就绪待收单」→ 打开来源会话 `0.6.0-test.19 出包`，自动定位「验收单/任务」段签；若验收由团队任务发起，则定位团队看板对应任务。完成后按来源返回通知工作台，保留已处理结果。
- **手机路径**：root 顶栏铃铛 → 通知卡 → 来源详情全屏页，隐藏底栏并定位验收段签；完成或返回均回通知中心，不回默认会话首页。项目入口先显示聚合卡，再跳会话/团队原域。
- `sourceContext` 至少携带 `domain / entityId / segment / alertId / returnPath`，保证跨域跳转、历史恢复和审计关联不依赖标题匹配。
