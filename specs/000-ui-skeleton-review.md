# cc-deck UI 骨架方案评审报告

评审日期：2026-10-03  
评审范围：`docs/v8-ui-mockup.html`、`docs/v8-ui-interactive-v2.html`、`web-console/index.html`、`expo-app/App.tsx` 及其当前列表/详情相关组件。

## a. 方案审查结论

### 总结

**方向可行，但当前方案不能原样进入实施。** 桌面 rail 与手机 root 底部导航的分层思路是合理的，主要阻塞不是视觉或交互原则，而是两份设计稿对手机一级导航的口径不一致：

- `v8-ui-mockup.html` 基础稿在手机导航注释中定义为三 Tab：会话 / 团队 / 设置。
- 同一文件的 V8 增量段又把项目升为第四 Tab；`v8-ui-interactive-v2.html` 实际可点击流也采用四 Tab：会话 / 团队 / 项目 / 设置。
- 桌面 rail 已同时包含会话、团队、项目、通知、设置；其中通知是行动入口，不是内容域。

因此建议本次先**原则性通过“桌面全局 rail + 手机 root 底栏、详情页隐藏底栏”**，但把“手机到底三 Tab 还是四 Tab”列为实施前必拍板项。未拍板前不应开始 UI 细化或改造。

### 信息架构合理性

1. **全局导航与局部视图分层正确。** rail/底栏负责在会话、团队、项目、设置等一级域之间移动；详情页内的消息、任务、输出物、统计等 Tab 负责同一实体的局部视图。两层职责清楚，避免把“域切换”和“详情视图”混成一排 Tab。
2. **桌面 rail 的密度适合长期驻留。** 56px 纯图标栏、顶部连接绿点、通知角标和选中品牌色，适合桌面宽屏，也能把原来挤在会话侧栏顶部的连接状态抽成稳定入口。
3. **通知放在 rail/顶栏而非一级内容 Tab 是合理的。** 通知是跨域行动队列，不应与会话、团队、项目并列为内容域；“未读 alert 数”角标也比泛未读数更符合行动导向。
4. **手机详情页隐藏底栏是合理的默认值。** 详情页已经有返回、标题和内部视图切换，继续保留底栏会压缩对话/看板/输入区域，也容易让用户误以为切换 root 会丢失上下文。返回键、系统返回和边缘返回手势应承担退出详情职责。

### 与现有功能模块的映射缺口

- **会话域：** 桌面现有 `#side + #detail` 已覆盖会话列表和详情；移动端 `App.tsx` 也是列表/详情两级状态机，映射最完整。
- **团队域：** 团队相关能力已经存在于网页的组织区/团队内容与移动端 `ListScreen` 的组织区、项目组详情弹窗，但目前不是独立一级 root；需要把现有入口收拢成稳定的团队 root，而不是再造一套数据面。
- **项目域：** 设计稿把项目定义为目录聚合、只读总览、联动回原域；现有移动端已有项目组/组织详情能力，但还没有设计稿中的项目 root 与项目详情导航地图。这里存在“项目组”和“项目域”概念边界不清的缺口。
- **设置域：** 网页已有 `gearPop` 的独立设置 rail，移动端已有 `SettingsDrawer`；若再增加手机设置 root，需要明确是把抽屉升级为页面，还是保留抽屉作为快捷入口，避免两套设置入口并存。
- **通知域：** 交互原型已有桌面通知浮层、手机通知二级页和统一 badge 语义；现有实现主要是任务完成浮层、确认浮层、连接状态入口，尚未形成同一套跨端通知中心与未读计数模型。

## b. 合并难点清单

### 1. 桌面布局改造范围

- 当前网页主壳是 `main > #side + #detail`，已有顶栏、可拖拽会话列宽、浮动新建/设置按钮；rail 需要成为 `#side` 之前的固定第三列，而不是简单把一个图标栏塞进会话列。
- rail 引入后要重新计算侧栏宽度、拖拽边界、空态、浮层锚点、任务完成卡和确认卡的位置；原有“相对侧栏左下角”的 FAB 不能继续直接复用旧坐标。
- 当前 `gearPop` 自身已有一套设置 rail。新增全局 rail 后必须区分“全局域 rail”和“设置页内导航 rail”的层级、宽度、选中态和键盘焦点，避免视觉与 DOM 命名冲突。
- 小宽度网页/窗口的响应式规则要单独定：是隐藏全局 rail、压缩为窄栏，还是转成横向域切换；不能让 56px rail、会话列表和详情区同时被挤到不可用。

### 2. 路由与视图切换改造

- 当前网页主要依靠 `selected`、`activeTab` 和 DOM 显隐切换；新增一级域后需要增加 domain 状态，并处理 rail 切域时会话选择、详情打开态、设置页子页、通知浮层的保留/清理规则。
- 需要定义浏览器历史、刷新、深链接和返回键语义。建议至少能区分“域切换”“进入详情”“详情内 Tab 切换”三种历史层级，否则浏览器后退会出现跨域跳转或回到错误会话。
- 移动端当前 `Shell` 只在 `detail` 与列表之间切换；底栏需要引入 root 导航状态、二级页栈和跨 root 的返回规则，同时保留现有详情横向六视图分页、悬浮卡和设置/扫码流程。
- 交互原型的 `PH_ROOT`/`PH_ROOT_OF` 已说明 root 与二级页应分离；实际实现也应采用同样的显式状态机，不建议用多个布尔值拼接导航状态。

### 3. 手机详情页是否加导航

- 设计稿明确“详情页不加底栏”，这是合理选择，但必须同步定义：详情内不能直接点击底栏切 root；若需要跨域跳转，应由详情中的明确联动入口触发。
- 现有详情已有返回按钮、硬件返回统一分发和入场/退场动画；新增导航后要保证动画期间不会误切 root，也不能让系统返回被空消费。
- 详情页从通知、验收单、项目聚合跳入时，需要保留来源栈；返回应优先回来源页，而不是无条件回会话 root。

### 4. 桌面 rail 与顶部 Tab 的取舍

- **不建议用 rail 替换详情顶部 Tab。** rail 应只承载一级域；现有详情中的对话/任务/全部/输出物/定时/统计仍是二级视图，移动端也应保持同一语义。
- 网页当前“顶部 Tab 布局”的问题不是 Tab 本身，而是缺少一级域壳。应先加全局 rail，再把团队/项目等现有内容挂入域视图；不要把所有现有 Tab 平移到 rail，造成行为和快捷键回归。
- 桌面会话列表仍应保留在会话域内；团队域、项目域、设置域需要各自定义左侧列表或内容区，不应复用同一侧栏而只改标题。

### 5. 三 Tab/四 Tab 与数据模型一致性

- 如果项目是正式一级域，手机三 Tab 就无法与桌面 rail 和交互原型对齐；如果项目只是聚合入口，四 Tab 又会增加一级导航负担。
- 项目详情的“只读聚合、联动不合并”原则要落到实现上，否则会出现同一会话/团队在会话域、团队域、项目域各有一份可写入口，造成状态冲突。
- badge 需统一定义：团队 badge 是待装机/待确认，通知 badge 只数需行动 alert，不能把任务完成、普通动态和系统提示混在同一个数字里。

### 6. 设置、通知与连接状态的入口冲突

- 当前网页连接状态在会话列头，设置通过底部齿轮打开；当前移动端连接 chip、设置抽屉、扫码/服务器编辑也已形成完整路径。迁移到 rail/底栏后，必须决定哪些是一级入口、哪些是快捷浮层。
- 设计稿把连接绿点作为 rail 顶部快览入口，把设置作为独立域；这比把“连接”藏在设置里更清楚，但需要确保异常状态、配对、编辑服务器等动作仍能落到正确的设置子页。
- 通知中心应与现有任务完成浮层、确认浮层、验收单待填卡建立来源关系；否则同一事件会在多个位置重复提醒，且 badge 无法可靠清零。

### 7. 跨端与可用性风险

- 底栏需要处理安全区、键盘弹出、横屏/折叠屏、详情输入栏和悬浮卡避让；56px 固定高度不能直接照搬到所有设备。
- 图标 rail/底栏必须有可访问名称、焦点态和非颜色提示；通知数字、连接绿点和品牌橙不能成为唯一状态表达。
- 域切换涉及较大面积重渲染，需避免会话流、看板滚动位置、输入草稿和连接快照在切换时丢失。

## c. 需要用户拍板的分歧点

1. **手机一级导航是三 Tab 还是四 Tab？**  
   建议：若“项目”已经确认是长期一级域，采用四 Tab并同步修正文档；若本单只补 v7.1 骨架，采用三 Tab，项目暂不进入手机一级导航。
2. **项目是否属于一级内容域，还是团队/会话的只读聚合入口？**  
   建议：保留项目域，但严格只读聚合、写操作回原域；只有在数据和入口已准备好时才进入手机底栏。
3. **桌面 rail 是否完全替代现有全局入口，详情 Tab 是否保留？**  
   建议：rail 替代全局域入口；详情 Tab 原样保留，不做跨层合并。
4. **通知是否作为独立一级页面，还是仅保留浮层/顶栏入口？**  
   建议：不占底栏/主域名额；桌面用 rail 铃铛弹面板，手机从 root 顶栏铃铛进入通知二级页，统一 alert badge。
5. **手机设置是 root 页面还是继续使用抽屉？**  
   建议：设置作为 root 页面；连接、模型服务等使用二级页。现有设置抽屉可在过渡期保留快捷入口，但不能与 root 形成两套并列导航。
6. **详情页隐藏底栏后，跨域跳转与返回从哪里恢复？**  
   建议：详情页只保留返回和内容内联动；记录来源栈，返回来源页；系统返回优先关闭浮层/详情，再退出应用。
7. **启动默认域和域切换是否写入 URL/历史？**  
   建议：默认进入会话；桌面网页将域/详情/子 Tab 纳入可恢复的 URL 或 history state，移动端保存最近 root 但不强制持久化详情。
8. **团队角标和通知角标的计数口径是否冻结？**  
   建议：通知只计“需要用户行动”的 alert；团队只计待用户确认/待装机事项；普通动态、任务完成汇报不进入一级 badge。

## d. 方案通过后的 UI 细化设计任务拆解建议

### 第 0 步：冻结 IA 与状态矩阵

- 交付：三/四 Tab 决议、桌面 rail 项目清单、域/详情/子 Tab 路由表、badge 口径、返回栈规则。
- 验收：每个入口只有一个主归属；项目是否可写、通知是否独立、设置是否页面化均有明确答案。

### 第 1 步：桌面骨架接入，不改业务内容

- 交付：全局 56px rail、连接绿点、选中态、铃铛角标、基础响应式壳；现有会话列表和详情内容先原位接入。
- 验收：会话选择、详情 Tab、输入框、拖拽列宽、现有浮层位置和键盘快捷键无回归。

### 第 2 步：桌面域切换与路由状态

- 交付：会话/团队/项目/设置/通知的域状态机，域内默认视图，浏览器 history/deep-link/back 规则，连接快览入口。
- 验收：切域不丢会话草稿与滚动状态；项目聚合跳回原域；通知打开/关闭和 badge 清零一致。

### 第 3 步：手机 root 壳与底栏

- 交付：Safe Area 适配的底栏、选中态、badge、root 页面切换、最近 root 恢复；按第 0 步决定落三 Tab或四 Tab。
- 验收：会话、团队、项目（如通过）、设置四类 root 均可进入，现有列表/组织区/设置功能有唯一入口。

### 第 4 步：手机详情与二级页栈

- 交付：详情页隐藏底栏、返回/系统返回/边缘手势、来源栈、通知/验收单/项目详情等二级页模板。
- 验收：详情横向六视图保持；从不同 root 跳入后能回正确来源；键盘、输入栏、悬浮卡不被底栏或安全区遮挡。

### 第 5 步：跨端模块映射与视觉收口

- 交付：团队域、项目只读聚合、通知中心、设置页面化、连接绿点/顶栏铃铛的统一视觉 token 和空态/错误态。
- 验收：同一事件在桌面与手机的状态、角标、文案和动作一致；不存在重复可写入口。

### 第 6 步：交互与回归验收包

- 交付：桌面宽屏/窄窗、手机小屏/大屏/横屏、深浅色、键盘与系统返回、断线重连、深链接和无障碍检查清单。
- 验收：按“域切换 → 进入详情 → 触发通知/验收 → 返回 → 刷新/重连”主路径逐项验收，并记录未决项。

## 评审结论（供拍板）

**有条件通过。** rail + root 底栏 + 详情隐藏底栏的导航分层没有根本性问题；当前必须先解决设计稿内部的三 Tab/四 Tab冲突，并冻结项目域、通知入口、设置页面化和返回栈四项规则。用户拍板前，本报告不建议进入 UI 细化或代码实施。
