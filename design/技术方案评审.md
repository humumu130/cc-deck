# Cloud Code Relay 技术方案评审

> 对照《Cloud Code Relay 产品设计方案》第 8/9/10 章，结合集成机制调研与两种使用场景（家中同局域网 / 公司跨网络）的评审结论。
> 评审日期：2026-08-23

## 0. 结论摘要（TL;DR）

| 评审项 | 结论 |
|---|---|
| 产品可行性 | ✅ 成立，Agent SDK 能力完整覆盖需求（多会话/流式输入/异步授权/中断/事件流） |
| 与官方 Remote Control 的关系 | 官方方案**不适用本环境**（智谱 API 自定义 base URL 被官方远程控制排除），自建无冲突 |
| 传输架构 | 双通道：家中 LAN 直连 WebSocket + 公司经自建云桥（出站 WSS）；蓝牙仅作近场补充，MVP 后置 |
| 手表连接 | 手表只连手机（Wear Data Layer），手机做网关，两场景行为统一 |
| 事件模型 | 产品文档 11 种事件方向正确，需补充 `seq` 序号、超时策略与心跳事件（见 §5） |
| MVP 切分 | 产品文档 MVP 范围合理，建议将云桥从 MVP 中拆出为 1.5 阶段（先 LAN 直连跑通全链路） |

## 1. 为什么自建（官方方案不可用的确认）

官方 Remote Control（research preview）允许手机 Claude app 远程操控本地会话，但有硬性前提：

- 需要 claude.ai 订阅 + **api.anthropic.com 直连**；
- 自定义 `ANTHROPIC_BASE_URL`（本环境接入智谱 GLM API）、Bedrock/网关均被禁用。

**本环境 Claude Code 接入的是智谱 API，官方远程控制根本不可用。** 因此：

1. 自建 Relay 不是"重复造轮子"，而是本环境下获得移动控制的唯一途径；
2. Agent SDK 驱动的是同一个 Claude Code CLI 子进程并继承环境变量——当前用智谱 API 正常运行的会话，Relay 拉起后同样走智谱，模型后端对集成层透明；
3. 风险极低，但 MVP 第一天需 spike 验证：Agent SDK spawn 的子进程正确继承 `ANTHROPIC_BASE_URL` / `ANTHROPIC_AUTH_TOKEN`。

## 2. 两种使用场景与总体拓扑

### 场景与通道

| | 家中 | 公司 |
|---|---|---|
| 网络 | 手机/手表与 PC 同局域网 | 手机与 PC 不同网络（跨网） |
| 通道 | **LAN 直连** `ws://<pc-ip>:<port>` | **云桥中继**：PC Relay 主动发起出站 WSS，手机连同一云桥 |
| 蓝牙 | 可选近场补充 | 可选近场补充（仅工位 ~10m 内） |

**关键判断：蓝牙不能作为公司场景的主通道。** 经典 BT/BLE 室内有效距离约 5–15 米，而产品核心价值是"人离开电脑时收通知、做确认"——离开工位那一刻蓝牙链路即断。公司场景必须有走网络的中继通道，蓝牙定位为"隐私优先的近场补充"，MVP 后置。

### 总体拓扑（已确认决策）

```
⌚ Wear OS 手表
   └─(Wear Data Layer：BT 近场 / WiFi 远场，系统托管漫游)
      📱 Android 手机（网关）
         ├─ 家中: LAN 直连 WebSocket ──────────────┐
         ├─ 公司: WSS 出站 ──> ☁ 云桥 <── WSS 出站 ─┤
         └─[可选补充: 近场蓝牙 RFCOMM]               ▼
                                              💻 PC Relay
                                                 ├─ Session Manager（Agent SDK 多会话）
                                                 ├─ Event Stream（结构化摘要）
                                                 ├─ Command Queue
                                                 └─ 鉴权 / 断线重连 / 事件缓存
```

- **手表只连手机**（已确认）：鉴权、配对、网络漫游全部交给系统 Data Layer 处理，两个场景行为完全一致；手表端不实现 WebSocket 客户端。
- **手机是唯一需要管理连接复杂度的端**：多通道自适应（LAN 可达则直连，否则走云桥）。

### 云桥设计要点

- 形态：极轻量转发服务（按设备/频道路由密文信封），无业务逻辑；部署形态灵活——自托管 Docker / VPS / Cloudflare Workers 均可，MVP 先提供 Docker 单文件部署。
- 防火墙友好：PC 侧只发起**出站** WSS（通常走 443），无需开入站端口、无需装 VPN 客户端；需支持 `HTTP_PROXY` 出站代理。
- 端到端加密：配对时通过二维码交换公钥（libsodium box），云桥只见密文信封（`{to, seq, ciphertext}`），桥被攻破不泄露内容。
- 配对流程：PC Relay 显示二维码（含 LAN 地址 + 云桥地址 + 一次性配对码）→ 手机扫码建立信任。

### 断线重连与可靠性

- 所有事件带**单调递增 `seq`**，Relay 维护环形缓冲（建议保留最近 500 条/会话）；
- 客户端重连时携带 `last_seq` 请求补发，避免事件丢失；
- 命令带 `command_id` + 客户端去重，保证 at-least-once 语义；
- 心跳：`PING/PONG` + 会话级 `HEARTBEAT` 事件（驱动 WORKING 状态的呼吸环动画与运行时长）。

## 3. PC Relay 技术选型

| 项 | 选型 | 依据 |
|---|---|---|
| 语言/运行时 | Node.js + TypeScript | Agent SDK 一等公民；`@anthropic-ai/claude-agent-sdk-win32-x64` 官方支持 Windows 11 |
| 会话驱动 | Agent SDK `query()` streaming input 模式 | 每次调用独立 spawn 子进程，单进程管理多会话；支持中途 yield 追加用户消息（语音指令场景） |
| 授权拦截 | `canUseTool` 回调 | 官方文档明确回调**可无限期挂起**——天然匹配"手表 30 秒后 Allow"的跨设备确认；注意 `bypassPermissions`/allow 规则自动放行的调用不进回调 |
| 中断/停止 | `Query.interrupt()` | 仅 streaming 模式可用，与选型一致 |
| 桥接 CLI 内部会话 | hooks（`Notification`/`Stop`/`PreToolUse` 等） | 用户自开的交互式 CLI 会话可通过 hooks **单向**通知 Relay；**外部无法控制已有 CLI 会话**（文档无此机制）——MVP 明确只管理 Relay 自己拉起的会话，hooks 集成列为 1.5 阶段增强 |
| WebSocket 服务 | `ws` 库 | 成熟、无依赖负担 |
| 进程模型 | 单 Node 进程（Session Manager + WS Server + 云桥客户端） | MVP 无需拆分 |

### 状态与指标的推导

- **WORKING / WAITING / ERROR / DONE**：由消息流推导——`assistant`/`tool_use`/`tool_progress` → WORKING；`canUseTool` 挂起 → WAITING；`permission_denied` / 非零退出 / `StopFailure` → ERROR；`result`（含 `terminal_reason`）→ DONE。
- **文件变更与增删行数**：`Edit`/`Write` 工具输出自带 `structuredPatch`/`gitDiff`（additions/deletions），直接聚合，无需自己解析 diff。
- **当前动作摘要**（"修改 src/auth.ts"）：最近一次 `tool_use` 的工具名 + 关键参数压缩。

## 4. 移动端选型

### 手机（Android）

| 项 | 选型 | 说明 |
|---|---|---|
| 语言/UI | Kotlin + Jetpack Compose | 单 Activity + Compose Navigation，四 Tab 对应产品设计 §5.1 |
| 网络 | OkHttp WebSocket（自实现客户端） | 需要多通道切换逻辑，不用系统托管 |
| 常驻 | 前台服务（Foreground Service）+ 数据层通知渠道 | 维持 WS 连接；WAITING 事件触发高优先级通知 |
| 数据 | Room 缓存会话/事件快照 | 断线时 UI 仍有内容，符合"本地状态缓存"要求 |
| 语音 | Android `SpeechRecognizer` | 转写文本经 `COMMAND_MESSAGE` 下发，MVP 不做端侧语义处理 |
| 手表桥接 | Wear Data Layer `MessageClient` / `DataClient` | 手机做网关：手表订阅状态摘要、上行确认与语音文本 |

### 手表（Wear OS）

| 项 | 选型 | 说明 |
|---|---|---|
| UI | Compose for Wear OS | 圆形表盘适配：`ScalingLazyColumn`（时间线上下滑动）、边缘弧形元素、大字号状态色 |
| 手势映射 | 水平 pager = Session Deck；垂直滚动 = 时间线；长按 = 语音/会话总览 | 与产品设计 §4.1 三条规则一致 |
| 表冠/旋钮 | `RotaryInputEvent` → 时间线滚动优先 | 有旋钮设备映射滚动而非切会话（精确操作给滚动） |
| 状态环 | WORKING 呼吸环用 `Animatable` 循环动画 | OLED 黑底 + 蓝紫品牌色 + 四态色，符合附录视觉决策 |
| Tiles/表盘复杂功能 | 1.5 阶段 | 不开 App 抬腕可见状态，价值高但依赖 Data Layer 同步链路稳定 |
| 语音 | Wear `SpeechRecognizer`（`RecognizerIntent`） | 手表端长按进 Voice Mode；注意部分表盘需兼容无麦克风设备（降级为仅确认/切换） |

### Data Layer 消息约定（手机 ↔ 手表）

- 下行：`/session_state`（当前会话摘要 JSON，<4KB）、`/waiting_request`（确认请求）、`/session_list`（总览）；
- 上行：`/decision`（Allow/Reject + request_id）、`/voice_text`（语音转写文本）、`/switch_session`；
- 摘要事件体积极小，MessageClient 足够；不把日志流发往手表（与产品设计 §9.1 一致）。

## 5. 事件模型修订

产品文档 §9.1 的 11 种事件方向正确，修订如下：

```
信封（所有事件/命令外层）:
{ seq: number, session_id: string, ts: number, type: string, payload: object }

会话事件（Relay → 客户端）:
  SESSION_CREATED   新会话（cwd、初始指令、分支名）
  SESSION_UPDATED   状态/摘要/文件统计变化（节流：≥2s 或状态翻转时发）
  SESSION_HEARTBEAT 运行心跳（新增：驱动呼吸环与计时，每 5–10s）
  SESSION_WAITING   等待确认（含 request_id、工具名、参数摘要、超时策略）
  SESSION_ERROR     错误（含可读摘要，不含原始堆栈全量）
  SESSION_DONE      完成（terminal_reason、耗时、变更统计）
  SESSION_OUTPUT    有删减：MVP 仅存 Relay 本地供手机拉取，不主动推送

命令（客户端 → Relay，带 command_id，at-least-once + 幂等去重）:
  COMMAND_CONTINUE  继续/批准（对应 canUseTool resolve allow）
  COMMAND_REJECT    拒绝（新增独立类型，替代原 COMMAND_APPROVE 的双义）
  COMMAND_STOP      interrupt()
  COMMAND_RETRY     终止后以同上下文重启
  COMMAND_MESSAGE   追加用户消息（语音/文字）
```

新增两个必须设计的问题：

1. **WAITING 超时策略**：`canUseTool` 可无限挂起，但人长时间不响应会导致会话卡死。MVP 策略：不超时自动拒绝，手机/手表持续升级提醒（通知 → 震动 → 可选重复）；1.5 阶段加"用户可配置超时后自动 Reject"。
2. **输出摘要管线**：产品文档 §9.2 的压缩（`npm run build` 三行日志 → "✓ Build passed"）在 Relay 内实现为规则引擎（正则 + 已知工具模式），MVP 覆盖常见构建工具即可，不追求通用 NLP。

## 6. MVP 切分（修订）

### MVP（第一阶段）—— 全链路跑通，仅 LAN 直连

1. **PC Relay**（Node/TS）：Agent SDK 单会话管理、状态推导、事件信封 + seq、WS 服务、二维码配对、鉴权 token、环形缓冲补发；*spike：验证智谱 env 继承*
2. **手机端**：配对扫码、会话列表、Session 详情（活动/日志/统计，文件 Tab 1.5 阶段）、WAITING 通知 + Allow/Reject、语音转写下发、Room 缓存
3. **手表端**：Session Deck（左右滑）、当前会话卡片（四态）、WAITING 确认页、长按语音
4. Data Layer 桥接（手机网关）

> 把云桥从产品文档 MVP 中后移：LAN 直连先验证全部产品价值，云桥是纯传输层增量，不阻塞任何产品功能。

### 1.5 阶段

- 云桥部署（Docker）+ 手机多通道自动切换；多会话并发；文件 Tab（diff 摘要）；hooks 桥接用户自开的 CLI 会话（仅通知）；Tiles；WAITING 可配置超时

### 2/3 阶段

- 与产品文档 §10.2/10.3 一致（多电脑多 Agent、自定义命令、会话搜索标签、远程安全体系、多语言语音、任务编排）；近场蓝牙通道在此阶段再评估

## 7. 风险清单

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R1 | Agent SDK 子进程未按预期继承智谱 env | 低（几乎确定继承，但未实测） | MVP 第一天 spike 验证，失败则显式传 env |
| R2 | `canUseTool` 挂起期间设备全离线，会话无限卡住 | 中 | 明确超时策略（§5）；UI 显示"等待中，已通知设备" |
| R3 | 云桥部署对普通用户有门槛 | 中 | 提供单文件 Docker；1.5 阶段前不依赖云桥 |
| R4 | 公司出站走代理，直连 WSS 失败 | 中 | Relay/手机支持 `HTTP_PROXY`；443 端口 |
| R5 | Wear Data Layer 在 BT/WiFi 切换时消息延迟或丢失 | 中 | 消息带 seq + 客户端请求补发；关键决策（Allow/Reject）手机侧确认回执 |
| R6 | Windows 侧蓝牙栈在 Node 生态支持薄弱（若做近场通道） | 中 | 已后置到 2/3 阶段；届时可由独立 C#/Rust 辅助进程承担 |
| R7 | Node 子进程在 Windows 上的信号处理/清理差异 | 低 | 统一用 SDK 的中断 API + 退出钩子清理 |
| R8 | 手表无麦克风/语音不可用的机型 | 低 | 降级为仅状态+确认，UI 隐藏语音入口 |

## 8. 待定问题（实现前需确认）

1. 会话由谁发起：MVP 是否需要手机端"新建会话"（发初始指令给 Relay spawn），还是只接管 PC 上已启动的会话？→ 建议前者（hooks 单向限制决定了接管不可行，见 §3）
2. 通知渠道细节：手机通知是否需要区分"需要行动"（WAITING）与"仅告知"（DONE）的渠道与优先级？→ 建议区分
3. 云桥的设备身份模型：一台 PC 多台手机/手表？多台 PC 一台手机？→ MVP 按"单 PC + 单手机 + 配对手表"，多设备 2 阶段
