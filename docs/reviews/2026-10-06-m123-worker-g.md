## 三、重投段链口径备案（运行时零段号，两面对齐）

**payload**：`COMMAND_DISPATCH { …, redispatch_of: "<原单dispatch_id>" }`。

**规则**（dispatchWorker 内，:4742 区）：
1. **root 归位**：`redispatch_of.trim().replace(/#r\d+$/, "")`——段 id 尾剥掉归位 root（导入器 import-dispatch-lesson 同款正则口径）
2. **三重校验**：root 空→error「redispatch_of 必填原单 dispatch_id」；原单不存在→error「重投原单不存在: <id 前 8 位>（核对台账 id）」；原单在途（status 非 done/failed）→error「原单 <id> 仍在途（<status>），不可重投（等终态或先停单）」——**在途拒收防双跑同活**
3. **同 id 追加行**：新行沿用原单 root id（不生成新 UUID）——读侧 readDispatchLog 同 id 去重留最后（收敛视图末行赢）=重投后即见 running
4. **导入侧自动出段**：import-dispatch-lesson 按行序终态切分（终态行后再现行=重投事件）→`<id>#r<N>` 段、attempt_no+1、parent_dispatch_id 指前段——**运行时零段号零新字段，段链由导入器推导**（两面对齐，导入器零改，40/40 回归绿即证）

**既有 duplicate-id 预检不冲突**：FIX-B 的 dispatchProcessed 是**存储导入侧**防重，运行时台账是 append-only 同 id 多行=段链语义，两面对齐不冲突。

**ACK**：重投成功链 data 与首战同形（dispatch_id=原单 root id、session_id=新会话）——C9① 断言 dispatch_id≡rootId。

**透传链**：payload.redispatch_of → orgAction("dispatch") case 透传 + M12-2 编排链/M12-1 直派两处 orgAction 调用条件透传（trim 空不给）——三路径（直派/认领/编排）均可重投。

## 五、漏出口修补清单（唯一修补）

**upsertNotification dispatch 域特化**（session-manager.ts :775 区）——测试探针抓到的真缺口：

- **缺陷**：原「同 stableKey 已在账即静默」防重与重投段链冲突——同一 root id 先 failed 后重投 done，done 终态被同 key 静默吞，通知账停在 failed，与台账收敛 done 不一致（账面永挂失败态）。
- **修法**：`kind === "dispatch"` 时已存在不静默，改为**刷新终态字段**（severity/group/title/body/actionable/sourceContext.sessionId）；`created_at` 与生命周期字段（已决议时间）不动——已处置的卡只换内容不复活。其余 kind 维持静默防重（重复事件/重放不双发）零变化。
- **哲学**：dispatch 无 revision（stableKey 恒 `dispatch:${entityId}` 一单一行），重投多次终态是**状态推进**不是重复事件——账面收敛末态与台账收敛视图（readDispatchLog 末行赢）对齐。

其余 13 出口审计无新漏，零修补。
