# V2 系统设计独立评审（PM 盲评，2026-10-05）

## 0. 总裁定
- `v2-system-design.md` 的**目标方向成立**：SQLite 负责实体当前态，`events.ndjson` 负责广播/审计，消息真相仍在 transcript（§五 63-78、§八 240-247）。这是用户已拍板的新版架构，不再把 JSON 文件视为终局。
- 但本文仍是“V2 目标蓝图”，不是可直接照抄编码的现状规范：表设计按 2026-09-23 的 Leader/worker、三态板、Claude 单实现书写；m2 已有 PM 重角色、beads 四件、六引擎枚举、通知双账与产物 view join。
- 建议：**保留 V2 为目标上位架构，新增一份 schema/compatibility 对照作为实施闸门**；018 不废止，转为协议/三端/CLI 过渡实施线，SQLite M1 数据地基先于新增持久化业务。

## 2. 概念演化冲突
- **Leader → PM**：V2 §七/§九大量使用 Leader 作为业务编排者；083 已定 PM 重角色、Leader 变薄且可插拔（`specs/083-org-model-final.md:37-55,68-82`）。数据库必须存 `business_role`（`team_pm/global_leader/review_pm/worker`）与 `command_role`、`task_participation` 分离；历史 `actor:"leader"` 只做兼容读取映射。
- **下发流**：用户新建任务应先写 `task.create` 当前态，再由 relay 产生 dispatch envelope；当前 `upsertBoardEntry`/`dispatchWorker` 仍是 JSON 板+台账组合（`projects.ts:440-490`、`session-manager.ts:4404`），需统一事务边界。
- **回写流**：Agent 不能直接改 SQLite/JSON；以 per-session 凭证调用 `claim/submit/self-verdict/receipt`，relay 单写者更新 task/session/dispatch，再发增量事件。V2 §七 194-212 已有原则，但缺 m2 `orgAction` 单漏斗与现有 COMMAND 的 adapter 映射。
- **引擎/锚**：V2 “M1 仅 ClaudeCodeAdapter”（§一 8-15、§十 260-262）已过时；m2 `SessionEngine` 有六枚举（`relay/src/types.ts:25-35`），Registry 已注册 Trae/Qwen Code/CodeBuddy（`engine-registry.ts:36-72`），Codex 有独立 JSONL/preflight（`relay/src/agent-codex.ts:84-104`）。外部身份应统一为 `(engine, external_sid, external_kind)`，不能再把 Claude 作为 schema 主词。
- **值守/watchdog**：V2 双信号三色仍对（§九 249-256），但 019 已把 PM 值守、行动位门控、DUTY_RECEIPT、独立审计纳入设计；这些字段必须在 schema 对齐时一次纳入，否则 SQLite 首轮后继续改表。

## 3. 三级清单

### 保留（9）
- **K1** SQLite=current state、`events.ndjson`=audit/broadcast，mutation 先库后事件（V2 §五 63-67）。
- **K2** 消息不进 Message 表，transcript 是消息真相，历史走分页/分块（V2 §六 190、§八 240-246）。
- **K3** task 五态 + 用户收单闸口；`done` 不因 Agent 自报自动产生（V2 §六 123-137）。
- **K4** `acceptance_item` 活工作态与 `acceptance_result(sheet×item)` 历史判定分离（V2 §六 96-121）。
- **K5** 所有状态变更走 relay 命令面，单线程/单写者提供原子性，Agent 不能直写库（V2 §七 194-212）。
- **K6** artifact 文件本体留文件系统，数据库只做登记、归属与状态；路径安全与 72A0 修复资产应保留。
- **K7** watchdog 只信 relay 本地双信号，不信手机在线态；缺能力时显式降级（V2 §九 249-256）。
- **K8** forward-only 迁移、双读过渡、已知损失清单（V2 §五 74-78）；但双写不得成为长期事实源。
- **K9** Adapter 契约与 MCP 侧门分层，不把单一 Agent 特性塞进核心（V2 §一 8-15）。

### 优化（12）
- **R1 task 映射**：保留 `BoardEntry` 兼容读侧，SQLite `task` 成为唯一写面；beads 的 `depends_on` 迁成关系/索引，`gate` 迁成阻塞条件，`lessons` 独立 `lesson` 表并保 `source_dispatch_id`。
- **R2 状态模型**：五态是持久业务态；`blocked`、`修复中`、`等待用户`、`running` 都做派生/子状态，避免新增第二套终态机。
- **R3 验收迁移**：新建稳定 `item_id`；旧 rows 进入 snapshot-only 或 `task_id=NULL` 的迁移兼容行，严禁按自由文本猜关联。
- **R4 session**：`lifecycle_status`、`run_status`、`waiting_reason`、`external_sid` 分列；`runtime_state_json` 只收低频/易变兼容字段，常查字段建列。
- **R5 team_member**：增加不可变 member archive、`joined_at/retired_at`、heartbeat/business-log；current assignment 与历史成员分离，时间线 live-first/archive-fallback。
- **R6 notification**：结构化通知入 SQLite；`decision-notifications.json` 保留为投递/注入账，`notifications.json` 迁为兼容投影；condition key、dismissed、resolved 分列。
- **R7 artifact**：表键采用 `(source_id, normalized_path)`，同时挂 project/session/task；`delivery_group_key` 优先，文件存在性三态与安全证据入库。
- **R8 engine**：schema 增 `engine/provider/model/role/capabilities/preflight_state`；Claude/Codex 专用路径与 Registry 三类统一由 Adapter Registry 描述，ZCode 显式 unsupported。
- **R9 orgAction adapter**：保留现有单漏斗（`session-manager.ts:3945-4121`），新增 task/dispatch 命令通过 adapter 映射至既有 shape，ACK 返回 canonical entity ids，避免第二写入口。
- **R10 值守/watchdog**：把 019 的 feed generation、DUTY_RECEIPT、duty policy、审计 rounds、告警 condition 纳入 task/session/notification 关联，不扩 EventType 作为值守审计。
- **R11 事件/快照**：先冻结实体引用增量事件 schema，再改 LAN/cloud/WAN/Expo；当前 `SnapshotPayload`/全量帧不能在客户端继续被假定为数据库快照替代品。
- **R12 018 融合**：R1 单写者、B0 parity、C1-C3 CLI、P1 bundle、W/E UI 可继续；所有新持久化写入改经 `StoragePort`，避免 018 文件路径继续增殖。

### 推翻重设计（4）
- **O1 推翻“Leader/worker 是数据库主角色”**：以 PM/薄 Leader/worker/review_pm 业务角色 + CommandRole + task participation 三轴重建；否则 083 一落地就再迁一次表。
- **O2 推翻“M1 只有 ClaudeCodeAdapter”**：M1 目标改为 Adapter capability matrix；现有 Claude/Codex/Trae/CodeBuddy/Qwen 兼容路径先纳入，未注册引擎 fail-closed，不为每引擎改核心。
- **O3 推翻 artifact “挂 project 不挂 sid”绝对口径**：project 是聚合归属，session/source/task 是追责与去重所需来源；删除任一会重现当前 deliver 归因或跨源 join 问题。
- **O4 推翻“先做全量 SQLite 表、再一次性切掉旧脊柱”的执行方式**：目标仍是 SQLite 唯一真相，但采用 schema-first + import snapshot + 有界双读兼容；禁止长期双写，也不等所有 UI 完成才迁移。这样能承接当前 JSON beads/018，而不把 `session-manager.ts` 与三端同时变成不可验收大爆炸。

## 4. 与 018 实施线的关系裁定
- 时间线：018 是当前 m2 的协议、relay 单写者、CLI、三端和 bundle 过渡线；V2 是用户拍板后的 SQLite 目标底座。018 不应继续扩展新的 JSON 事实源，但已落的 JSON 资产必须成为迁移输入。
- **立即保留并收尾**：018 R1 单写者/通知、B0 parity/未知命令、C1-C3 对账、P1 统一 bundle、已完成 T2；它们是 SQLite 之前必须有的协议与验收资产。
- **先插入 V2 数据地基**：在新增 083 模式、019 D1/D2、#75 引擎模板、#72 全局产物中心前，先完成 schema 对照、ID/角色/权限/事件注册表与导入器；否则这些线会各自写一套 JSON 字段。
- **不再新增**：新的 boards/confirms/deliverables/notification durable 文件格式；保留旧文件只读兼容与迁移审计。`events.ndjson` 仍保留，但不再承担实体当前态。

1. **M1-0 契约冻结**：逐文件 inventory；确定 project/team/task/session/member/dispatch/acceptance/notification/artifact schema；纳入 083 PM 角色、019 值守、beads、artifact-view；命令/事件单一注册表与 orgAction adapter；迁移损失/旧端降级 fixture。
