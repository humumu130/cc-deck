## 二、编排 payload 最终形状备案（M12-3 依赖此口径）

### COMMAND_DISPATCH 编排扩展（M12-1 冻结字段零改动，只增 task）

```jsonc
{
  "gid": "g-xxx",              // 编排链必填（无组无板可写卡）；直派路径仍可选
  "prompt": "细指令",           // **可选化**：带 task 时可省，缺省兜底 task.text；
                               //   无 task 路径维持 M12-1 必填语义（error「prompt 必填」零变化）
  "task": {                    // 编排链开关：给了就先写卡再派单
    "text": "卡文本",           // 必填
    "status": "todo",          // 可选，词表收窄 todo|doing（done 建卡即完成不收），缺省 todo
    "note": "备注",            // 可选
    "depends_on": ["t-xxx"],   // 可选，#087 依赖卡 id
    "gate": {"reason": "…"}    // 可选，#087 只设闸——gate:null 清除仍走人决策口（红线：无自动放行路径）
  },
  // 其余 M12-1 字段（anchor_dir/title/entry_id/role/skills/engine/model/provider）原样可用
}
```

**互斥规则**：`task` 与 `entry_id` 同给 → error「task 与 entry_id 互斥（建新卡或认领旧卡二选一）」。

**三路径**：①带 task=编排链（本文档主角）；②带 entry_id 无 task=M12-1 认领（computeReady 前置在 dispatchWorker 内）；③都无=M12-1 直派（自动建 doing 卡）。②③行为零改动（C8⑭ 回归断言）。

## 三、blocked 口径备案（倾向后者的定稿）

**blocked = 正常编排态，ACK `ok:true`**：

```jsonc
// 依赖未全 done / gate 未过：
{ "command_id": "…", "ok": true, "data": {
    "entity_id": "t-xxxx", "gid": "g-xxx",
    "task_ref": "t-xxxx",              // ≡entity_id（计划表原文键）
    "blocked": true,
    "block_reasons": ["依赖卡 t-yyy 未完成（todo）"],   // computeReady 逐条可判定，直接透传
    "gate_reason": "等用户验收口径"      // gate 未设过时单列（无 gate 阻塞则 null）
} }
// 零 dispatch_id / session_id 键（零 spawn——不建 worker 会话、不落 dispatched/running 台账行）
```

**就绪成功链**：`data{entity_id:卡id, gid, task_ref:卡id, blocked:false, dispatch_id, session_id}`——blocked 键恒带显式布尔（消费方免猜状态），dispatch_id/session_id 仅就绪链携带。

**三分类语义**（派单文②的落定）：
1. 依赖未完成/gate 未过 → **blocked**（ok:true，零 spawn，卡入账保留——backlog 语义）
2. **坏引用（depends_on 指不存在卡）→ error**（ok:false「依赖卡不存在: t-ghost（坏引用编排拒收——先核板再建卡）」，**写卡前预检零写零 spawn**——坏引用不留脏卡，区别于 blocked）
3. 就绪 → 编排放行（认领派单）

## 四、幂等与失败中间态收口备案

1. **task 成功 dispatch 失败**：卡保留（已入账不回滚），`ok:false, error:"<原错误>（task_ref=t-xxxx 已入账，可带 entry_id 重派）"`——task_ref 内嵌 error 文案（orgCommand 错误返回形状零漂移，error 可读可 grep 可引导重派）。
2. **dispatch 成功但卡认领写失败**（勘察结论）：dispatchWorker 既有路径对 upsertBoardEntry 失败是**宽容收口**（:4803 返回值未判，派单照跑）——派单事实以台账为准（dispatched/running 已落账），卡挂接失败不回滚派单；卡留原状（todo/无 dispatch_id），worker 收口时 moveEntryByDispatch 按 dispatch_id 找卡 no-op 不误伤，卡等人处置/重派。**编排链沿用此既有语义不新加回滚**（触发窗口极窄：写卡与认领之间板被冻结/组被挂起；人决策路径本来就开放重派口）。
3. **幂等**：编排链无内建重试/去重——同 payload 重复发会重复建卡（卡天然唯一 id）。防重复靠 entry_id 认领路径（先查卡再派）。M12-3 receipt 对账单若需「同 task_ref 幂等重派」再立。

## 五、过程中修的真缺陷（重要）

**orgAction("board") upsert 分支白名单缺口**：store 层 upsertBoardEntry 支持 depends_on/gate（#087 落的字段），但 orgAction 漏斗只透传 id/text/status/note——M12-1 接线时未暴露。首跑探针抓到：编排链带 depends_on 建卡，deps 被漏斗滤掉，卡裸奔 → computeReady 误判 ready → **依赖未满足的活被放行 spawn**（正是本单要防的事故态）。已修：upsert 分支补 depends_on（数组守卫+trim 洗刷）与 gate（形状守卫：`{reason:string}` 设闸 / `null` 显式清除 / 其余拒收——gate 面用户命令必须守卫，防脏 gate 落盘）。修后 C8④⑤ 全绿。

## 六、时序与漏斗（grep 实证）

编排链五拍（全在 orgCommand 咽喉内，审计两行）：
```
① 形状校验（gid/互斥/text/status 词表/gate 形状）——failAudit 统一（审计+返回同文案）
② 坏引用预检（loadBoard 查存在性）——零写零 spawn
③ 写卡 orgAction("board",{op:"upsert",…deps/gate}) → 审计「编排建卡」
④ computeReady(落盘卡, 板)（store 洗刷后事实源）→ 未就绪 blocked 零 spawn → 审计「编排 blocked 零 spawn」
⑤ 就绪 → orgAction("dispatch",{entry_id:新卡id, title:task.text, prompt||task.text}) → 审计「编排派单已受理」
```

单漏斗证据：`this.dispatchWorker` 唯一消费点 session-manager.ts:4354（orgAction "dispatch" case）；`upsertBoardEntry` 消费点 :4392（orgAction board upsert，编排③写卡经此）+ :4803（dispatchWorker 认领承接，既有路径）。

**title=task.text 的理由**：dispatchWorker 认领分支以 `title||prompt首行截60` 覆盖卡文本（:4805 既有行为）——编排链传 title 保卡文本全文不截断（C8② 长文本断言 70+ 字符），deps/note/gate 在认领的条件覆盖下原样保留（只挂 doing/owner_session/dispatch_id）。
