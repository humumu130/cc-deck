## 三、history 不折叠 vs E1「最新批次账」区分理由（派单点名备案）

两个「重复」源形似而质不同，判据是**源文件的语义**：

1. **E1 notifications.json = 同实体的重复投影**。同一通知 key 在事件流里反复出现（每次状态推进都重发），byKey 归并 Map 同 key 折叠成一行——**当前态语义**：一条通知只有最新形态有意义，旧形态是噪声，折叠+duplicate-key 落账正确。
2. **F1 results.json 的 history[] = append-only 判定事实流**。线上 `saveResult`（acceptance.ts）每次提交都是 push 追加新批次，用户可对同一条目改判重提（pass→fail）——每条历史都是独立事实：改判链本身就是验收过程的真实记录，折叠即销毁审计面。
3. **折叠发生在读投影，不在存储**。线上读侧 `listAcceptances:169` 取 `history[末位]` 做「最新批次」投影——文件源本身全量落盘 history，SQLite 存全量批次正是对源语义的忠实迁移；「只要最新」是视图层需求，由投影实现。
4. **反证**：若存储层折叠，改判历史不可回溯（审计需求：验收单改判谁在何时改的，bug 定责要用），且与源文件语义背离——重灌时源里明明有 N 条，库里只剩 1 条，幂等对账都对不上。

## 四、范式分叉备案（vs C1/D1/E1 五要点）

1. **目录级 checkpoint 虚拟源**：acceptances 目录不逐文件记账（同 D1 tasks 目录口径）——mtime=树内最大、lineCount=文件数；任一变化→域清重灌。acceptDir 是三表唯一生产者，DELETE acceptance_result→acceptance_item→acceptance_sheet 子先父+按源清旧 loss，单事务内聚。
2. **results 双后缀解析**：`.results.json` 后缀 **13 字符**切 id（施工中曾踩 12 字符坑导致 sheetById 全 miss，已修+注释在案）；`.json` 后缀 5 字符。
3. **行号口径**：sheet/results 是 JSON 单文档无物理行号——lineNo 用语义行号（sheet=1、item=itemIndex、history=hIdx+1），定位线索放 excerpt（results_id/item_index 等），同 D1 目录源口径。
4. **loss source_path 源根级**：统一 acceptDir（同 D1），非 C1 文件级。
5. **无行级续跑**：D1 有 events offset 行级断点续跑；F1 目录级全有或全无——JSON 文件非 append-only，无「半文件」中间态，checkpoint 命中=全快进、任一变化=全重灌，语义等价无缺口。
6. **无 appendLossOnce 守卫**：F1 失效路径先 DELETE 旧账再重落，不存在 D1 的「offset 回拨重遇坏行重复落账」边角态，三元查重守卫无需引入（不动 B2 件）。
7. **observe 定序 stat 先于 read**（P2-1 同款，知会已落实）：observeAcceptanceDir stat 先行，read 前被改→旧 mtime 配新内容→下次失效重扫，安全侧多扫一次。
8. **sha12 私有副本**（3 行，与 C1/D1 逐字同逻辑）——任务书口径：G1 开工前统一定夺共享化，本单不动。
