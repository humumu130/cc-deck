# 团队成员管理策略分析报告：用完即退 vs 固定角色常驻（对标 Multica）

> 2026-11-01 ｜ PM 主持·三路调研（Multica 源码考古/本机实据/cc-deck 编制审计）+交叉质证 ｜ 用户 1101 令
> 证据链：artifacts/w-{multica-source,multica-runtime,ccdeck-org-audit}.md + review-teamstrategy-cross-1101.md（三路全文+质证回执，行号级锚点均在彼）

## 一、问题

用户三问：
1. **图钉事故**：为什么「图钉优化任务」看起来派给了一个已退休的成员？（既然退休为何又派？值得派为何退休？）
2. 我们「任务完成即退休、下次开新会话」的编制 vs Multica「测试/后端开发固定角色常驻」，哪种好？
3. 如果他们的更好，我们怎么改？

## 二、图钉事故真相（法证结论）

**「派给退休成员」从未发生。** 路由三条自动链全部有退休闸（代码+生产 events+journal 三方互证）：熟手链编制门（session-manager.ts:7822 `roster.has(e.session_id)` 才可 resume）、触顶复用链 retired 即 skip、自动拉活链「退休成员不得起死回生」（lifecycle/revive.ts:172）。

用户看到的矛盾是**三个真实机制叠在同一屏**的呈现：

1. **24h 自动裁编**（trimHeadcounts，:8185）：10-31 因额度暂停全员停工 → 11-01 00:28 定时器判定「无活动 1 天」→ 编制 11 人一夜裁到 2 人，退休名单从个位数炸到 91——这是房屋保洁动作，不是能力判决；
2. **席位身份再雇佣**：同夜新派单以「新会话」形态落回**同一个席位 id**（生产 sqlite 双层铁证：席位 id 稳定、其下 CLI 会话全新）——「编制常驻+会话可换」其实已在生产运行；
3. **板卡静态归属**：done 卡 owner 一次绑定永不解绑，把「承接时在编」呈现成「现在派给了谁」。

**根因定性**：「已退休」一个词盖了三种成因（手动除名/自动闲置裁编/组解散），信任动作与房屋保洁混为一谈；加上板卡无时间维度——**矛盾感的 80% 由语义过载制造，不是路由过错**。

## 三、Multica 的「固定角色」到底是什么（源码+本机实据合并）

**常驻的是「数据与配置」，不是进程，也几乎不是记忆。**

- **Agent = 云端一等实体**（服务端 agent 表）：name/instructions（角色人格=用户经 AI Builder 对话生成的完整提示词包，非平台内建枚举）/skills/tools 白名单/并发上限（max_concurrent_tasks）/visibility/归档软删。「测试」「后端开发」= 用户自配的 instructions 提示词包。
- **身份与引擎解耦**：Agent 绑定 RuntimeDevice（本机 daemon），26 协议族可换绑；daemon 常驻（Go），**CLI 进程按任务起、按回合终**（spawn 实录：headless claude → 73.7s 任务生命周期 → GC）。本机实据：探测 6 引擎注册 2。
- **会话键=(agent, issue) 钉死**：同 issue 恒归同角色续会话（CLI 原生 --resume + workdir 粘性）；同角色换 issue=新会话新目录。**跨 issue 的角色级积累记忆不存在**——记忆=服务端记录+CLI 会话+技能库三层拼合（我们的经验库/规则库是其没有的超集）。
- **Squad=路由对象非执行者**：一切路由只到 leader，成员不自动扇出；leader 按花名册+成员 skills 清单委派。
- **断链披露三件套**：retired/rollout-missing/poisoned 会话续接失败时**明示告知**「上轮上下文不可用」而非静默新开。
- **推导态状态**：presence=f(心跳,任务计数) 纯函数推导不存储——天然免「状态同步断链」类 bug。
- **记账到任务行**：TaskAttribution（代谁跑）+per-task token/cost 四元组。

## 四、cc-deck 现状：机制近齐，策略未用

**机制层已有的**（审计十项清单，全部行号实证）：pickVeteran 熟手链（编制门内 resume+免重启注入+熔断）、编制 idle 复用、席位 id 稳定+CLI 会话可换（生产实证）、member-add 复拉通道、routing 评鉴三维（count/failed/rating/**tags**——生产几乎全空，策展从未发生）、经验库/岗位模板/团队规则三注入（=角色级记忆已成型，但 role 只用 worker/pm 泛称，模板三岗闲置）、雇员独立家（未启用）、trim 旋钮（从未按项目节奏调过）、编制 cap+排队治理、组归档编制快照语义。

**策略层的三个缺口**：
1. **叙事缺口**：「已退休」语义过载（三成因一词）+席位复用无文档无 UI 叙事（G6 黑点：源码路径未定位）——用户看到的是矛盾，实际是机制在正常工作；
2. **习惯缺口**：派单默认「新开」而非「复拉熟手」，24h trim 让熟手活不过一个间歇期，pickVeteran 链上经常无单可复用；
3. **角色缺口**：没有「角色」产品面——团队页是会话列表不是花名册，role-templates 闲置，用户无法像 Multica 那样「把 issue 指给测试/后端」。

## 五、三模式评估矩阵

| 维度 | A 用完即退（现状） | B 会话级常驻保活 | C 混合：席位常驻+会话可换+角色记忆 |
|---|---|---|---|
| 任务连续性 | ★ trim 后必冷启动 | ★★★ 上下文全在 | ★★☆ 席位档案+三注入承接，深连续显式 resume |
| 记忆延续 | ★ 仅派单三注入 | ★★★ 但上下文老化腐化（污染累积/压缩失真，200K 窗很快逼 [1m] 档） | ★★☆ 角色级记忆可策展可 GC，会话记忆按需 |
| 成本 | ★★★ 零空转（但冷启动重复学习是隐性税） | ★ 保活+resume 重载（中位 65s） | ★★ 席位是账面概念近零成本 |
| 复杂度 | ★★★ 机制最简 | ★ 看门狗/僵尸/代际全套伺候 | ★★ 判定/注入/席位映射三件套——cc-deck 已基本齐 |
| 用户认知 | ★ **本次事故**：退休组一夜爆炸+悖论感 | ★★★ 名册稳定 | ★★☆ 名册稳定，「离席」语义后矛盾消失 |
| 失败恢复 | ★★★ 死会话=退休无牵挂 | ★ 常驻死=角色失能 | ★★★ 死会话换新 CLI 挂回同席位（**生产已实证**） |

## 六、业界对标

- **MetaGPT/ChatDev**（角色制流水线）：常驻的是「角色定义与流程位」，每轮全新上下文——角色常驻≠会话常驻的经典解；
- **AutoGen**：常驻团队的「何时散场」是一等设计对象（显式终止条件）——对应我们的 trim 参数，但人家是**决策**，我们是缺省值；
- **Claude Code subagents 官方设计**：fresh context 当特性 + memory 目录跨会话持久 + 需要连续性时显式 resume——**官方答案本身就是 C 模式**，与我们机制现状同构。

## 七、结论

**选 C 模式（席位常驻 + CLI 会话可换 + 角色级记忆外挂）——这不是切换，而是把 cc-deck 生产的既成事实「升格为契约」。**

- **B 模式（会话级常驻保活）三路共同否决**：上下文老化腐化 + 保活成本 + resume 重载（实测中位 65s/200K 窗）在 CLI 世代是逆水行舟——Multica 五万星也没这么做（CLI 进程按任务起、按回合终）；
- **A 模式（现状）的问题不在「退」而在「退得没人认账、回来没人知道」**：图钉事故是它的用户认知账单，且 24h trim 让 pickVeteran 熟手链（机制完备）经常无单可复用；
- **C 模式的前置链纪律**（质证裁定）：①先做退休措辞+trim 语义手术（事故收尾）→②G6 席位机制定位并契约化（策略不得压在未定位机制上）→③再建 issue 亲和/复拉优先/角色库（策略层）。

**三个口径纪律**（本报告及后续所有材料遵守）：①席位复用在 G6 定位前只称「生产观测事实」不称「已有机制」；②Multica 记忆统一表述「issue 域内连续+角色级零积累」；③状态哲学「状态=推导、成因=入库」。

**实施**：见 docs/team-strategy-proposal-1101.md（10 模块·按投入排序·语义/机制/习惯三分账+不做清单）。
