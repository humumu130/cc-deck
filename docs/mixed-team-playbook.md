# 混编团队协作实践手册 v1

> 2026-10-04 · 来源：A 方向设计冲刺实战复盘（order23~36 十四批，PM=Codex、Leader=GLM-5.3、用户拍板）
> 定位：Leader↔PM 协作的工程范式沉淀，反哺团队模式产品字段设计（M4 派单/任务书/验收点）。产品化字段见 §7。

## 1. 角色分工与铁律

| 角色 | 职责 | 绝不做 |
|---|---|---|
| **Leader** | 写任务书、探针取证、核验、通报、回炉单 | 下场改交付文件（哪怕一行）；绕过 PM 直改 |
| **PM**（交付方） | 按单实现、自检、诚实汇报环境限制 | 自行扩scope；改单外文件 |
| **用户** | 设计决策拍板、审美裁量 | — |

- **一切修改走单**：Leader 核验发现的 bug → 写修正单（fix1/fix2…）→ PM 修 → Leader 复跑探针。三轮回炉均按此闭环。
- **不进单清单显式写**：审查发现但决定不修的项（误读/记档/超范围），任务书里单列「不进本单」节，防止 PM 自作主张或下轮重复发现。

## 2. 任务书模板（实战验证结构）

```markdown
# orderNN · <一句话主题>（N 项，改哪些文件）

<两行背景：来源（哪轮审查/哪条反馈）、甄别结论（几真几误，误的不进单）>

## 1.【P1】<缺陷标题>（位置选择器）
现象：<肉眼可见的错>；复现：<点哪里看到>；
根因方向：<探针/grep 证据 + 指向哪段代码>（给方向不给死法）；
要求：<终态>（可测量的：宽度/断行/计数/零重叠）；
注意：<相邻不许回退的已验收条款>。

## N.【P2】…

## 不进本单（记档，勿动）
- <项 + 一句理由>

## 验收（Leader 探针）
- <逐条可断言>（含数字口径）
- <回归要求：上轮探针全绿不破>

## 纪律
- 只改 <文件清单>；已验收成果不回退；
- 环境受限（如 headless 崩）静态自检后交 Leader 探针，诚实汇报。
```

**要点**：P 级标注；每项独立可验收；验收断言 Leader 先想好物理自洽的数字（见 §4）。

## 3. 核验流水线

```
PM 交付（watcher 报真终态）
→ git diff 逐项静态核对（grep 关键改动点）
→ CDP 探针断言（本轮新增断言 + 上轮全量回归）
→ FAIL 分诊：真缺陷（回炉单） / 探针姿势（修探针不改代码）
→ 全绿 commit（逐批一 commit，message 带探针成绩）
```

**FAIL 分诊三问**：断言口径物理上成立吗？（期望值是否拍脑袋）→ 测量时元素可见吗？（hidden/display:none 天然量 0）→ 是功能的正确行为撞上断言吗？（如源过滤隐藏卡片）。

## 4. 探针姿势清单（血泪教训）

1. **扫文案禁 textContent**：body.textContent 含 script 源码 → TreeWalker 只走文本节点 + REJECT SCRIPT/STYLE。
2. **先激活再测量**：display:none 屏内元素 getBoundingClientRect=0——先点导航/进详情再量。
3. **隐藏容器量宽=0**：bottom sheet、折叠分组内的图标量 0 属正常——量可见实例，或退而查 computed style。
4. **use/svg 量宽**：`<use>` 元素本身 rect 可能为 0，量 `u.closest("svg")`。
5. **断言口径物理自洽**：期望值类型（[16]≠["16"]）、数字来源（聚合=各源之和）、布局数学（窗口放不下的宽度不许期望）。
6. **过滤后清单断言**：功能会隐藏元素（源过滤）——「总数」与「可见数」分开断言。
7. **探针环境残留**：Chrome user-data-dir 复用带出上轮 localStorage（主题颠倒事故）——探针/截图先 clear localStorage 或全新 user-data-dir。

## 5. 协作基建（模板化）

- **发单**：WS COMMAND_MESSAGE → 必验 ACK `ok:true`。脚本模板 sed 换文件路径复用，零手写。
- **watcher**：盯 PM 会话事件流，`DONE + 90s 无新事件 = 真终态`（DONE 后可能续跑）；40 分钟超时。**必须 run_in_background 挂**（nohup 收不到完成通知）。
- **截图**：全新实例 + 清存储；一张一操作（先点导航再截）。
- **多模态复审**：子 Agent 逐图调 5.3 Flash 分析，产出 P1/P2/P3 清单——**单路结论不采信**，必须源码 grep + DOM 探针交叉甄别（终局轮 9 条 P1 误读 4 条：错字/拼写/版本号均源码零命中）。

## 6. PM（Codex）能力画像

- 交付快、静态改造质量高；**静态 markup 改造可能漏运行时覆盖**（hydrateAvatars 运行时重写 avatar 抹掉 svg 事故）——涉 JS 注入/hydrate 的单，任务书提醒查「运行时是否覆盖静态结构」。
- 其环境 Chrome headless 会异常退出，CDP 自测跑不了——探针核验天然归 Leader（本就是职责分工）。

## 7. 产品化反哺（M4 派单/任务书字段建议）

从实战倒推，团队模式的「派单」数据结构应含：

| 字段 | 来源实践 | 说明 |
|---|---|---|
| `acceptance_probes[]` | §2 验收节 | 每项一条可断言验收点（选择器+期望值/谓词），交付方自检+收单方复跑同源 |
| `out_of_scope[]` | 不进本单 | 显式排除项，防 scope 蔓延+重复发现 |
| `regression_refs[]` | 回归要求 | 关联上轮探针/测试，交付须全绿 |
| `evidence` | 探针/grep 证据 | 任务书内嵌复现证据（量到的数字/grep 计数），交付方可复核 |
| `env_limits` | 环境受限声明 | 交付方诚实声明自测缺项（如 headless 不可用），收单方据此补位核验 |

——回炉单机制 = 同 order 关联的 fix1/fix2 子单；watcher 真终态判定 = M4「派单完成回调」的静默窗口语义参照。
