cc-deck 团队模式 · 组织形态规范 矩阵式裁决稿 v3.1 · 2026-09-26

回答五个互相咬合的问题：AI 团队按什么单位组织（项目制 vs 常驻制 vs 矩阵式）、记忆与台账怎么隔离不混乱、小需求和咨询怎么办、工作怎么路由到项目与人、数据模型与状态机长什么样。结论：矩阵式——常驻的「组织」（唯一 Leader + 两本账）+ 动态的「项目组」（编制/worktree/任务板）；你只跟一个 Leader 交流，开团从用户操作变成 Leader 的分诊决策。v2 = v1 + 三视角审查 32 条分诊修复 + 战略讨论五项增量（cwd 硬规则 / 亲和路由 / 开团自动化 / 两本账 / 三态生命周期）。本稿 preview only，拍板前不 commit。

0现状与问题

现状（V7/V8 已设计，未实现）：团队跟项目走——「开新团队：描述目标 → Leader 建议编制 → 你确认 → 自动建 worktree 并 spawn 全员」，项目完「收团归档」。四个隐性成本：

  • 冷启动重复税：每次开团 Leader 重新理解你的偏好、规范、验收标准，第 N 次开团仍是第一天；
  • 经验归零：A 项目踩过的坑 B 团队不知道，「收团」把养出的默契全部归档；
  • 多线管理：并行项目 = 多个项目 Leader 多条沟通线，管理负担回到你身上；
  • 粒度一刀切：改个按钮和做大工程走同一套开团仪式，轻需求付重税。

1三方案对比 → 裁决

纯项目制（现状）纯常驻制矩阵式（推荐）
组织单位一项目一团队，完事收团一个团队框住所有项目常驻组织 + 动态项目组两层
沟通线每项目一个 Leader单线（唯一 Leader）单线（唯一 Leader）
经验复利✗ 收团归零✓ 持续累积✓ 组织层持续累积
并行隔离✓ 天然隔离硬伤 任务板/编制/上下文混流✓ 项目组物理隔离（cwd）
Leader 上下文小而干净硬伤 装不下多项目历史，单点瓶颈两本账外置，读档恢复
闲置成本无（收团即清）常驻编制挂着编制动态缩回常备态
矩阵式：你要的其实是「一家公司」，不是「一个团队」
  • 常驻层 = 组织：唯一 Leader（你的技术合伙人）+ 两本账（组织记忆 = 经验，慢涨；派单台账 = 状态，快涨但外置结构化）——智能不靠会话生命，靠基础设施。Leader 换模型/厂商 = 换壳不换档：账是文件，新 Leader 上线先读档自检（能复述关键偏好即通过）；
  • 动态层 = 项目组：立项时从组织抽调 + 按需扩编，配 worktree + 任务板 + 验收单；结项归档项目但经验回流组织，编制缩回常备态；
  • 纯常驻制三硬伤分别被「cwd 物理隔离 / 两本账外置 / Leader 只管分诊与汇总」解掉。

2两层结构 · cwd 硬规则 · 三域映射

组织 · 常驻Leader + 两本账 —— 对话入口常开 · 分诊与立项 · 经验沉淀与回流
项目组 · 动态编制 + worktree + 任务板 + 验收单 —— 按项目并行若干个，三态生命周期
普通会话 · 自由不受矩阵约束的逃生舱 —— 任何正经活都可以不经过组织完成

2.1 cwd 硬规则：隔离的物理地基

矩阵式的隔离单位是 cwd（工作目录）——Claude Code 的第一公民（CLAUDE.md 自动加载、memory 按项目 slug 隔离全顺着 cwd 自动成立）。「所有人挤一个目录」结构性不可能：

谁cwd记忆 / 产物落哪
Leaderorg 目录（组织的家，不属于任何项目）组织记忆 + 台账在 org 侧
项目组 worker项目锚点目录（worktree），spawn 时由 Leader 设定项目层记忆 + 产物都在项目目录内
临时探员 / 单会话目标项目目录（按任务锚点）结论按归层规则落位（§3.3）

派活必须带项目锚点——Leader 自己不进项目目录干活：要么派探员带 cwd 去，要么轻量活以项目为 cwd 拉一次性会话。

2.2 项目组生命周期：三态，不是二态

态编制任务板记忆watchdog
在办 active在线干活流动项目层活跃告警
挂起 parked退休进熟手池（释放）冻结保留原地不动，不触发回流静默
结项 archived解散归档只读经验回流组织层，其余封存归档区（不删）—
  • 转移：在办 ⇄ 挂起（双向：你说「先放放」→ 挂起；两周无活动 Leader 主动建议挂起、你点头）；在办/挂起 → 结项（单向，你说「完了/不做了」）；结项 → 在办 = 复活边（虚线特殊转移：读档 + 按归档终态重建编制与看板）。
  • 间歇项目不要过早结项：结项带两个副作用（回流流程白折腾 + 完结心智）；挂起是零仪式暂停，恢复 = 任务板原样解冻 + 路由表把原班人马派回来。

2.5 单聊信息流：单线 ≠ 不分流

「单线指交互对象唯一，不是信息不分流」。并行多项目时 Leader 对话流按项目带锚点（视觉分组 / 话题折叠）；汇报类默认聚合成 digest，不逐条刷流；watchdog 告警进台账与通知流，不进对话流刷屏。

3记忆与台账：两本账 + 三层归位

3.1 两本账（Leader 手里）

组织记忆派单台账
装什么偏好 / 方法论 / 坑（经验）哪些项目在跑、编制状态、派过什么活、什么档、进行到哪（状态）
涨速 / 形态慢，有写入门槛，自由文本快，结构化 append-only（同 events.ndjson 哲学：会话可死，账本不丢）
纪律宁缺毋滥 + 修订淘汰（§3.4）派单先落账再执行；过程不回灌、只收回执一行；活跃/历史分档（活跃全量注入、历史留审计查时检索）

3.2 记忆三层（归位）

层装什么隔离方式生命周期
项目层spec / prd / 决策记录、项目代码理解、架构决策、任务状态、验收标准、项目内踩坑跟项目目录物理走（单一权威位置 = 主 worktree / relay 侧项目组目录，worker worktree 内只放工作性 notes 不入回流——避免合并冲突与回流歧义）结项封存归档区（不删），二次立项读档恢复
组织层（=组织记忆）Leader 维护的团队资产：机器学到的偏好、跨项目方法论、通用坑常驻一份持续沉淀 + 周期淘汰
个人层你手写的全局 CLAUDE.md / memory（commit 纪律、文案军规——这些本来就在这）跨一切，对一切 AI 生效已在运行
写入判据两条：① 换一个项目，这条经验还成立吗？（成立→组织层；不成立→项目层）② 谁维护——个人层 = 你手写、Leader 只读不写；组织层 = Leader 机器维护、你可选读。个人层已有的不收，只收机器学到的增量（防双写漂移）；两处冲突时个人层优先（手写的压倒推断的）。咨询结论归层：项目相关的写项目目录记忆位（目录即锚点，不依赖活的项目组），通用的才进组织层。

3.3 检索机制分工（谁自动注入什么）

  • 项目层：自动注入发生在以项目目录为 cwd 的会话（worker / 探员）上——机械保证，零注入代码；
  • 组织层：Leader 的 cwd = org 目录 → org 的 CLAUDE.md / memory 自动加载（零代码捷径）；Leader 不装项目层明细，靠探员回传；
  • 个人层：全局机制，已在运行。

3.4 修订 · 可见性 · 回流（防「只写不修」）

  • 变更可见：Leader 每次沉淀 / 回流，对话流带一条摘要，你事后可否决（不必审批制）；组织层写入统一走 append-only 审计（谁何时写了什么，UI 可查）；
  • 周期淘汰：结项时 + 周期性对组织记忆做一次复核（环境类经验会过期：代理端口、adb 行为…）；
  • 回流 = 提案 diff + 你一键确认（复用验收单既有交互模式）；漏回流是设计内代价（宁缺毋滥的另一半，明示）；
  • 纠偏覆盖：正经立项有独立验收（换厂商）——轻档接受无独立复核，靠痕迹可回滚兜底（显式取舍）；
  • 文档防漂移：spec / prd / 决策记录与代码同权走 git——动到 spec 的改动进同一 commit，回执「改动文件」自然体现，不设附带物、不加确认（组织记忆跨项目静默生效故提案确认；spec 项目内演进、git 可回滚故附报）；结项归档前断言级核对（限可验证断言，背景叙事不参与；先 git log --follow 机械清账无回执变更，再逐断言查代码；零异常一句话归档，有异常出漂移清单走验收单逐条裁决）；纪律载体 = 立项时生成项目 CLAUDE.md 防漂移条款（目录级自动加载，普通会话也覆盖；改一字亦须报；你本人直改天然合法，不入核对异常）；红线：不做段落级映射与覆盖率统计（防滑坡；落 M2）。

3.5 Leader 会话生命周期

常驻 = 逻辑常驻（固定 session id + org cwd），物理按需拉起（复用现有 resume / auto-revive 底座）：拉起 → 注入 org 记忆 + 活跃台账 → 干活 → compact 是预期行为（长会话必然撞），两本账就是 compact 后的回锚——读档恢复，它「知道手下有哪些团队」不是因为记得，是因为每次上岗先读账。写档侧：沉淀是显式动作或回合末增量（实现时取舍），不依赖「会话结束自动沉淀」钩子。

3.6 边界划清

  • 跨项目工件：代码复用走工程手段（包管理 / git 引用），组织层只沉淀经验不沉淀工件——防止把组织记忆当资产库做胖；
  • 轻立项：不建独立 worktree，项目层记忆直接放项目目录（与咨询归层同解）；结项走极简回流；
  • 越级：单线是默认交互模式不是权限墙——你是所有者，随时可进任何 worker 会话直接说话，事后知会 Leader 一声即可。

4响应四档 + 第五态：分诊权在 Leader

档场景组织动作确认门槛落点
咨询问问题、要分析，不改代码一律在 Leader 对话内完成（探员是 Leader 的子 agent，不产生第二条沟通线，用完即弃）；结论按 §3.2 归层沉淀；发现 spec 勘误转随手办顺手修零确认Leader 对话
随手办30 秒~几分钟小改（改文案、加按钮）派单会话 worker；不建 worktree；痕迹三件套：完成回一行结果+改动文件、commit 归属 [随手办] 描述、派单记录留台账；worker 会话归档不删档（审计）；权限走 acceptEdits + 白名单，改前认领、改后报 diff零确认项目目录（cwd 锚定）
轻立项几小时~几天小功能编制 = 1 worker + Leader 兼管；任务板单卡简化态（渲染降级非独立模型）；不建独立 worktree同类免确认（首次确认一次，信任累积）项目组（轻）
正经立项复杂项目（现完整团队模式）全套：编制、看板、验收单、独立验收（换厂商）；保留你确认编制环节（现状锚点，明写防丢）必须确认（一次点击，防误判档烧钱）项目组（全）
建议暂缓与在办冲突、依赖未就绪、时机不对分诊的合法第五输出：一句理由 + 触发条件，对齐 [搁置] 习惯你点头即挂起—
  • 升降级：任一档运行中 Leader 可提请升降级（一句理由 + 增量编制/验收点），你确认即迁移——任务卡与 worktree 原地继承、只补不重建（分诊是概率判断，必须有矫正通道）；
  • 护栏：单项目预算超线要确认；并行项目组数量上限（活跃台账因此天然是小表）；闲置自动缩编回收；
  • 开销认账：分诊融合在 Leader 回复里（非独立调用）；每个随手办比直接开会话多一跳固定开销（分诊回合 + 拉起 + 回报），属可接受代价——换来的是痕迹与归口；
  • 手动开团降级为高级路径：你预知是大工程可直接说「给我立个项」——说一声即走，不走表单。

6信息模型与状态机

6.1 六实体（初期文件态，模型不漂、存储可换）

实体关键字段形态
org 组织单例：记忆目录、配置目录 + 文件
project_group 项目组锚点目录、状态（三态）、编制快照、任务板引用、时间戳组json 索引
dispatch_log 派单台账append-only：档位、目标、项目锚点、状态、回执一行ndjson
routing_table 路由表agent × 项目：次数、上次、评价、技能标签json（量大迁 sqlite）
org_memory 组织记忆自由文本 + append-only 审计md 文件
worker= 会话 id + 档案（退休后只剩路由表记录）无独立表，快照存项目组

项目层记忆（spec / prd / 决策记录）物理 = 项目目录文件，不入独立实体，实体模型只管引用（project_group 锚点目录）；spec 变更的权威存储 = git commit 本身，台账不存 diff 内容。

6.2 三层状态机

项目组（主）：在办 ⇄ 挂起（主动 / 两周无活动建议） ｜ 在办/挂起 → 结项（单向终态） ｜ 结项 ┄→ 在办（复活边：读档 + 重建）
派单：已派 → 执行中 → 完成 ｜ 失败 → 重派（失败学习回写路由表）
成员会话：active ⇄ parked（与项目组态联动：组挂起 → 全员 parked；恢复 → 路由表拉原班）
