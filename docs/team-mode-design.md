# 团队模式（Multi-Agent Team Mode）设计笔记

> 2026-09-18 与用户讨论定稿的探索性专项。目标：把"多 Claude 会话并行开发 cc-deck"从手工操作升级为产品能力，作为 cc-deck 的差异化特色。本文档是立项快照，动工时从此接续。

## 背景与动机（2026-09-18 实证）

当日真实工作流暴露的痛点与机会：

- **套娃接手**：三个云端会话连续"卡住"（实际是 completed 但 UI 不刷新），根因是 spawn 环境缺陷（见 M0），且每次"接手"都丢上下文，靠考古 transcript 恢复
- **验证阻塞开发**：单会话时间轴里 70% 是等待型验证（tsc / gradle / CI / KV 上传 / 清单校验），零智力含量但串行占坑
- **用户角色校准**：用户不 review 代码，只做真机装机看效果；效果验证大部分可 Agent 化，用户只兜底最后一公里
- **成本模型反转**：GLM Coding Plan 包月（不按 token 计费），并行成本从"花钱"变为"占容量"（5h 限额池，多会话加速消耗，需确认口径）

## M0：环境注入（地基，与团队模式与否无关都该做）

relay 创建会话进程时自动配好环境，两件事：

1. **注入 PATH**：会话进程默认 PATH 仅 `/usr/bin:/bin:/usr/sbin:/sbin`，node 在 `~/node/bin`、`/usr/local/bin` 均不可见（实证：6366b926 会话 hook 报 `node: command not found`；gradle 构建 APK 报 `Cannot run program "node"`）。spawn 时补全 PATH 即根治
2. **固定 cwd**：云端会话自带 Windows 残留路径 `/C:`，无效即回落家目录 `/Users/xdd`，会话连仓库都找不到（三连"卡住"的根因）。relay 配默认项目目录（或建会话必选项目），绝不回落家目录

技术形态：spawn 时多传两个参数（env.PATH / cwd），与 `f283b58`（任务工具门控的 spawn 注入）同一套机制，改动小。

## 架构映射：团队部件 → cc-deck 现有能力

| 团队模式需要的 | cc-deck 已有的 |
|---|---|
| 消息总线（Agent 间通信） | relay 本就是所有会话的总线（消息/状态/生命周期全过它） |
| 会话创建/管理 | 手机端建会话（cwd、权限模式）已有 |
| Claude Code 钩子 | cc-plugins 体系 + spawn 注入先例（f283b58） |
| 指挥界面 | 手机 App = 随身控制台 |
| 代码隔离 | relay spawn 时自动建 worktree + 分支，结束回收 |
| 发版互斥 | relay 全局锁：test.N 序号、latest-test.json 写入串行化（当日手工维护的纪律产品化） |

## 产品交互设计

### 入口与开启

- 手机端"新建会话"旁加显式"开启团队"入口，选项目后进入团队工作区；**不做默认**（单会话仍是主流）
- 桌面端同款入口

### 会话形态：单聊 + 看板（不做群聊）

用户界面 = 与 Leader 的普通对话 + 团队看板，**不是**微信群式的多 Agent 群聊：

- **主对话**：用户只与 Leader 一个对话（形态与现有单会话完全一致，零学习成本）——下目标、确认编制、收"就绪待装机"通知、回效果反馈，全在这一个窗口
- **团队动静不进聊天流**：派工/汇报/Agent 间协调是机器间通信，进聊天流对用户全是噪音——用户角色是验收效果，不是围观过程。动静以看板状态变化 + 活动时间线呈现（类似群聊"系统消息"，按 Agent 分卡片）
- **群聊的技术死穴**：N 个 Agent 共享一个聊天上下文会互相污染、膨胀变钝（会话越长越钝），且 worker 直接看到用户消息会各自解读、指挥链就散了
- **成员会话聚合**：worker 会话收纳在团队工作区内（点卡片可只读旁听该 Agent 会话——M2+），不在普通会话列表散着显示
- **不直连 worker**：默认无绕过 Leader 直接指挥 worker 的入口，插话经 Leader 转达

### 团队规模：任务定编制，不是先拍人数

- 默认流程：用户描述目标/任务清单 → **leader 分析改动面后建议编制**（"三件事互不碰文件，建议 3 开发 + leader 兼验收"）→ 用户确认或修改
- 高级设置：允许硬性指定规模（含上限），与套餐 5h 限额联动做水位提示
- 编制方案必须过用户的目：leader 的智能放在可见、可否决的位置，不做黑箱

### 身份 = 三件套（不是一个名字）

1. **提示词模板**：system prompt 写死角色边界（"手机端 worker，只改 `expo-app/**`"）
2. **权限与资源**：worktree 分支名、可用工具、默认无发版权
3. **身份模板库**：手机端 / 桌面端 / relay / 验收 / 调研（只读）——leader 按任务改动面映射

身份动态可调：验收高峰开发转验收；worker 卡住 leader 收编任务。

### 手机看板（用户的"只看效果"视野）

呈现形态（v4 定稿竖排、v5 补色语义闭环，2026-09-18/19 与用户对齐）：手机又细又长，看板做**竖向泳道**——状态分组纵向堆叠（组头 = 状态名 + 计数 + 可折叠），**「就绪待装机」组置顶**（用户最关心，组头/卡片/按钮统一琥珀高亮），已完成默认折叠；卡片全宽，可多带一行过程信息（自测进度、活跃新鲜度、停滞告警）。顶部保留**进度总览条**（分段配色与状态语义闭环：灰=待认领 · 绿=进行中（对齐成员三色"绿=干活中"）· 品牌色=待验收 · 琥珀=就绪待装机（与徽标同色）· 深蓝灰=已完成）补状态分布一览；看板 tab 琥珀徽标 = 待装机数量（琥珀 = 需要你行动/注意，与「⚠ 停滞」告警同色族）。曾评估横滑泳道（Trello 式）：适合"搬卡的人"，但手机端用户是指挥/验收者不搬卡，拇指工学与卡片信息密度都输给竖排——弃。成员页每卡：三色状态（绿=干活/黄=滞留/红=失联，watchdog 双信号）+ 上下文水位条 + 心跳新鲜度 + 当前任务/分支；"旁听"（M2+）与"经 Leader 转达"入口。交付物出 test 包后标"就绪待装机"，用户装机看效果、一句话反馈，leader 派修复循环。

**任务板是团队共享的单一事实源，建在 relay 层**。Claude 内置任务清单（TaskList）按会话隔离、跨会话不互通（已实证，见风险 5），团队协作必须有一份所有人（含用户）共用的板——relay 的 events.ndjson 事件流是现成载体的自然延伸。一份数据两端消费：

- 手机/桌面端渲染成状态泳道：待认领 → 进行中 → 待验收 → 就绪待装机 → 完成
- Agent 端读写（认领、状态流转）：cc-plugins hook 把本地任务变化上报 relay，spawn 注入的团队身份让 Agent 知道自己在哪块板上、是谁

**与原生 TaskList 的关系（勿混淆）**：今天手机上看到的任务面板 = 单会话自己的原生清单，经 cc-deck 透出（多端查看）。团队板不是在它基础上改——原生清单活在会话 runtime 里、天生私有、无跨会话接口（当日实证：接手会话靠考古重建清单）。正确关系是：**管线复用（事件→relay→手机 UI 那半截沿用），数据重建（换成 relay 共享数据）**；成两层分工——原生清单 = 工位便签（成员内部小步骤，私有），团队板 = 墙上看板（跨成员任务，共享），hook 只做单向"便签动静抄上墙"。

### 桌面端（驾驶舱——Tab 制全宽，开发主场景）

v5 定稿（2026-09-19 与用户对齐，替代 v4 三区并排）：**不新开布局**——现网 web-console 骨架原样（侧栏会话列表 + 右详情区 Tab 制），团队模式只是**侧栏多一个「团队」分组**（成员卡 = 现有会话卡同款样式：三色状态点 + 当前任务/分支一行）+ **详情区多三个 Tab**：消息（与 Leader 单聊，全宽）/ 看板 / 成员 / 活动——与现有「消息·任务·全部」同一套 Tab 骨架，**互斥全宽**，会话永远不被挤；团队动静（派工/提交/验收/异常）落「活动」时间线，不进聊天流。看板在宽屏下**横排泳道**全宽铺开（手机细长才竖排——同一份数据，各用各的形态）；看板 Tab 琥珀徽标 = 待装机数。

驾驶舱按需开：◱ **分屏**把看板钉成右半屏（消息+看板并排，再点收起）；EXE/Mac 独有 ⧉ 看板**弹出独立窗口**（可挂副屏）+ 📂 打开成员 worktree 目录——网页端经能力探测隐藏这几个本机按钮。

桌面端独有能力（手机/网页做不了的）：

1. **worktree 可视化**：成员卡显示本地 worktree 路径，一键在终端/编辑器打开——桌面端就跑在宿主机上，路径真实存在，人可以直接钻进成员的工作区看代码
2. **收团操作的呈现面**：leader 做 merge 时桌面端展示合并预览/冲突提示（执行者仍是 leader 会话）
3. **relay 运维入口**：重启重建、spawn 记录查看、团队归档等管理动作收纳在此

### 网页端（与桌面端完全同构）

**一套 web-console 代码**：网页端与桌面端/EXE/Mac 完全同构——同一设计、同一交互（发消息、看板、成员、活动全可操作），仅通过能力探测隐藏本机专属按钮（📂 worktree / ⧉ 弹出窗口），配对即信任，不做只读降级。v4 设想的「M1 只读观察窗」废弃：产品现状本就是三端一份代码同权使用，团队视图没有理由做二等公民。

### 三端一致性原则

三端 UI 形态不同、数据同源：全部由 relay 同一事件流驱动（BOARD_* / SESSION_* / notify.user），端只做渲染层差异。板的单一事实源原则，落在三端就是"任何一端看到的板都可能过期，relay 的才是真的"——断线重连走既有 last_seq 补发，不另做端间同步。

### 分工边界（当日验证的教训）

- **开发自测不外包**：tsc/构建等快反馈含在开发内（丢出去丢上下文）
- **验收会话独立视角**：不信任开发者自我声明，独立出包复现、对照验收清单；共享 1 个验收会话而非 N 个配对（负载均衡 + 出包口全局唯一）
- **按改动面切任务**（组件边界）：expo-app / web-console+tauri / relay+cc-plugins / scripts+CI；横切任务（如 updates.ts 类）不并行拆
- **开发可并行，发版永远串行**：版本号、清单、KV 是竞态资源，全局唯一出包口

## 与 Claude Code 内置多 Agent 的关系（差异化定位）

内置子 Agent（Agent 工具）和内置 teams 模式都是**"一个会话进程树内的并行"**；团队模式解决的是**"会话之间的协同"**——分层互补，不是重复造轮子：

| 维度 | 内置子 Agent | 内置 teams | cc-deck 团队模式 |
|---|---|---|---|
| 生命周期 | 父会话的子进程，父死全死 | 同一 runtime 内同生共死 | 成员 = relay 上各自独立的会话，互不连坐；leader 挂了可被接替，团队照跑 |
| 协调中枢 | 父会话上下文（占父的注意力，父是单点） | team 共享内存（runtime 内） | relay 任务板（外置持久化，不占任何成员的上下文） |
| 状态存续 | 内存，随会话消失 | 会话级 | relay 持久化 + git，任何成员可被新会话接续 |
| 用户界面 | 终端（单机单操作者） | 终端（单机单操作者） | 手机/桌面 App，随处指挥、逐成员旁听 |
| 模型 | 同一 Claude Code | 同一 | 可异构混编（GLM/Claude 等，协议在 relay 层） |
| 身份与隔离 | 简单（prompt + 工具白名单） | 简单 | 身份三件套 + 自动 worktree + 发版互斥（运维纪律产品化） |

要点：

- **内置能力照样用**：Leader 会话内部仍可用子 Agent 做快速扇出（并行搜代码/读文件）——"会话内并行"用内置，"会话间协同"才上团队模式
- **护城河在产品面不在编排机制**：手机指挥台 + relay 持久化断点 + 异构模型，是内置能力结构上给不了的（它绑在单机单终端单 runtime 上）；编排机制反而要保持糙
- **当天反例即现状**：三个云会话互相"接手"靠考古 transcript、手工 HANDOFF，就是没有团队模式时的会话间协同水平

### 对外速答：优势在哪（被问时的标准答案）

"独立会话"本身不是卖点，独立之后买到的五样东西才是：

1. **抗死**：互不连坐、断点接替。Leader 卡住 worker 照跑；接替 = 指着板起个新会话，不是考古 transcript。反例实证：当日三连"卡住"靠翻会话记录接手
2. **领队不膨胀**：协调状态外置（relay 板 + git），汇报不流经 Leader 上下文——原生模式里所有子 Agent 汇报都撑父会话，编排者自己变瓶颈；任务越多跑越久差距越大
3. **24/7**：team 是 relay 上的持久实体，不是 runtime。人离开组照跑，手机收"就绪待装机"推送——用户在公司、家里出包的真实工作流，原生结构上给不了（合上终端组就散）
4. **异构混编**：协议在 relay 层，Leader 用强模型、搬砖走包月订阅（GLM）、验收再一路——按角色路由质量与成本
5. **运维纪律产品化**：文件域权限、自动 worktree、发版互斥——真实团队踩坑变成的护栏，原生 subagent 是"聪明的大脑"不是"守纪律的团队"

原生赢在零基础设施与共享上下文（Leader 内部照样用它做快速扇出）。一句话：**原生 teams 是"办公室里的工作组，你一关门组就散"；团队模式是"挂在服务器上的常设工作组，掏出手机随时指挥"。**

## 通信与协调原则

- **控制流用消息**（谁该干什么），**状态用 git 和文档**（干到哪了）——HANDOFF/任务描述/commit 是团队的制度记忆
- **连续性不靠会话记忆**：Agent 会话上下文是消耗品（越长越钝），文档和仓库才是记忆
- 任务板载体：GitHub Issues（推荐，认领/状态/标签现成）或仓库任务文件
- 跨模型无关：编排协议设计在 relay 层，不依赖具体模型的自觉（leader/worker 可能跑不同模型）

## 运行时协议（M1 细化草案）

原则：**糙**。字段够用就行，消息类型能少则少，权限收紧留到 M2。

### 任务卡（板的唯一实体）

```json
{
  "id": "T-12",
  "title": "更新通道隔离",
  "scope": ["expo-app/**", "scripts/build-test-apk.sh"],
  "accept": [
    "test 设备应用内可查到新 test 包",
    "release/snap 设备检查更新永远看不到 test 版本"
  ],
  "status": "ready_to_install",
  "assignee": "worker-mobile",
  "branch": "wt/t7/mobile-upd",
  "artifact": "0.5.2-test.17",
  "handoff": "现象/根因/修复选项/验收/部署流程的自包含说明（可选）",
  "updated": 1695024123
}
```

- `scope` = 改动面（文件域）：派工时按它做互斥分组——scope 有交集的任务不并行
- `accept` = 验收点清单：worker 自测对着打勾，验收会话独立复核同一份——单一验收标准，两道关
- `artifact` = 产出物（test 包版本号），"就绪待装机"的依据
- `handoff` = 交接自包含说明（可选）：任务中途换人/换会话时，新接手者读卡即接手，不考古 transcript——手工交接文档（2026-09-18 晚实战验证）的产品化内嵌

### 状态机

```
backlog（待认领）
  ├─ worker 认领 / leader 指派 ──────────→ claimed（进行中）
claimed
  ├─ 自测过 + commit 上分支 → 提交 ─────→ submitted（待验收）
  ├─ 卡住 / 放弃 ──────────────────────→ backlog（任务回板）
submitted
  ├─ 验收复核通过 + 出包 ──────────────→ ready_to_install（就绪待装机）
  └─ 验收打回（必附一句话原因）─────────→ claimed
ready_to_install
  ├─ 用户装机看效果 OK ────────────────→ done
  └─ 用户一句话反馈问题 ───────────────→ claimed（leader 派修复循环）
done（终态，板保留供审计）
```

- **用户在环是硬性设计**：ready_to_install → done 必须用户确认——用户是最终验收人，这一步不自动化
- 打回必附原因：原因是 worker 下一轮的直接输入，闭环就此成立
- **认领必须原子**（2026-09-18 撞车实证）：backlog → claimed 由 relay 单点判定（读-改-写在同一 tick 完成），先占坑者得，后到者收到"已被认领"即让位；成员 spawn 后第一动作 = 读板认领，不直接开工
- M1 流转权限从宽（谁都能改状态，UI 按角色高亮默认动作）；M2 收紧（worker 只能操作自己的卡）

### 消息集（刻意最少）

只有三类，全部经 relay：

1. `chat`：用户 ↔ leader 的会话消息（现有能力，原样）
2. `board.*`：任务卡增删改/流转（板操作的事件化，手机和 Agent 双端消费同一事件流）
3. `notify.user`：推用户的（就绪待装机、验收打回摘要、成员异常）

**worker 之间 M1 不做点对点通信**——必须协调的经 leader。控制流=leader 的派工消息（spawn 后首条 prompt 或会话内新指令），状态=板。少一类消息，少一类失控。

### Leader 循环 / Worker 循环（伪码）

```
leader:                          worker:
loop                             loop
  读板 + 成员心跳                   领卡（或接 leader 派工）→ claimed
  有 submitted 且验收空闲           在自己 worktree 开发
    → 派验收                       自测不过不提交（含在开发内）
  有 backlog 且编制有空位           commit 上分支 + 自测结果 → submitted
    → 按 scope 互斥派工            被打回 → 读原因继续改
  用户有新消息 → 处理               通过 → 领下一张
  成员心跳超时
    → 卡回 backlog，可重启成员
  全部 done 且用户确认 → 收团
```

### 接替机制（连续性的机制化）

- 每成员周期性心跳到 relay（hook 上报，不靠 Agent 自觉）
- 接替 = spawn 新会话 + 注入身份（"你是 team X 的 leader，板在 relay"）→ 新 leader **读板即恢复**，无需考古 transcript
- 这条就是把"连续性不靠会话记忆，靠 git 和文档"的原则变成机制

### git 工作流

- 每成员一个 worktree：`git worktree add ../cc-deck-wt/<member> -b wt/<team>/<member>`
- 分支只允许动自己 scope 内的文件；越域改动 leader 合并时拦
- 合并由 leader 统一做（squash 回 dev），成员之间不互相合并
- worktree 回收：成员名下任务全部 done 且已合并后删

### 发版互斥

- relay 提供锁（单机文件锁即可，糙够用）；build-test-apk.sh 出包前先拿锁
- test.N 序号、latest-test.json 写入的竞态彻底机械化消掉——当日手工纪律的产品化落点

### 开团 / 收团

- **开团**：用户点入口 → relay 建团队实体（板+id）→ spawn leader → leader 分析任务提编制 → 用户确认 → leader spawn 成员（身份三件套 + worktree 注入）→ 运行
- **收团**：leader 全量 merge → 出 snap/release 包 → 板转归档只读 → 清 worktree → 团队条目折叠进历史（板的审计价值保留）

## 实现原理（M1 具体怎么做）

上一节定协议，这节落代码。全部改动收敛在 relay + cc-plugins 两处，三端客户端只加渲染。

### 数据层：team-store.ts（relay 新模块）

- **内存板** `Map<task_id, TaskCard>` + 落盘快照 `~/.cc-deck/teams/<id>/board.json`（tmp+rename 原子写）——与 events.ndjson "快照答当前态、事件答审计"的双轨架构同构（见"存储"定档）
- **每次 mutation 双写**：改内存 → 写快照 → `bus.emit("BOARD_UPDATED", {card})` 进事件流；客户端断线重连靠既有 last_seq 补发，板不需要自己的同步机制
- 快照下发：SNAPSHOT payload 增加 `teams` 字段（板 + 成员清单），增量走 BOARD_UPDATED——手机/桌面/网页三端同一条路

### 命令面：COMMAND_BOARD_*（走既有 Command 信道）

`LIST / CREATE / CLAIM / SUBMIT / REVIEW / INSTALL_FEEDBACK`。关键在 **CLAIM 的原子性不靠锁靠单线程**：relay 是 Node 单进程单线程事件循环，CLAIM 处理函数同步完成"读卡→验状态→改 assignee→写快照→广播"，两个并发认领天然串行，后到者 ack `ok:false, error:"已被 worker-mobile 认领"`。这是"糙但正确"的典型——不加分布式锁、不加事务，架构本身保证。

### 成员身份注入（复用 injector 机制，零新发明）

spawn 参数扩一组（与 M0 的 PATH/cwd 注入同一挂点）：

- env：`CCR_TEAM_ID` / `CCR_TEAM_MEMBER` / `CCR_BOARD_URL`（成员自知在哪个团、是谁）
- system prompt 模板：角色边界 + "第一动作读板认领" + 协议速查（任务卡 schema、状态机、汇报格式）
- 权限：默认 `acceptEdits` + 文件域说明写进提示词（M2 再机械化）

### hook 上报："便签抄上墙"（cc-plugins 新增）

成员会话内原生 TaskList 变化（TaskCreate/Update 的 hook）→ POST `localhost:<port>/api/board/report` → relay 把摘要挂到对应成员卡（只作展示，不改任务卡状态——卡状态只由协议动作驱动）。任务存储直读（`~/.claude/tasks/<sid>/`，#206 既有路径）做兜底对账。

### watchdog：三色判定的信号源

不用新机制，relay 已有两路信号组合判定：SESSION_HEARTBEAT（5s，进程活着）+ SESSION_LOG 时间戳（真在干活）。无心跳=红（死，接替）；有心跳无日志超阈值（默认 10min）=黄（滞留，通知 leader）；日志在流=绿。全部在 relay 本地判定，**不信端上在线状态**（手机休眠/云桥断连不构成假死证据）。

### worktree 供给线

开团确认编制后，relay 逐成员执行 `git worktree add ../cc-deck-wt/<member> -b wt/<team>/<member>`，spawn cwd 指向该目录；收团 leader 逐分支 squash merge 回 dev（scope 机械校验：`git diff --name-only` 对照任务卡 scope，越域改动打回），全并后删 worktree。磁盘与成员数控制见风险 6。

### 发版互斥

M0 已把 mkdir 原子锁写进 build-test-apk.sh（同款 pid 探活防死锁）。M1 只需把锁暴露为 relay HTTP 端点（`/api/lock/acquire|release`，LAN token 门禁），脚本与未来验收会话共用同一把锁。

### 接替与重启重建

- **接替**（成员死）：spawn 新会话 + 注入同身份 → 新会话读板 + 读卡（`handoff` 字段）→ 认领继续。全程不碰 transcript
- **重启重建**（relay 死）：spawn-record.json（身份/cwd/cli session_id/分支）+ 启动时按记录逐个 SDK resume——对话记忆在 transcript 无损，成员进程原地复活，团队从"灭团"变"闪断"

### 一次派工的完整消息序列（示例）

```
用户 → leader: 「把更新检查做成三通道隔离」
leader → relay: BOARD_CREATE ×3（按 scope 拆卡）
leader → relay: COMMAND_TEAM_SPAWN(worker-mobile, 身份模板=手机端)
relay:          worktree 建立 → spawn 注入 env+prompt → 成员卡上线（绿）
worker-mobile:  BOARD_CLAIM(T-12) → relay 原子判定 → BOARD_UPDATED 广播（三端看板同步）
worker-mobile:  （开发，hook 摘要上墙）→ commit → BOARD_SUBMIT(T-12, 分支, 自测结果)
leader → relay: COMMAND_TEAM_SPAWN(verifier) → 验收复核 → BOARD_REVIEW(T-12, pass) + 出包
relay → 用户:   notify.user「T-12 就绪待装机 0.5.2-test.18」
用户 → leader:  装机反馈「OK」→ BOARD_INSTALL_FEEDBACK(T-12, ok) → done
```

## relay 现状评估（2026-09-18 盘点）与前瞻改造

结论先行：**云桥（ECS/CF）零改造；本地 relay 缺的是"实体状态层"与几处小改；不需要引入数据库。** 团队模式的板/锁/心跳全部落本地 relay，手机看板走"看会话列表"的同一条云桥链路（桥只见加密帧，保持哑的）。

### 需求对照盘点

| 团队模式需要 | relay 现状（实测代码） | 差距 |
|---|---|---|
| 持久化底盘 | events.ndjson 追加 + 启动压缩（30 会话/50 状态/300 日志上限、心跳丢弃）+ 重启重放重建 + 500 环形缓冲 + last_seq 补发——**极简事件溯源已就位** | 板需要"当前态查询"，不能靠重放事件 → 加状态快照层（见下） |
| 心跳/死活 | 会话级 heartbeat 定时器、云桥 10s ping/25s 判死、外部会话 pid 探活（process.kill(pid,0)）、重放时非终态矫正 | 组装成成员 watchdog 即可，无新机制 |
| cwd 固定 | **#293 三级回落已实现**（手机指定 → CCR_CWD → homedir，带指引警告） | M0 的 cwd 半件已完成，任务 #2 只剩默认值与残留路径清理 |
| PATH 注入 | 无：会话继承 relay 守护进程的残缺 PATH（实证 node not found） | M0：injector 加 env 补全（injector.ts spawn 注入先例现成） |
| 互斥锁 | relay.lock（pid 文件锁）单实例锁已有 | 发版锁照抄同款模式，补脚本可用的获取/释放端点 |
| 身份注入 | injector.ts spawn 参数注入（f283b58 先例） | 加 team_id/role/身份三件套载荷 |
| 任务清单透出 | 直读 ~/.claude/tasks/<session>/*.json（#206 根治跨会话聚合） | 复用为"便签动静抄上墙"的上报源 |
| 会话间消息 | 手机→会话消息、WAITING 审批通道已有 | leader→worker 派工注入：大概率复用现有通道，M1 落实 |
| 云桥 | 本地 relay ↔ 云桥 E2E 加密帧、按设备路由 | **零改造** |

### 存储：不需要数据库（"要不要 DB"的定论）

relay 单机、单进程、单写者；板的数据量 = 几十条任务卡。分档：

- **M1：状态快照 JSON + 原子写（tmp+rename）+ 事件流广播双写**——快照答"当前态"，事件答"审计与实时"，与现有 events.ndjson 架构同构，零新依赖
- **M2+ 才考虑 SQLite**（better-sqlite3 单文件嵌入式），触发条件：多项目多团队、卡上千、需按字段查询索引
- **永不上服务型数据库**（MySQL/Postgres）：relay 产品形态是零依赖单进程（桌面端内嵌同款），外部 DB 直接破坏 embedded 形态

### 盘点顺出的优化点（与团队模式无关也值得做）

1. events.ndjson 仅启动时压缩——长期运行的 relay 文件只增不减（摘要级量小，不急；周期压缩是个定时器的事）
2. 会话保留上限 30（MAX_SESSIONS_KEPT）：团队成员会话会挤占普通会话名额 → 收团归档时连带清理成员会话
3. 手机端残留 /C: Windows 路径仍在制造 create-cwd 警告（任务 #2 现象）——手机端目录记忆需清理/校验，属 M0 外围

## 实战反馈（2026-09-18 晚，双会话并行实录——dogfooding 第一课）

当晚双会话（本会话 + tag 会话）在同一工作区并行工作数小时，以下五件事是设计必须吃回去的实证：

1. **撞车事件 → 认领必须原子**：同一条指令被发给两个会话，两者同时扑向同一批文件（清理 HANDOFF 文档），靠后到者人工发现"文件已被对方改过"才避让。结论：任务板认领（backlog→claimed）必须是 relay 端原子操作——先占坑者得，后到者收到"已被认领"即让位；成员 spawn 后第一动作 = 读板认领，不直接开工
2. **relay 部署链 → 重启韧性是 M1 硬需求**：换一次 relay 代码 = 构建 bundle → 换 App 内文件 → 重启 App → **托管会话全灭**（对话在 transcript 无损，但进程全死、需逐个手动恢复）。团队模式的命脉是 relay，每迭代一次灭一次团不可接受 → 见"重启韧性"节
3. **心跳 ≠ 在干活 → watchdog 必须分层**：tag 会话"卡住"判定实录——心跳 5s 一跳很健康，但 action 标签是过期的（所跑命令早已返回），真死/滞留/思考中三种态单靠心跳分不清。看板成员状态三色：无心跳=死（红）；有心跳但 SESSION_LOG 停滞超阈值=滞留（黄，通知 leader 处置）；日志在流=正常（绿）。标签类展示（"正在执行X"）必须随 tool_result 即时失效
4. **内部产物进开源仓库 → 数据边界先立**：HANDOFF-72/74/75 曾被提交进开源仓库（含机器路径/内部流程），当晚清除。团队产物三类分置：开源仓库（产品代码 + 产品文档 docs/）、内部数据（~/.cc-deck/：板/身份模板/交接/events）、易失（/tmp）——见"数据边界"节
5. **手工交接 → 任务卡内嵌 handoff**：当晚一次真实交接 = 写自包含交接文档（现象/根因/修复选项/验收/部署流程）→ 用户转告路径 → 对方会话读文件接手，全程零考古、成功。这验证了"交接靠文件不靠会话记忆"，也说明任务卡应内嵌 `handoff` 字段承载这类说明，不再靠手工文件

## 数据边界与目录布局

| 类别 | 内容 | 位置 |
|---|---|---|
| 开源仓库 | 产品代码、产品文档（docs/*，如本文档与 mockup） | git |
| 内部数据 | 团队板快照、身份模板库、交接文档、events 流 | `~/.cc-deck/teams/<team-id>/`（board.json / spawn-record.json / identities/）+ `~/.cc-deck/handoffs/` |
| 易失 | 锁、临时产物 | /tmp |

收团归档：板转只读留存（审计价值），worktree 删除，spawn 记录清空；内部数据永不进 git（.gitignore 已挡 HANDOFF 类文件，团队数据同样不提交）。

## 重启韧性（M1 硬需求）

relay 重启杀全员是既成事实（进程拓扑：托管会话 = relay 子进程）。团队模式下必须补：

1. **spawn 记录持久化**：每次成员 spawn 记录 {身份、cwd、cli session_id、worktree 分支} → `spawn-record.json`
2. **relay 重启自动重建**：启动时读板 + spawn 记录，按记录逐个 SDK resume 拉起成员（对话在 transcript 无损），团队从"灭团"变"闪断"
3. **远期热更新**：bundle 换装不重启（新会话用新代码、旧会话自然收敛），彻底消除部署停机

## 风险与边界

### 战略层（做不做、做到什么程度）

1. **worker 可靠性决定一切**：会话层脆弱性（卡住/回落/状态不同步）不解决，团队模式把混乱放大 N 倍——M0 必须先行
2. **编排协议勿过度设计**：任务 = issue 式文本（改动面+验收点），完成 = 分支+汇报，从最糙协议开始
3. **不是所有任务值得并行**：强依赖链、需频繁用户拍板的任务串行更快；用户 review 带宽（只看效果）仍是最终瓶颈

### 运行期具体问题与预案（M1 实跑必撞的）

4. **审批风暴**（最可能先爆）：N 个成员各自触发 canUseTool，用户手机被审批轰炸，自己成了新瓶颈。预案：成员默认 `acceptEdits` + 文件域写进提示词（越域才升级审批）；看板页聚合审批（同类请求一条通知批量放行）；夜间开团提供"预授权到明早"选项
5. **会话容量挤占**：MAX_SESSIONS=20 / 保留 30，一个团 5-6 成员长跑会挤掉普通会话。预案：成员会话在 relay 内挂 team 标记单独计池，收团归档时连带清理（已列 relay 优化点）
6. **限额池烧穿**：5h 池若账号级共享，N 并发 = N 倍速消耗。预案：开团时按编制估耗、水位提示；leader 可挂起成员（挂起不烧额度）
7. **Leader 自身钝化**：即使汇报不流经 Leader，Leader 自己轮询读板也会累积上下文。预案：relay 读板接口默认返回 diff/摘要而非全量；Leader 长跑（如 >50 回合）提示用户换岗——接替 Leader 和接替 worker 同一套机制
8. **板与 git 漂移**：卡标 done 但分支没并、或合并冲突收不了场。预案：done 前置机械校验（分支存在 + scope 内 diff + 出包成功）；merge 冲突时卡转 blocked 状态回炉，不静默挂起
9. **worktree 磁盘与心智负担**：每成员一份全量工作区，仓库大了 ×N。预案：成员默认上限 4；收团即删；必要时浅克隆
10. **假死误判**：手机休眠、云桥断连不代表成员死了。预案：watchdog 只信 relay 本地双信号（心跳+日志），端上离线状态不参与判死（实现原理节已定）
11. **板写操作安全面**：board 是 relay 新攻击面。预案：COMMAND_BOARD_* 走既有鉴权信道（LAN token / 云 E2E），`/api/board/report` 等 HTTP 端点仅 localhost + token 双门禁
12. **异构模型纪律差异**：GLM/Claude 对"只动 scope 内文件"的遵守度不同。预案：不靠自觉，leader 合并时 `git diff --name-only` 机械对照 scope，越域即打回（纪律产品化的最后一道闸）
13. **用户在环堵车**：用户不确认装机，卡全堆在 ready_to_install。预案：notify.user 推送 + 看板常驻琥珀徽标；超 24h 未确认标"待确认"催办，但**永不自动 done**（用户在环是硬设计，宁可堵不可绕）
