## 0. 摘要与推荐

**先纠正一个前提**：org CLI 不是「本地文件工具」，而是 **localhost HTTP 客户端**（`bin/org:310` exec curl `http://127.0.0.1:${port}/api/org`）。真正的病根是**每台机器各跑一个 relay、org 域是 relay 本地文件**（`org.json`/projects/board/`dispatch-log.ndjson`/`experience.json`/`rules.json`），而 hook 与 CLI 的解析全部指向**本机** relay（hook 候选=本机 bridge.json 列表，`cc-bridge-hook.mjs`；CLI 缺省 `~/.cc-deck/data/bridge.json`）。所以「建团写到另一台机器」=「打到了另一台机器的 relay」。

**推荐方案（P1 主线）＝ A1「org CLI 远程直达」**：公司机通过**一次性云桥配对**成为家 relay 的 satellite peer，org CLI 检测到「本机不是 org 主权 relay」时，改调一个随 relay 物化的小型 node 助手，把 org 动作打成**既有的** `COMMAND_ORG_ACTION` 云桥密封帧直达家 relay 的 `orgCommand` 咽喉。家 relay 侧近乎零改动——云通道命令面（含 org 全动作）今天已通到咽喉，代码注释甚至预留了「未来连接级角色只换这里实参，咽喉零改」的扩展点（`commands/board-commands.ts:14-24`）。

**关键架构判断（本稿核心论点）**：org 命令面必须拆成三张面分别处理，不能一刀切路由——

| 面 | 归属 | 理由 |
|---|---|---|
| **记账面**（groups/编制/板/台账/经验/规则/status） | 路由到主权 relay | 纯数据，单一事实源 |
| **执行面**（spawn/注入/hook 事件/回执文件/artifacts 本体） | 留在发起机 | `dispatchWorker` 对锚目录 `statSync` + 本机 spawn（`session-manager.ts` dispatchWorker 头部），执行天然机器绑定 |
| **决议/授权面**（confirm-decide / auth-bypass） | confirm 永远用户端；**auth-bypass 落执行侧** | 授权位放行的是「该 relay 的 spawn 权限确认」，spawn 在哪台、授权位就在哪台 |

**dispatch 是唯一的记账+执行混合动作**，P1 不动它（P1 最小可用=建团+member-add 路由，按任务书口径），P1.5 用「两相位」（主权先闸后记账 → 发起机 spawn → 回绑 session_id）解决。

**同时强烈建议一件无论选哪条路都该做的事（P1.5）**：面板 org 域跨源聚合。今天面板会话域已跨源聚合（sid 为跨源主键，`expo-app/src/protocol.ts:412-413`），但 **org 域是 per-connection 的**（`expo-app/src/store.ts:107-110` `conn.projects`）——即使公司源连着，团队卡也只在该源视图下可见。这是「面板零变化」的一半根因，纯客户端可修。

## 1. 现状精读（证据链）

### 1.1 org CLI 与四个同病兄弟

`~/.cc-deck/bin/org`（310 行 bash，由 relay `ensureOrgCli` 物化升级，`org.ts:397,704`）：

- 端点解析：`CCR_DATA_DIR`（缺省 `~/.cc-deck/data`）→ `CCR_TOKEN` → `CCR_PORT`（缺省读 `bridge.json`，再缺省 8787）→ `exec curl POST 127.0.0.1:${port}/api/org?token=...`（`bin/org:40-44,310`）。
- 注释明说：Leader 会话由 relay spawn、经 childEnv 继承 `CCR_*`，沙盒 relay 拉起的会话自动打沙盒（`bin/org:37-39`）——**CLI 忠实于「离它最近的 relay」，没有任何跨机概念**。
- 同款 localhost-HTTP 形态的还有：`deliver`（`/api/deliver`，`bin/deliver:33`）、`acceptance`（`/acceptance-cloud/`，`bin/acceptance:83,116-117`）、`leader-dispatch`（拼 org dispatch 请求体后同路 POST）、`leader-harvest`。**验收交付链与 org 链是同一个病**，只是器官不同。

### 1.2 多源拓扑与「org 域不聚合」实锤

- 每机一个 relay（内嵌/服务化，`docs/design/relay-service-switch-design.md`），各自持有 `~/.cc-deck/org/`（组/板/台账/经验/规则）与 `~/.cc-deck/data/`。
- 云桥：relay 出站连桥（`CCR_CLOUD_URL`，公司网友好，`cloud-client.ts:106-109`），设备经配对入 `cloud-peers.json`（`cloud-identity.ts`），帧 E2E 密封按 dev 路由；CF worker 只有 `/cloud /cloud-poll /wan /view /dl /app` 面，**没有通用 HTTP 代理**（`cloudflare/src/worker.ts:338,444`）。
- 面板（expo）多源：会话域聚合（`protocol.ts:412-413`「sid 为 uuid 全局唯一，可作跨源主键」）；**org 域 per-conn**（`store.ts:107-110` `projects: ProjectGroup[] | null` 挂在 conn 上；`store.ts:622` `projects: c.projects`；`store.ts:2371-2380` SNAPSHOT 覆盖式重锚到 conn）。→ 用户看家源，公司源 org 永不可见，反之亦然。
- 会话归属：hook 只报本机（`cc-bridge-hook.mjs`：cfgs=本机各 data 目录的 bridge.json，403/连不上逐候选回退）。公司机会话只进公司 relay 的会话表。

### 1.3 云通道命令面：org 远程化的轨道已经铺好

- `COMMAND_TYPES` 白名单已含 `COMMAND_ORG_ACTION`/`COMMAND_ORG_CONFIRM`（`cloud-client.ts:74-76`），与 ws-server LAN 白名单逐字一致纪律（`cloud-client.ts:43-45`）。
- 云/LAN 两入口统一收口：`COMMAND_ORG_ACTION → mgr.orgCommand("owner", by, action, payload)`（`commands/board-commands.ts:14-28`），且注释预留角色分化点（「现连接面全部持主 token…角色统一记 owner；未来连接级角色（viewer 分享链接等）只换这里实参，咽喉零改」）。
- 咽喉：`orgCommand(actor, device, action, payload)` 先过 `evaluateCommandPermission(actor, "org:write")` 权限矩阵（owner/operator 均含 org:write，viewer 无，`org.ts:23-27` COMMAND_CAPABILITY_MATRIX），全程 `auditOrgCommand` 审计行落 append-only `dispatch-log.ndjson`（`session-manager.ts` auditOrgCommand 体，注释「审计不进 events.ndjson」）。exp-*/rule-* 已实证云面可通（board-commands 注释「LAN/cloud 两入口均已通该命令」）。
- 配对协议通用：pair_req（6 位码/空码在场信标）→ 桥把配对码定位广播转发给所有在线 rl- 设备（`cloud-bridge/src/router.ts:130-136`）→ relay grant 入 peers。浏览器/exe/手机都是这条道，**再来一个「设备」没有协议障碍**。

### 1.4 执行面与数据校验的机器绑定（路由的硬约束）

- `dispatchWorker`：anchor 必须绝对路径且 **`statSync` 在 relay 本机文件系统上验在/验目录**（「锚目录不存在/不是目录」错误即出自此处），随后本机 spawn worker。→ 记账与执行在同一个函数体里耦合。
- `orgCommand` case `create`（面板建团路径）：`pm_session_id` 必须**在本 relay 会话表在册**（「PM 会话 … 不在册（PM 需是已有会话卡）」；注释：「在册（**外部允许**——生产 PM 主会话即 ext- 外部会话…）」，`session-manager.ts:4819` 起约 40 行内）。→ **把建团整个路由到家里，PM 行会被「不在册」拒绝**，因为 PM 会话在公司机会话表里。
- 两个建团入口不同形：CLI `org create` → HTTP `project-create`（无 PM 行逻辑）；面板 → WS `create`（带 PM 行/编制，W-TEAMSNC「PM 卡团队 chip 点亮的数据链，数据缺口是唯一硬缺口」）。事故里公司会话走的是 CLI 面（聊天里自己报成功），所以公司在 org.json 里有的应是无 PM 行的裸组。
- HTTP 面白名单 `ORG_HTTP_ACTIONS`（`ws-server.ts:860-884`）刻意**排除决议类**（confirm-decide 只走用户端 WS）；新动作默认不放行。
- `member-add` 咽喉直通 orgAction，**无在册校验**（`session-manager.ts`：「member-retire|member-add|… 直通」；projects.ts:513「此处只做形状校验」）→ 跨机 sid 可入编，这是 P1 能落地的关键豁口。

### 1.5 广播/生效链现状（要「复用」的东西）

org 写动作单点广播：`emitOrgState()` → `PROJECTS_UPDATED`（groups+delta）+`ORG_CONFIRM_UPDATED`；`emitBoard(gid)` → 板帧差分（`session-manager.ts:6175-6188` 及 M13-2 注释）。EventBus 帧经 LAN ws 与 CloudClient E2E 双路下发全部已 hello 设备；SNAPSHOT 全量域含 `projects/experience/rules/acceptances/deliverables`（`cloud-client.ts:482-545`）。**即：只要写动作发生在主权 relay，三端团队卡即时生效，零新增广播机制**——这正是任务书说的「复用 RELAY_NAME_UPDATED 类广播」的同一条轨道。

## 2. 目标 / 非目标

**目标**：① 公司机（satellite）会话的 org 记账落在主权 relay（家），面板即时可见；② 本机会话行为逐字节不变；③ 决议权与安全边界不因远程化扩大；④ 离线行为明示；⑤ 给出九宫格全链路审计与分批。
**非目标**：P1 不做会话镜像/跨机 chip 完整体验（明示缺口与后续路径）；不做 org 数据双向同步；不改云桥 worker 转发协议主体。

## 4. 方案对比

### A1：org CLI 远程直达（org-remote 助手 + 云桥 COMMAND_ORG_ACTION）★推荐

satellite 机一次性配对为家 relay 的 peer（新角色 satellite），org CLI 在「本机≠org 主权」时改调 `org-remote.mjs`：短连桥 → 密封 `COMMAND_ORG_ACTION` → 家 relay 咽喉执行（审计+广播照旧）→ ack 回传打印。

- **优点**：家 relay 改动≈0（命令面已在，只加角色解析）；CLI 零协议知识（bash 只多一个分支 exec 助手）；与 relay 物化升级体系同轨（`ensureOrgCli` 一并管助手）；node 运行时随 relay 必然在机；对断线/超时可以做成一次性短连接，无常驻状态。
- **代价**：satellite 侧新增绑定文件+配对 UI 一次性动作+助手；CLI 输出从 HTTP 响应形变为 command ack 形（{command_id,ok,data|error}，消费方是 Claude 读 JSON，兼容）。
- **风险**：桥断=org 全断（离线降级 §5.8）；云桥 1MiB 帧限约束大载荷动作。

### A2：本地 relay 代理（satellite relay 配对 home，/api/org 透明转发）

CLI 完全不改；satellite relay 拿到 org-home 绑定后把本地 `/api/org` 转发到家的云通道。

- **优点**：CLI/体验零变；转发逻辑集中在 relay（升级走 relay 单源）。
- **代价/否决点**：① relay-to-relay 需要卫星 relay 以 peer 身份常驻云桥连接（状态机/重连/风暴治理全套搬一份）；② 本地 relay 必须在跑且版本新，否则行为不一致（旧 relay=旧病，静默）；③「本地 relay 替我做远程决定」让排障面翻倍（CLI↔本地 relay↔桥↔家 relay 四跳）。**结论：作为 A1 的退化变体记录，不取主线**。

### B：org 数据双写同步 —— 否决

- org 域不是无冲突数据：板卡状态机/编制闸/确认卡生命周期都有业务闸（「第四写口」教训：宣称单点共用的设计要逐入口核对，团队经验 pitfall）；双写=两边都成权威写者，冲突面=组状态迁移/确认卡决议/编制 cap 三处硬冲突。
- `dispatch-log.ndjson` 是 append-only 审计账（org.ts:8-10「走事件流会破坏 append-only 审计语义」同族理由），双写重放会伪造审计序。
- 先例：candidate 镜像双写者恒输震荡（团队经验 pitfall）。**否决**。

### C1：org 跟锚联邦（数据跟执行地，面板跨源聚合补可视）——哲学对照，列为拍板点

org 数据留在锚所在机器（执行地），不搬家；把面板 org 域改成跨源聚合（源角标区分），用户在聚合视图里同时看到家/公司两组团队。
- **优点**：零 RPC、零一致性风险，执行与数据同机（dispatch 不用拆相位）；改动全在客户端。
- **缺点**：无单一台账/经验库/熟手池（团队资产按机分裂，恰与「团队是产品能力」的 v8 方向相悖）；跨机协作（家里的 Leader 派公司的锚）仍无解。
- **定位**：它回答的是「看见」，没回答「统一」。即便采 A1，P1.5 的面板跨源聚合也要做（两者互补不互斥）。

### C2：完全主权化+会话镜像（P2+ 演进）

satellite 会话事件经轻量上报镜像到主权 relay（bounded：只镜像 dispatched sids 的生命周期里程碑），home 会话表含 origin 标记 → chip/螃蟹旗/值守/patrol 全链在主场闭环。代价：hook 通道改造+事件双落+去重。**P2+，不进 P1。**

### 对比矩阵

| 维度 | A1 直达 | A2 代理 | B 双写 | C1 联邦 | C2 镜像 |
|---|---|---|---|---|---|
| 家侧改动 | ≈0（角色解析） | ≈0 | 大（同步器） | 0 | 中（事件面） |
| satellite 侧改动 | 中（绑定+助手+CLI 分支） | 中（relay 转发） | 大 | 0（客户端在面板侧） | 大（hook/事件） |
| 单一事实源 | ✅ | ✅ | ❌ | ❌（按机分裂） | ✅ |
| dispatch 跨机 | P1.5 两相位 | 同 | 冲突 | 天然（本地全链） | ✅ |
| 断网可用性 | 硬失败明示 | 同 | 假可用（后裂） | ✅ 本机全链 | 降级 |
| 决议/安全收口 | ✅ 咽喉+新角色 | ✅ | ❌ | ✅ | ✅ |

**拍板建议**：P1=A1，P1.5=面板 org 跨源聚合（兼收 C1 的「看见」），P2=C2 按需演进。

## 5. A1 详细设计

### 5.1 身份与绑定（satellite 怎么知道家在哪）

新文件 `~/.cc-deck/data/org-home.json`（**放 data/ 不放 org/**：随 `CCR_DATA_DIR` 走，沙盒/多实例变体天然隔离，与 F-09 同款纪律）：

```json
{
  "home_relay_dev": "rl-xxxx",        // 家 relay 云身份（COMMAND_CLOUD_INFO 的 rd 可自查；配对成功时家侧回填确认）
  "bridge_urls": ["wss://cc.humumu.online/cloud"],
  "role": "satellite",
  "paired_at": 0, "last_ok_at": 0
}
```

- **解析优先级**（org CLI 开头）：`CCR_ORG_HOME=local|off` env（测试/显式逃生）＞ org-home.json ＞ 缺省=本机（**无绑定=行为逐字节不变**）。
- 绑定建立=一次性配对动作（见 5.2），由用户在场完成；解除=删文件+家侧踢 peer。

### 5.2 配对与角色

- 复用既有 pair_req 6 位码流：satellite 出码（或家侧面板「添加卫星机」出码、satellite 填码，方向择一，建议**家侧出码**——决议权在主场用户），桥转发给在线 rl-（router.ts:130-136 已有），家 relay grant 入 `cloud-peers.json`，meta `{app:"ccdeck-satellite", platform:...}`（PEER_META_KEYS 已有 app/platform 位）。
- 角色落地：`COMMAND_CAPABILITY_MATRIX` 增 `satellite: ["org:write", "artifact:read"]`；`board-commands.ts COMMAND_ORG_ACTION` 的 actor 实参由 peer meta 解析（`app==="ccdeck-satellite" → "satellite"`，其余维持 owner）——正是该处注释预留的「只换实参，咽喉零改」。
- **satellite 动作拒绝清单**（在 COMMAND_ORG_ACTION 入口按角色挡，错误文案明示）：`confirm-decide`（决议面）、`auth-bypass`（授权位属于执行侧，本来就不到家）、`create-with-pm`（PM 在册校验必然拒，先挡掉换友好文案指路 CLI 面）。其余 ORG_HTTP_ACTIONS 同集放行。可选 P2：per-peer `allowed_gids` 收窄。

### 5.3 传输与帧

- `org-remote.mjs`（node，随 `ensureOrgCli` 物化到 `~/.cc-deck/bin/`）：读 org-home.json + 卫星自身 device keypair（配对时生成的 `data/satellite-keypair.json`，dev 前缀建议 `st-`——见疑点⑥的前缀路由核对）→ 连桥 → sealed `COMMAND_ORG_ACTION {command_id: uuid, payload:{action,...}}` → 等 ack（超时 20s，dispatch 长动作 60s）→ 退出码映射（ok=0 / error=1 / 超时=2，附「云桥不通」文案）。
- 幂等：command_id 幂等键；dispatch 两相位用 (gid, entry_id|prompt-hash) 去重防双派。
- 逐次短连，不常驻：牺牲首连延迟换零状态机（桥连接握手开销 ~1s 级，org 操作频率可接受；重试 1 次）。

### 5.4 dispatch 两相位（P1.5）

```
satellite CLI org dispatch
 └─相位①（主权闸+记账）：COMMAND_ORG_ACTION dispatch {anchor_attest:{path,relay_dev}, exec_relay:"st-..", prompt,...}
     家 relay：跳过本机 statSync（exec_relay≠self 时以 anchor_attest 为准）
              → 编制 cap/依赖 gate/建卡/台账 queued → ACK {dispatch_id}
 └─相位②（发起机执行）：本地 relay HTTP（既有本地口）spawn with dispatch_id
     → 成功：COMMAND_ORG_ACTION dispatch-bind {dispatch_id, session_id} → 台账 dispatched+编制挂 sid+emitBoard
     → 失败：dispatch-fail {dispatch_id, reason} → 台账 failed（不产生孤儿在办）
```

- 顺序必须是**先记后 spawn**：与「编排 blocked 零 spawn」闸序一致，cap 在主权侧单一执行点强制，杜绝先斩后奏绕编制。
- 崩溃夹缝（①成功②未回报）：台账停在 queued，家侧值守/patrol 的 hanging 检测既有机制天然可见（leader-duty DutyDispatchCandidate 有 dispatched/hanging 态）——不是新死角。
- spawn 的 prompt 注入仍由本地 relay 完成（执行面不动）；板卡文本继续走 normalizeBoardCardText 单口（家 relay 内建，天然单点）。

### 5.5 PM 行 / chip / Leader 旗的跨机语义

- P1 事实：CLI 面建团（project-create）+member-add 都无在册校验 → 跨机建团/入编可用；但**团队 chip/螃蟹旗需要「会话卡 ↔ 编制 sid」匹配**，会话在公司源，家源 org 视图匹配不到 → P1 缺口**明示**：面板须连着公司源，且需 P1.5 org 跨源聚合后按 sid 跨源匹配（sid 跨源主键已成立，protocol.ts:412-413）。
- P2（C2 方向）：`create`/PM 行允许 `origin_relay`+sid 按「外部身份」挂账（咽喉已有 ext- 外部会话先例注释）；collab-mode 的 leader_session_id 同理携带 origin；SNAPSHOT sessions 端补 origin 角标即可在家源点亮 chip。
- PM 选举/值守：leaderId 是会话 id（`session-manager.ts:688`），值守 feed 消费家侧事件流——satellite worker 的静默在家侧不可见（P1 缺口），P2 用「dispatched sids 生命周期里程碑镜像」补（只镜像 dispatch 相关事件，bounded，避免全量事件双落）。

### 5.6 锚点跨平台（anchor_bindings）

- group 增可选 `anchor_bindings: { "<relay_dev>": "<本机绝对路径>" }`；canonical `anchor_dir` 仍是主权侧原值。
- project-create/dispatch 路由时 satellite 上报本机锚（绝对路径，win32/posix 由既有 `anchorPathError` 宿主判定单点 #260 校验），家侧存 binding；gid 派单时 satellite 用自己的 binding 解析锚（组内取锚 `g.anchor_dir` 的既有逻辑增加 per-relay 解析层）。
- 同一仓库两机两路径（`/Users/xdd/dev/cc-deck` vs `C:\dev\cc-deck`）由 binding 表显式对齐，不做启发式猜测。

### 5.7 生效链（建团成功 → 三端可见）

写动作落在家里 → 咽喉内 `emitOrgState()/emitBoard()` 单点既有广播 → LAN ws + CloudClient E2E 到全部已 hello 设备 → 家源面板团队卡即时刷新；PROJECTS_UPDATED/ORG_CONFIRM_UPDATED 帧已是三端同构消费。**零新增广播机制**。team-chip/头像旗的最后一公里=会话域匹配（§5.5），P1 明示缺口。

### 5.8 离线降级（云桥断）

- **默认硬失败**：`org-remote` 超时/桥不可达 → exit 2 + 文案「org 主权在 <rl-xxx>（家），云桥不通，命令未执行——修复网络或在主场机器操作」。宁断不裂：静默回落本地=复刻本次事故。
- 显式逃生 `org <cmd> --local`（P2 再议）：建「本地孤岛」组带 `origin:"stray"` 标记，**永不与主权自动合并**（合并必须人工迁批，org 导出/导入工具先行——experience 已有 export/import 先例可仿）。
- 桥断期间主场面板一切照旧（家 relay 与桥的断连治理是 #268 已修域，不属本设计）。

### 5.9 安全边界（远程设备能操作家 org 到什么程度）

| 能力 | satellite | 依据 |
|---|---|---|
| 读 status/detail/board/经验/规则 | ✅ | artifact:read 同级 |

## 8. 关键疑点清单（呈 PM/拍板）

1. **裁定语义二义（最重要）**：「org 落在会话所属 relay」——「所属」按**主权**（家，本稿采信）还是按**锚/执行地**（C1 哲学）？若用户要的是 C1（数据不搬家、面板聚合看见即可），P1 工作量砍半且无 RPC。建议拍板表二选一呈用户。
2. **member-add 无在册校验**是我 P1 可行的支点之一，仅核到「咽喉直通+形状校验」两级（projects.ts:513）；实施批须复核 member-add 全链确无 sessions.get 依赖。
3. **事故现场归因待证**：公司机 org.json 里新组是否带 PM 行、`org create` 走的 CLI 面（project-create）——决定 chip 缺口归因于「数据没到」还是「PM 行链路本就缺」。PM 已实锤侧可查证。
4. **dev 前缀路由**：桥 router 有 rl- 特判（广播/定位）；satellite 用 `st-` 前缀是否被 pair 定位广播覆盖、有无被当 relay 的误路由——实施前核对 `cloud-bridge/src/router.ts` 全文（本稿只读了 grep 断面）。
5. **面板 org 跨源聚合是否已有排期**：#294 只做了会话域；org 域聚合涉及 OrgZone/团队详情数据源切换（OrgZone.tsx 有「数据不在此聚合」注释），工作量独立评估。
6. **org-remote 助手的物化归属**：进 ensureOrgCli 单源（推荐）还是独立 bin？涉及 relay 升级联动。
7. **exp-import（≤5MB）vs 云桥 1MiB 帧限**：远程导入需分帧协议或「本地导入+文件传家」旁路；P1 不含 exp 路由可绕开，P2 前必须定。
8. **多桥落点**：cloudUrls 多桥时 satellite 连接落点与家 relay 在线桥的会合（家换桥落点时 satellite 跟随重连的语义）——#268 判死直排重连机制是否复用，实施批核对。
