# PRD：PM 权限自由度（Freedom Levels）

> 状态：草案 v0.1（待用户拍板决策点 §11）｜提出：2026-10-29（用户产品想法固化）｜归属：cc-deck relay 组织面
> 用户原话要点（1029）：团队成员不应出现需用户审批的事；审批由 PM 消化或 PM 询问；**用户可设权限自由度档位**——PM 依自由度决定自行拍板 vs 升级用户审批（不止审批：其他决策类问题同理 PM 依自由度自处理或上呈）。
> 载体约定：本 PRD 即该想法的固化载体（用户要求「千万不要丢失，过两天要能找出」；PM 侧另有 memory 锚双保险）。

## 1. 背景与问题

**现状**：团队决策类事件（建团/升降级/规则变更/放行确认卡……）最终都要用户 ✓ 确认卡——用户成为组织运转的串行瓶颈。P81 之后工具权限面（bypassPermissions 物化）已经解决「worker 跑工具要不要点确认」，但**组织决策面**（这类事该不该做、要不要花钱、能不能扩编）仍是全上呈模型：PM 只提案（`orgAction rule-append` 缺省出卡、`suggest-hold`/`tier-change` 全走确认卡），用户不在场团队就停摆。

**矛盾**：用户既不想被琐事轰炸，又不能对「删生产数据/发正式版/改安全闸」这类事失控。缺的不是全开或全关，而是**可分档的授权梯度**——把「用户信任 PM 的程度」变成显式配置，PM 在梯度内自主路由：能拍板的拍板（留痕），该上呈的上呈（复用既有确认卡通道）。

**非目标**（防范围蔓延）：
- 不改 worker 会话的工具权限面（P81 evaluatePermission 体系语义零变——两层正交，见 §2）。
- 不做「PM 代替用户按安全闸」（auth-bypass on/off、调档本身恒为用户本人动作，红线不随档位放宽，见 §8）。
- 不做细粒度 ACL/资源级权限（那是权限系统，本 PRD 是**决策路由系统**）。

## 2. 核心概念与定位：两层正交

```
┌─ 层A：工具执行面（P81 既有，不改）─────────────────────────┐
│ 「这个会话跑 Bash/写文件要不要弹权限确认」                    │
│ 主体=会话（worker/PM）；开关=勾选跳过+role×env 闸+auth-bypass │
└──────────────────────────────────────────────┘
┌─ 层B：组织决策面（本 PRD 新增）────────────────┐
│ 「这类组织决策（花钱/扩编/发版/删数据/改规则）谁拍板」  │
│ 主体=PM；开关=组级自由度档位；路由=PM 自决(留痕) or 上呈│
└──────────────────────────────────────────────┘
```

- 层A 解决「干活卡不卡」；层B 解决「决策等不等用户」。PM 在层B 拍板「可以干」之后，具体会话在层A 仍按 P81 物化权限跑——两层互不越权。
- 交点只有一处：**层B 的拍板不得改层A 的安全闸**（auth-bypass、自由度档位本身、kill-switch 类），此交点恒上呈且用户本人执行（§8 红线）。

## 3. 档位定义（Freedom Levels）

四档，从最保守到最放权。语义锚：**档位定义的是「上呈面的大小」，不是「PM 能力的大小」**——所有档位下 PM 能做的事完全一样（提案/派单/收口），差别只在决策类事件是否需要用户确认卡。

| 档位 | 名 | 一句话语义 | 上呈面 |
|---|---|---|---|
| **F0** | 全上呈 | PM 是纯提案机+路由器，零拍板 | 全部决策类 |
| **F1** | 关键上呈 | 仅明确低危类 PM 代决，中危以上全上呈 | 中危+高危+红线 |
| **F2** | 日常自决+大事上呈 | 低中危 PM 代决，高危（不可逆/大额）上呈 | 高危+红线 |
| **F3** | 全放权 | 除红线外全部 PM 代决，仅事后审计+翻案兜底 | 红线（+可配高危） |

- **缺省=F0**（新组最保守，验收点3）：未配置 = 现状行为逐字节不变（全上呈），本 PRD 上线零行为波及。
- 档位**组级**配置（`ProjectGroup` 增 `freedom_level?: "F0"|"F1"|"F2"|"F3"`，缺席=F0 fail-closed；词表外值写入即拒，team-rules audience 同款范式）+ 全局缺省档（`plugin-config` 第十一键 `freedomDefault`，缺省 "F0"，供存量组统一调）——作用域拍板项见 §11-D1。

## 4. 档位 × 事件类矩阵（验收点2）

事件分类法：按**可逆性 × 影响半径**分三档危级，六类事件（用户点名的六类全覆盖）+ 恒红线行。

**危级定义**：
- 低危=可逆、组内（错了能撤，损失限本组）
- 中危=可逆、跨面（错了能撤但波及多组/外部可见）
- 高危=不可逆或大额（错了撤不回，或花钱超限）

| # | 事件类 | 危级 | F0 全上呈 | F1 关键上呈 | F2 日常自决+大事上呈 | F3 全放权 |
|---|---|---|---|---|---|---|
| E1 | Bash/工具权限（worker 例行工具面预授权范围内的放行类确认） | 低 | 上呈 | **PM 自决** | **PM 自决** | **PM 自决** |
| E2 | 费用预算（额度内：组预算窗/常规 API 花销） | 低 | 上呈 | **PM 自决** | **PM 自决** | **PM 自决** |
| E3 | 费用预算（超组额度/单笔大额——阈值见 §11-D5） | 高 | 上呈 | 上呈 | 上呈 | **PM 自决**（双留痕+即时通知） |
| E4 | 发版（test/snapshot 通道 tag+出包） | 中 | 上呈 | **PM 自决** | **PM 自决** | **PM 自决** |
| E5 | 发版（正式版 Release+latest.json 清单） | 高 | 上呈 | 上呈 | 上呈 | **PM 自决**（双留痕+即时通知） |
| E6 | 删数据（可恢复：归档/软删/清理临时物） | 低 | 上呈 | **PM 自决** | **PM 自决** | **PM 自决** |
| E7 | 删数据（不可恢复：rm 生产数据/清账本/删验收档案） | 高 | 上呈 | 上呈 | 上呈 | 上呈（**§11-D2 拍板：F3 是否例外放行+break-glass**） |
| E8 | 新成员（编制内 headcount 增减、member-add/retire） | 中 | 上呈 | 上呈（**§11-D3 可调为自决**） | **PM 自决** | **PM 自决** |
| E9 | 规则变更（rule append/retire/supersede、tier-change 升降级） | 中 | 上呈 | 上呈 | **PM 自决**（数值硬闸仍全拦，§6.2） | **PM 自决** |
| R1 | 安全闸红线：auth-bypass on/off、自由度调档、kill-switch（duty/patrol 等总闸）、生产 bypass 授权位 | 红线 | 上呈·**用户本人** | 上呈·用户本人 | 上呈·用户本人 | 上呈·**用户本人** |

矩阵读法：**F1/F2/F3 从左到右只是逐步把「上呈」换成「PM 自决」；红线行永不换**。E7 在默认方案下四档全上呈（不可逆生产删除不设 PM 代决口，除非 §11-D2 拍板加 break-glass）。

## 5. 路由规则表（PM 侧判定流程）

**判定流程**（PM 收到/产生决策类事件时）：

```
决策事件 → 事件归类（E1-E9/R1，归类不确定=就高不就低）
  → 查组 freedom_level → 矩阵单元格
     ├─ "PM 自决" → PM 拍板（§5.1 拍板协议：审计+通知，不弹确认卡）
     ├─ "上呈"     → 既有确认卡通道（OrgConfirm 出卡 + decision-notify 通知 + 手机远程审批）
     └─ "上呈·用户本人" → 确认卡 + 提示语注明「安全闸须用户终端执行」（P81 分类器拦 PM 代按，语义对齐）
```

**5.1 PM 拍板协议**（自决路径的仪式，全部既有面复用）：
1. **拍板动作**=`orgAction confirm-decide` 通道代决：决策类事件仍**先出确认卡**（OrgConfirm 形状不变，审计权威），档位允许时 PM 以 `decided_by: "pm:<session_id>"` 决议（approve/reject 走 applyConfirmEffects 既有副作用链）——**卡不省略，省略的是等用户**。这样决策事实、理由、载荷天然进 confirms.json append-only 账。
2. **拍板即留痕三面**：①确认卡 `decided_by` 字段（谁拍的）；②chain-audit 新事件 `pm-decision`（actor/gid/事件类/档位/决议/理由一句，events.ndjson 持久）；③通知账一行（group=activity，用户事后翻得着：「PM 已代决：×××（F2·E9）」——对齐 dispatch done 通知先例）。
3. **高危代决加料**（E3/E5 的 F3 档）：拍板即时通知升级 severity=waiting+group=attention（不是事后翻账，是当下手机弹「PM 刚替你放行了一笔大额/正式发版」）。

**5.2 归类细则**（防归类歧义）：
- 事件不在 E1-E9 词表 → **就高归入上呈**（fail-closed，未知决策不猜）。
- 一个动作跨多类（如「删数据+发版」的清仓重发）→ 取最严单元格。
- 归类权在 relay 侧判定函数（纯函数 `routeDecision(eventClass, freedomLevel)`，单测锁定矩阵全表），PM 提案时附事件类自报，relay 复核——**PM 自报不足以放行，relay 判定才是权威**（防注入伪造低危标签，§9 安全面）。

## 6. 与既有基建整合

**6.1 P81 权限面（permission-policy.ts）**：正交不动（§2）。唯一接线：`pm-decision` 审计行的 `event_class` 沿用 P81 的 env/dir_scope 词汇描述上下文；E1 类（worker 工具放行确认）在 F1+ 档由 PM 代决=既有 `gate-release` 审计的 actor 从「系统代填勾选」升级为「PM 拍板」，audit 面向后兼容（新增字段不删旧字段）。

**6.2 团队规则库（team-rules.ts）**：**数值硬闸×4 与 sanitize 全量保留，不随档位放宽**（形状/去重/数量/注入预算是结构性约束不是决策——F3 也不能往满库塞规则）。档位只改「入库前的确认卡路由」：F0/F1 时 `rule-append` 卡等用户（现状）；F2/F3 时 PM 代决（`created_by: "agent"` 语义不变，`confirm_id` 回链由 PM 决议产生）。规则文本仍全量过 sanitizeExperienceText（防注入面不降级）。

**6.3 确认卡+远程审批（decision-notify.ts / OrgConfirm / confirm-decide）**：完全复用，零新通道。上呈路径=现状（卡+通知五类+手机 ✓，test.54 已验）；代决路径=同卡不同决议人（§5.1）。`approval-timeout` 另单在修的超时基础与本 PRD 正交（超时后卡去向：F0=搁置提醒用户，F2+=可配「超时视为 PM 可代决」——§11-D6 待拍板，默认不开）。

**6.4 值守链（leader-duty/feedPM）**：PM 代决事件计入 duty 快照的候选面（待验收回执/待决议卡）——F0 下「用户不 ✓ 卡堆积」本身就是 duty 唤醒 PM 的场景（PM 收卡后该催用户或建议调档，见 §9 产品面信任环）。

## 7. 审计面（PM 拍板全留痕，验收点1）

| 面 | 内容 | 查处 |
|---|---|---|
| confirms.json | 每次代决的完整卡（kind/payload/reason/decided_by=pm:xx/decided_at） | append-only，重启回放 |
| events.ndjson | `pm-decision` 事件（actor/gid/event_class/freedom/resolution/reason） | chain-audit 既有查询面 |
| notifications.json | 「PM 已代决」通知行（高危=attention 即时弹） | 通知账三端 |
| org status 展示 | 当前档位+近 7 天 PM 拍板数/翻案数 | `pmDutyStatus` 同族扩展 |

翻案（用户事后否决 PM 拍板）：`confirm-revert` 动作（新）——决议可逆类（E4/E8/E9 等）执行回滚副作用（既有 applyConfirmEffects 的反向边），不可逆类仅记 `reverted: true` 败笔账（翻案率进 §9 信任环统计）。翻案不改历史行（append-only 哲学，追加反向行）。

## 8. 默认档安全与红线（验收点3）

1. **缺省 F0**：字段缺席/词表外/坏 JSON 一律 F0（fail-closed），上线日全组织行为零变化。
2. **调档恒用户本人**：`freedom_level` 写入口仅两个——用户 CLI（`org freedom set <gid> <档>`）与三端设置面（走用户确认卡）；PM/agent 的 orgAction **不注册** freedom-set 动作（提案可以：PM 建议「该组可升 F2」→ 出卡，用户 ✓ 才落）。防注入调档的第一道闸（§9）。
3. **红线行不可档位化**：R1 四类（安全闸/调档/kill-switch/生产 bypass 授权位）在矩阵层硬编码为「上呈·用户本人」，实现上不进矩阵表——路由函数遇 R1 类直接 return 上呈，档位参数不参与（结构性防绕过，不是配置防）。
4. **降档即时生效，升档次回合生效**：降档（放权→收权）立即；升档（收权→放权）在下一个确认卡周期生效（防「注入 PM 先骗升档再滥拍」的连续攻击窗）——升档本身是 R1 用户动作，此条是纵深（§11-D7 可拍板简化）。
5. **全局 kill-switch**：plugin-config 新键 `freedomEnabled`（缺省 true？——**缺省 false 更稳**：整功能未启用时一切照 F0，用户显式开总闸后才可调档。拍板项 §11-D8）。

## 9. 三路审查视角预埋（验收点4）

**A 路·安全反方（PM 被注入后滥权面）**——档位是权限放大器，攻击模型：
- 注入 PM → 诱导连续代决高危（E3 大额/E5 发版）：防线=①高危代决即时 attention 通知（用户秒级可见）②单窗代决频次告警（如 1h 内 ≥N 次高危代决 → 自动降档 F0+通知，**熔断**）③E7 不可逆删除默认四档全上呈。
- 注入 PM → 伪造事件归类（把 E5 报成 E4）：防线=归类权威在 relay 纯函数（§5.2），PM 自报仅参考；动作特征（tag 名/金额/路径）由 relay 从 payload 复核。
- 注入 PM → 建议用户升档话术：防线=调档是确认卡+用户本人（§8.2），卡文案固定模板（不透传 PM 自由文本进调档卡 reason——只带结构化字段，防话术操纵）。
- 待审查项：熔断阈值 N 与窗口、attention 通知轰炸上限。

**B 路·产品（用户信任曲线）**：自由度不是一次设定，是反馈环——
- 信任升：连续 X 天零翻案+决策量稳定 → 通知建议「该组可考虑升档」（用户拍板）。
- 信任降：翻案率超阈（如 7 天 >20%）→ 建议降档；熔断触发=强制降档。
- 曲线冷启动：新组 F0 起步，PM 拍板统计积累后才可见升档建议（不给新组直接放权的捷径）。
- 待审查项：阈值合理性、建议通知频率（防反向轰炸）。

**C 路·实现成本/回归面**：改动面枚举=projects.ts（字段+词表校验）、session-manager orgAction（freedom-set/confirm-revert 两个新动作+白名单）、路由纯函数新件+矩阵全表单测、decision-notify（高危代决 attention 升级）、confirm-decide 漏斗（decided_by=pm 通道）、通知文案、org CLI 两子命令、三端设置面（M3 再上）。回归风险集中点=confirm-decide 漏斗（既有用户决议路径零变：decided_by 缺省仍=user 面，PM 通道是显式新入口不共线）。
