## 〇、结论速览

1. **回归轮**：两轮人工串的 12 步里，8 步已是脚本或纯机械可执行——缺的不是零件，是**串联器＋回归清单单源**。推荐立 **L1**（一键 `regression-round.sh` 串「出包→快照→换装→立验→定向回归→回执骨架」），单轮人工时长从大半天压到 ~30min；**L2**（改动面→回归面映射自动生成清单）随后；**L3**（换装后自动回填验收账）挂验收拍板结果。
2. **验收循环**：A/B 两版并呈，**PM 推荐 A 版**（验收单退役→装机探针＋口头确认入账）——依据：23 张 pending 仅 1 张回流〔数据支撑〕、用户装机请求 160 次但表单回填 1 次的行为错配〔数据支撑〕、DEV-33 已示范零表单替代闭环（五单结论记 issue）。B 版（TTL 化）为保守备选：止血压不住根因——机制继续存在就继续产生 pending。
3. **与 DEV-43 三哨的衔接定位**：**轮次=定向触发面（一次性、深验证），哨兵=常态观测面（持续、浅验证）**。轮末把「观察面判定」项移交哨兵清单——这是 DEV-33 回执里已有的人工判断（R6/R11/R12/R13 判「观察面，长期复发监控归 patrol」），本设计把它机制化。

## 二、自动化分级 L0→L3

### L0 全人工（现状）

- 成本：如上，大半天/轮；步骤散落在任务书+回执里，无单源，每轮 PM 重新拼。
- 依赖：无。
- 问题：①步骤无单源（两轮回执各写各的，口径已见漂移——test.37 七步 vs test.38 五步段）；②换装窗口虽仅 7s 但前后散命令链长；③回归清单靠现场读台账拼，漏项无守卫。

### L1 一键脚本串〔推荐立即立项〕

**形态**：`scripts/regression-round.sh <版本号> [--from-tag <上个装机tag>]`，沿 release-test.sh 的「顺序锁死＋守卫不绿不动」纪律。

| 段 | 内容 | 来源 |
|---|---|---|
| P0 前置自检 | dev 净树（release-test 已检）＋磁盘余量（disk-watchdog 同款阈值）＋哨兵三件在位断言（`launchctl list` 含 relay-sentinel/patrol/disk-watchdog）＋version-sentinel 陈账核对 | 新增，薄 |
| P1 出包 | 直接调 `release-test.sh`（不重造）＋CI 等绿（tag 触发的三 workflow，gh run watch） | 已有 |
| P2 快照落盘 | 指纹/health/org 锚/cloud-peers 数 → `artifacts/round-<ver>-snapshot.json`（轮末对账用） | 散命令收编 |
| P3 预检 | dmg 内嵌 sqlite dlopen+建表往返（ABI 闸的装机侧补网） | DEV-33 手跑命令收编 |
| P4 换装 | `swap-nova.sh --dry-run` → 实换；**换装窗哨兵 pause 纪律**（见 §四） | 已有 |
| P5 立验断言组 | 全机械断言：三处版本指纹一致＝<版本>／launchd 三件 exit=0／`/api/wakeup` 200＋装配日志行／sqlite 读面零 NODE_MODULE_VERSION 降级行／设备回连计数 ≥ 快照值 | test.37/38 两轮回执的「立验」段逐条提炼 |
| P6 定向回归 | 读**单源清单** `docs/operations/regression-checklist.md` → 逐项执行：探针项跑 relay/probes 对应脚本产出行式结果；UI 机器检查项跑既有 harness；观感项自动标「留用户一眼」；手机端项自动标「留用户」 | 清单单源化＋探针收编 |
| P7 回执骨架 | 生成 md：回归表（项/探针/输出/判定建议）＋快照对账＋回滚位（swap 备份路径自动登记）＋留用户项清单 | 新增 |

**退出码语义矩阵**（沿 swap-nova 纪律，调用方按码决定不吞）：

| 失败点 | 动作 |
|---|---|
| P0-P3（未动生产） | 停，报因，零残留 |
| P4 换装失败（exit 4） | 停＋提示回滚位；**哨兵 pause 不解除**——哨接管复活重试（§四） |
| P4 换装成功但立验未绿（exit 3） | 停＋报警；pause 保持，交哨兵重试窗口；超窗人工 |
| P5/P6 断言红 | 换装不回滚（包是好的，回归项红≠换装失败），逐项记「不过」进回执，转修复单流程 |
| 全绿 | 回执骨架落盘，人只做判定确认＋留用户分流 |

- **成本**：1-2 批（约 300 行 shell/mjs＋探针收编）〔PM 推断〕；单轮人工大半天 → ~30min（盯输出＋判定＋分流）。
- **依赖就绪表**：release-test.sh ✓／swap-nova.sh ✓／relay/probes 探针（部分，缺的随批补）✓／launchd 三件（DEV-43 已装，2026-11-28 实存）✓／CI 三 workflow ✓——**零新增外部依赖**。
- **验收标准**：①test.39/40 连续两轮全程经脚本走完、零人工补步；②每包 release note 的回归表由 P7 直供——即产品报告 P0-1 验收标准「每个 test 包 release note 含回归表」的供数通道；③快照对账 100% 可回放。

### L2 回归清单自动生成（「改动面→回归面」映射）

- **映射表**：改动面（文件/目录/ci.json 键族）→ 回归面（R 系项/probe 脚本/CI 键/哨兵观察项）。数据源＝`git diff <上个装机tag>..<本tag>` × 映射表 → 自动算出本包回归清单。
- **冷启动**：DEV-33/56 两轮回执就是标注数据——R1↔web-console 卡序、R6↔状态灯 css、wakeup 链↔relay/src/wakeup 面等，反填即得首版映射表〔PM 推断〕。
- **成本**：L1 落地后 1 批；映射表是活资产，每轮回执回填（漏项即新增映射行）。
- **验收标准**：连续三轮，自动清单 vs PM 人工清单 diff 为「只多不少」（宁可多跑，不许漏）。

### L3 换装后自动回填验收账

- A 版（验收退役）下：P7 回执直接推进 feedback-ledger 行状态（「已修待验」→「装机回归过/留用户」），口头确认再推进到「用户已确认」。
- B 版（TTL 化）下：P7 代填 results 或触发 TTL 计时。
- **成本**：小（L1 记账段的延伸）；**依赖：验收循环拍板（§三）**。

### 推荐档位

| 档 | 时机 | 理由 |
|---|---|---|
| L1 | **立即**（S2-W5 可派，56/42 收口后） | 零新依赖；两轮痛点全在串联缺失；第三轮（test.39 起）就该吃到 |
| L2 | L1 后 1 批 | 映射表需 L1 的清单单源先立；冷启动数据已有 |
| L3 | 随验收拍板 | 拍 A/B 决定回填目标 |

## 三、验收循环重设计（两版并呈，〔待确认〕＝决策#3）

### 3.1 机制现状与死亡证据

**机制现状**：`~/.cc-deck/bin/acceptance <验收单.md>` 解析四段结构（标题/前置说明/表格前三列=任务号+验收项+通过标准/备注）→ 落 `data/acceptances/<id>.json` → 吐云表单链接（per-sheet 密钥走 KV＋fragment 携带，防伪造关单——#28 云通道密钥）→ 用户浏览器点选提交 → `<id>.results.json` → relay 拉回。relay 侧 `relay/src/acceptance.ts` 承载 API 面。机制工程质量不低；死因不在工程。

**死亡证据**：

- 23 张 pending 仅 1 张回流，最老挂 29 天（10-29 test.74 起）〔数据支撑：DL-P1-3；2026-11-28 复核目录仍 23+1，另有 archived-20261029 前科——物理归档 28 张死账后又攒 23 张〕。
- 用户行为实锤：两月装机请求 **160 次** vs 表单回填 **1 次**——用户在意装机（高频要链接），但不填表〔数据支撑：产品报告附录 A 计数〕。用户实践=实时口头反馈不回填（DL-P1-3 定性原话）。
- 「『以后不会再积』这种话你跟我说过一百次了」（11-12 转录〔用户明示〕）——积压承诺已透支。
- **替代路径已示范**：DEV-33 轮五张 in_review 单（DEV-21/24/29/30/31）装机结论全部记到各自 issue，「过/留用户」零表单零积压〔数据支撑：DEV-36 父单夜批收口注记〕。

### 3.2 A 版：验收单退役 → 装机探针＋口头确认（PM 推荐）

**用户侧体验流程（文字版）**：

```
新 test 包出（L1 轮次自动跑完）
  → 手机/桌面收到推送：一页「本包含哪些修复 + 回归结论 + ≤5 项留用户一眼清单」
      （推送腿=DEV-43 云桥直推 bridge_alert，待手机 App 更新生效〔数据支撑：DEV-56 任务书〕）
  → 装机自动更新（桌面在线更新/手机应用内更新）
  → 装机后 24h 内：R 系自动探针跑一轮，结论入账（机器代验）
  → 用户日常使用；有问题随口说（聊天/口头）
  → PM 当场入账 feedback-ledger：报什么/修到哪/验没验 三态，来源标「用户原话+日期」
  → 修复合入下个包 → 循环
```

**用户要做的：什么都不填。** 唯一动作=用；有问题说话。

- **探针面**：装机后 24h 探针轮＝L1 的 P6 清单降档重跑（只跑机器项），结论自动写回账本。
- **漏验风险与兜底**：UI 观感类（六芒星闪动感/布局微失调）探针盖不全 → 兜底＝UI 机器检查 harness（DEV-33 已 24 项）＋截图留档＋「留用户一眼」清单每包 ≤5 项推送点名（有名单有触达，不靠用户翻台账）。
- **入账纪律**：口头确认无表单痕迹 → 回执每条标来源（探针名/用户原话+日期），可追溯性靠账本行不靠表单。
- **两账收向**：feedback-ledger 为唯一闭环账本（P0-4 原文「两账合一」方向），defect-ledger 收敛为结构性问题台账，R 系行状态由 L1-P7/探针轮自动推进。

### 3.3 B 版：验收单 TTL 化（保守备选）

**用户侧体验流程（文字版）**：

```
同 A 版：出包 → 推送 → 装机 → 探针轮
  → 验收单照出，但带 TTL（默认 72h〔待确认：时长〕）
  → 到期未回填：探针结论代填＋标「TTL 闭环」自动关单
  → 用户事后否决任一项 → 重开该行为修复单（否决通道永在）
```

- **落点**：`relay/src/acceptance.ts` 加 TTL 腿（DL-P1-3 台账原话：「验收单 TTL 改 acceptance.ts（relay 面）若做须挪批 A」）＋出单工具带过期位。
- **保留的优势**：表单式回收的形式感＋逐项「通过标准」颗粒度——对 UI 大批（一次十几项观感判定）有价值。
- **代价**：比 A 版多一个机制的永久维护面；且 TTL 只是止血不是对因——机制继续存在就继续产生 pending 噪声（duty feed 被滚爆的下游症状可能复发）〔PM 推断〕。
- **成本**：一批（acceptance.ts+工具+TTL 扫描腿），高于 A 版（A 版的探针轮在 L1 里本来就要做）。

### 3.4 对比表＋推荐

| 维度 | A 版（退役） | B 版（TTL 化） |
|---|---|---|
| 用户负担 | **零填表** | 到期前仍可填（不填也能自动关） |
| 漏验风险 | 观感面靠「留用户一眼」清单＋harness 兜底 | 最低（逐项 criteria＋到期代填） |
| 机制维护面 | 最小（账本+探针，均已有） | 多一套表单+TTL 扫描 |
| pending 噪声 | 根除（无 pending 概念） | 压制（TTL 兜底但机制仍产单） |
| 数据痕迹 | 账本行标来源（探针/原话+日期） | 表单结构化（更强） |
| 工程 | 复用 L1，近零增量 | 一批 |
| 历史包袱 | 24 张死账需归档〔待确认〕 | 可被 TTL 自动清 |

**PM 推荐 A 版**：数据（1/23 回流）＋用户行为（160 vs 1）＋DEV-33 替代闭环已跑通＋维护面最小。B 版的唯一实质优势（颗粒度形式感）可以保留在「装机探针清单」里——criteria 进探针断言，不需要用户填表来承载〔PM 推断〕。**两版差异的本质**：B 版赌「机制修好用户就会用」，A 版承认「用户行为已经投票，产品迁就行为」。

### 3.5 A 版配套项（若拍 A）

1. 24 张历史验收单归档（`archived-<日期>/`，先例 archived-20261029）〔待确认〕。
2. `/acceptance` 出单命令退役口径：保留工具不删（机制资产，外部部署者场景可能复用——治理包产品化 P1-5 的候选件），仅停用出单动线〔待确认：退役=停用还是删除〕。
3. 推送腿依赖手机 App 更新（bridge_alert 处理器）——与 DEV-56「留用户」项同链，装机后 A 版触达面即全通。

## 四、与 swap-nova／哨兵 plist 的衔接（DEV-43 已落地件编进轮次）

**定位原则**〔PM 推断〕：**轮次=定向触发面**（换装时刻一次性、深验证、全量清单）；**哨兵=常态观测面**（轮间持续、浅验证、增量异常）。两轮回执的人工判断「R6/R11/R12/R13 判观察面，长期复发监控归 patrol/boardrecon」＝把项从轮次面移到哨兵面的判断，本节把它变成轮末固定动作。

## 七、风险与边界

- **失败语义是设计核心不是附件**：换装类失败（P4）与回归项红（P5/P6）严格分流——前者停机交哨兵/人工，后者照常出回执转修复单。混同会造出「回归红就回滚包」的错误动作。
- **手机端永远「留用户」**：bridge_alert 处理器、R14 埋点、真机装机属用户面，不强求自动化（DEV-56 任务书口径继承）。
- **观感漏验残余**：A 版下探针盖不住的观感面，靠「留用户一眼」清单＋推送触达兜底——残余风险=用户不看推送则漏，接受（用户本来也不填表，净改善 strictly）。
- **本设计纯纸面**：不预设 L1 已存在；所有成本/时长为 PM 推断档，施工单另行核定；哨兵衔接动作（pause 纪律）需施工时对哨脚本现行为再核。
- 生产 data 只读铁律在 L1 设计中继承：脚本面不写 `~/.cc-deck/data/`（快照/回执落 artifacts/），pause 位是哨自有的协作接口不算写生产数据。
