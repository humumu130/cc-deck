## 0. 现状调研（设计依据）

### 0.1 项目列表的数据流：relay 下发索引，端上实时推导卡片

```
relay SNAPSHOT (ws-server.ts:936)          projects: listGroups()   ← projects.json 全量 ProjectGroup
relay 增量 (session-manager.ts:5572)       PROJECTS_UPDATED {groups, delta}  ← 瞬态帧，离线端靠 SNAPSHOT 兜底
        ↓
端上 deriveEntries() (index-005.html:5142-5156)   ← 卡片不持久化，每次渲染从 sessions+projects 现算
        ↓
renderQueue() (index-005.html:5202-5219)   三分组：活跃项目 / 待确认立项 / 挂起·归档
```

`deriveEntries()`（index-005.html:5142）的归组规则，是本次三个设计题的共同地基：

1. **立项组卡**：每个 `ProjectGroup` 出一张卡（`key:"g:"+id`），会话按 **cwd 前缀匹配** 吸进组卡——`underAnchor(cwd, anchor)`（:5131，`cwd === anchor || cwd.startsWith(anchor + "/")`，已做 `\`→`/` 归一，#158-批4a）。
2. **未立项卡**：没被任何锚吸走的会话，按 **精确 cwd** 分桶（`byCwd` Map，:5146-5152），每目录一张卡，`group: null`——卡片副行渲染「… · N 会话 · **未立项**」（:5213）。
3. 排序：最新会话活动优先（:5154-5155）。

**关键事实：relay 侧不存在「会话→项目」权威映射**。普通会话的项目归属纯靠端上前缀匹配推导；`SessionState.project_gid`（types.ts:259）只有派单/编制成员（worker 会话）才标。

### 0.2 项目模型：单锚点、一锚一团

- `ProjectGroup`（relay/src/projects.ts:42-74）：**单一 `anchor_dir`**（:45，注释明确「worker spawn 与记忆归层都锚它」）+ status 四态（pending/active/parked/archived）+ tier 两档（轻立项/正经立项）+ headcount。
- **一锚一组**硬规则：`findGroupByAnchor`（projects.ts:225-228）+ `createGroup` 校验（projects.ts:280-283「锚点目录已被项目组「X」占用（status），一锚一组」）。
- 活跃组上限 5（`maxActiveGroups`，projects.ts:235-238）。
- 立项入口在**团队域**（组织命令），项目页只读（index-005.html:5240 readonly-banner「该目录未立项。立项确认在团队域发起（组织命令），项目页不产生第二写面」）。建团表单锚点目录单行输入（:4774，placeholder「项目仓库绝对路径（必填，一锚一团）」，默认值 `teamCwdDefault()`）。
- 物理存储：`~/.cc-deck/org/projects.json`（`orgDir()`，org.ts:108-110；写穿全量，读侧防御坏 JSON 当空态）。

### 0.3 会话 cwd 的来源

- 托管会话：create 时用户指定（session-manager.ts:174-256 校验链：绝对路径→存在性→自动创建开关→sticky last-cwd→回落 home）。

- 推论：relay 重启后历史会话按 transcript 重建，**历史 cwd 的未立项卡会回来**——「这台机器上干过活的目录」口径，属预期行为。

## 1. 设计题①：项目卡快捷链接

### 1.1 交互形态

**方案：卡片副行（路径那行）行尾加一枚文件夹图标按钮**，点击 = 在系统文件管理器中定位项目目录。

- 位置：`renderQueue` 的 `card()`（index-005.html，以函数定位为准）副行 `<p>` 内，路径文本之后。**定死行内 flex 尾随（修订 UX D2-4，弃 absolute 右缘悬浮案）**：副行同时可能有「需行动」tag（右缘悬浮），absolute 右缘案会与之重叠遮挡、真机「按钮点不到」；定案=图标在 tag 之后行内尾随，并给**最小 32px 命中区**（触屏响应式布局虽不渲染未立项卡，桌面窄窗仍可能触达）。
- 命中区：图标按钮独立 `data-project-open`，点击 `stopPropagation`——不能触发卡片选中（选中会切第三列总览，误触代价高）。
- 显示条件：`window.ccDeck && typeof window.ccDeck.openPath === "function"`（**沿用 :3386 `shellReveal` 判定**）——桌面壳显示，浏览器/手机不渲染该按钮（title 悬浮已有完整路径可抄，不做「复制路径」降级，见开放问题 #2）。
- 未立项卡同享：它也是 `card()` 出的卡，anchor=cwd，顺手即得。

### 1.2 点击行为：reveal 还是 open

**推荐 reveal（定位+高亮项目目录本身）**：

| | reveal（推荐） | open（进入目录） |
|---|---|---|
| 用户心智 | 与产物域「在文件夹中定位」完全一致（已上线先例） | 新心智 |
| 窗口行为 | 复用/唤起父级 Finder 窗口，高亮项目目录 | 连点 N 张项目卡 = N 个新 Finder 窗口，桌面爆炸 |
| 安全面 | `dangerous_ext` 不拦（只定位不执行） | 目录无扩展名问题，等价安全 |

reveal 在 macOS 上的表现 = 打开父目录并选中项目目录（视觉锚定强，一眼看到目标）；open = 进入目录内部。对「我想看看这个项目的文件」的诉求，reveal 更贴近。若用户反馈偏好进入，加修饰键或后续菜单项即可，**P1 先 reveal 单行为**。

### 1.3 容错：路径不存在（目录被删/外置盘未挂载/远程源）

**沿用 #106/#158-批3 先探后开两段式**：

```
点击 → ccDeck.probePath(nativePath)
  ├─ true  → ccDeck.openPath(nativePath, true)  // reveal；catch 里 toast 错误摘要（:4180 同款）
  └─ false → toast「目录不存在（可能已删除或未挂载）」  // 不给 openPath 报错上屏（:4172 口径）
```

probePath 是微秒级只读 stat（main.rs:154 注释），无性能顾虑，不做防抖/节流。

### 1.4 实现细节坑：必须传原生路径，不能传归一化路径

- 立项组卡：`entry.anchor` 直接来自 `group.anchor_dir` 原值（:5144 未归一）——Windows 下原生反斜杠，✅ 直接用。
- **未立项卡：`entry.anchor` 是 `normDir(session.cwd)` 的产物**（:5149 分桶 key 已归一成正斜杠）——Windows 下 openPath 收到 `C:/foo/bar` 形态。`open_path` 的绝对路径校验（main.rs:135-139）接受正斜杠盘符，Windows API 层也普遍容忍，但**按 #158-批4a 教训不应赌容忍度**：分桶时保留原始 cwd（如 `byCwd` 存 `{list, nativeCwd}`，取该目录首个会话的 `session.cwd` 原值），openPath/probePath 一律吃原生形态。

### 1.5 改动面

| 域 | 改动 |
|---|---|
| relay | **零** |
| 面板（index-005.html） | `card()` 加按钮 + 点击处理（probe→reveal）+ 未立项分桶保留原生 cwd + 少量 CSS |
| 壳（desktop-tauri） | **零**（open_path/probe_path 现成） |
| expo / 手机布局 | 不涉及 |

## 2. 设计题②：多路径聚合

### 2.2 先回答一个关键问题：微服务场景下自动启发式为什么弱

用户举的场景（一个微服务系统 = 一个项目，多个仓库散在不同路径）恰好是自动启发式的**最弱场景**：

- **git remote 同源**聚的是「同一仓库多个 checkout」（worktree/克隆），而微服务 = 多个**不同**仓库、remote 各异——聚不到一起；
- **父目录启发式**（同一父目录 = 同项目）：`~/work/` 下并排放二十个不相干仓库是常态，误伤面巨大；更糟的是 `~` 本身常出未立项会话，父级一聚全进 `~` 卡；
- **命名前缀**（`cc-deck-*`）：约定靠自觉，误伤/漏收都不可判定。

**结论：自动聚合不做**（不是 P2 都不做，是不做自动生效的任何形态）。多路径归组的信任模型应该是「用户显式声明，系统忠实执行」。

### 2.3 方案空间

| 方案 | 描述 | 优点 | 缺点 | 判定 |
|---|---|---|---|---|
| a. 不聚合（现状） | 一路径一卡 | 零成本零歧义 | 微服务多仓库 = 多卡占列表，无整体视图 | **P1 维持** |
| b. 手动归组 | 组可挂多条路径；用户显式加/删 | 语义清晰、零误伤、与「立项是人的决策」同哲学 | 要做组编辑面 + schema 扩展 | **P2 推荐** |
| c. 自动启发式 | remote/父目录/前缀自动聚 | 零操作 | 微服务场景恰聚不到（见 2.2）；误伤不可控；静默改变归组最伤信任 | **不做** |

### 2.4 推荐方案详设：主锚 + 附路径（b 的最小改动面形态）

**核心原则：锚点的「编制语义」不动，只扩「展示归组」语义。**

- `ProjectGroup` 增可选字段 `extra_anchor_dirs?: string[]`（主锚 `anchor_dir` 保持唯一且语义不变）。两张皮：
  - **主锚** = worker spawn、记忆归层、防漂移 CLAUDE.md 种子（projects.ts:45 注释的三件事）、派单台账 `project_anchor`、stale 扫描——**全部不动**；
  - **附路径** = 纯粹「这些目录下的会话也归到这张卡显示」。不参与编制、不参与派单、不落记忆。
- **归组校验（升级为前缀语义，修订 UX D2-1·必须修）**：归因是前缀匹配（underAnchor：`cwd === anchor || cwd.startsWith(anchor + "/")`），clash 校验若只比路径**相等**则「组 B 附路径 /Users/xdd/dev、组 A 主锚 /Users/xdd/dev/cc-deck」两两不等、校验放行，但 cc-deck/** 下所有会话同时命中两组，卡片归属随遍历序漂移——「会话跳卡」比列表长更伤信任。定案：**不同组的全路径集合（主锚+附路径）两两禁止祖先/后代关系（相等与嵌套都拒）**；**同组内冗余嵌套可容忍**（主锚+附路径互为嵌套不拒）。单测锁性质「**任意 cwd 至多匹配一个组**」（全路径集合两两无前缀关系 ⇒ 此性质成立）。现状单锚模型已埋有同款嵌套暴露（两锚嵌套时 deriveEntries 先命中先得），**顺带在 P2-1 一并收口**。
- **归一函数共享（修订 REL 建-9）**：既有 relay clash 比较 findGroupByAnchor 归一=仅去尾斜杠（projects.ts:225-228），端上 normDir=反斜杠→正斜杠+去尾斜杠（index-005.html）——两套口径已并存。P2-1 扩 clash 到附路径时**抽共享归一函数（以端上 normDir 口径为准）**，relay clash 校验与端上归组**同谓词**——否则出现「relay 判不 clash、端上归同卡」的劈叉窗口。
- **归因链改动面（全在端上）**：
  - `underAnchor(cwd, anchor)` → `underAnyAnchor(cwd, group)`：主锚+附路径任一前缀命中即归组。**同规则改动点实为三处独立实现（修订 REL 建-9，逐一列出防漏改）**：① deriveEntries 的 underAnchor（卡片归组）；② `getSessionProject`（会话域项目徽标）——**独立实现**的归一前缀匹配、直接读 S.projects，**不消费 deriveEntries 产出**（原稿「两处同规则」表述有误），漏改它会话域徽标与项目卡归组劈叉；③ 第三列总览（overviewMini）。三处同批改；
  - relay 侧归因面**零改动**（0.1 已证：relay 无会话归因概念；clash 校验扩展是写侧校验不是归因）。
- **下发**：`listGroups()` 全量随 SNAPSHOT（ws-server.ts:936）+ `PROJECTS_UPDATED` 增量（session-manager.ts:5572）自动携带新字段——旧端忽略未知键（#71 deliverables 同款兼容口径），无协议版本问题。
- **交互面**：
  - 建团表单（index-005.html，以表单定位为准）锚点目录行加「+ 附路径」追加行（可留空；表单默认仍单锚，高级用法不挡路）；
  - 组编辑入口（团队域组详情）加路径清单管理（加/删附路径）。**P2-1 范围写死：只做附路径增删，主锚编辑不在本批（修订 ARCH M4）**——relay 现不存在组编辑路径（orgAction 无 group-edit/updateGroup 类 action，createGroup 是唯一写入口；组编辑面本身是未落件、需从零建 orgAction 面+确认/审计+广播），「改动主锚走既有流程」的前提当前不存在；主锚编辑等组编辑面单独立项，其从零建工作量不混进 P2-1；
  - **死附路径非阻断弱提示（修订 UX D2-3/ARCH Q3，纳入 P2-1）**：组编辑/组详情对当前不存在的附路径给灰字弱提示「目录当前不存在」（probePath 基建现成，保存时探测一次）——与「配置时不校验存在性」的宽松口径不冲突（开放问题 6 选 A 的连带责任：写错的路径永远静默无会话归入，用户无从分辨「还没干活」还是「挂错了」）；不阻断、可保存。
- **迁移成本**：存量组零迁移（字段缺省 = 无附路径，行为与现状逐字节一致）。
- **用户体验原则：「用户要不要关心」**——默认不让用户关心。不挂附路径 = 一路径一卡（现状）；挂了才聚。不做任何推荐/提示打扰（可选 P2+ 增强：组详情里对「 frequent 未立项目录」给一条「归入本项目？」的一键建议，用户点了才落——是 b 的便捷入口，不是 c 的自动聚）。

## 3. 设计题③：「未立项」分组

### 3.1 判定标准：不做第二套「目录意义性」判定

用户设想的判定（主目录根 / /tmp / 无 git 无立项标记）经过误伤分析后**全部不建议做**：

| 候选判定 | 误伤场景 |
|---|---|
| `cwd == homedir` 或 `~` 根 | 用户真在 home 干活的会话被降格（本次会话 cwd 就是 `/Users/xdd`——这是常态不是噪音） |
| `/tmp`、`$TMPDIR`、系统临时目录 | 一次性实验会话偶尔也要回看 |
| 无 `.git` | 大量非 git 工作目录是真项目（docs/、sandbox/） |
| 点前缀目录 | `~/.cc-deck` 里跑的运维会话是正经工作 |

**根本原因：判定错了的代价是「会话从列表消失」**——找不到会话比列表长更痛。

**推荐的判定 = 现状的「未立项」本身，零新增**：`deriveEntries` 里 `group: null` 的卡（:5153）全部进一个新分组。降噪靠**折叠**，不靠**过滤**——所有会话始终可见（多一次点击），只是换个抽屉放。这样判定永远无歧义、零误伤、无新概念，实现上就是把 `renderQueue` 的 `activeList`（:5203）按 `e.group` 有无拆成两半。

（目录意义性判定的合理用途留档：若未来未立项组涨到几十卡，可在组内按「最近活动时间」排序/收敛条目数——是抽屉内部的整理，不是抽屉的准入条件。）

### 3.2 展示方案对比

| 方案 | 描述 | 判定 |
|---|---|---|
| a. 置底折叠组（推荐） | 第四个 `queue-group`「未立项 · N」，默认折叠，点组头展开 | ✅ 与既有「活跃项目/待确认立项/挂起·归档」分组语言完全同构（:5216 `group()` 机制现成），改动最小 |
| b. 置底分区不折叠 | 平铺在底部 | ❌ 列表照样被撑长，没解决痛点 |
| c. 筛选开关（「显示未立项会话」） | 设置里开关 | ❌ 关掉=会话消失，违背 3.1 原则；状态藏设置深处，用户找不到开关在哪 |

**推荐详设（方案 a）**：

- 组序：活跃项目 → 待确认立项 → 挂起/归档 → **未立项**（置底）；
- 组头：`未立项 · N`（N=卡数，**修订 UX D2-2：贴卡副行既有「未立项」徽标词汇，同词自释——弃原稿「零散目录」，同一视图同一概念不发明第二个名字**）+ 折叠箭头；组内有 WAITING/ERROR 会话时，组头加一枚 hot 小圆点（提示「抽屉里有要处理的」，不强行展开）——沿用卡状态点词汇（:5207-5208）；
- 折叠态存 `localStorage`（纯端上视图态，不上 relay、不进 SNAPSHOT——同键位自定义的存储层级）；
- 组内排序沿用 `latest` 活动序（:5154），最近用的目录在最上。

### 3.3 立项升出路径：已天然存在，零机制改动

现状闭环（已验证）：未立项卡里的会话 → 用户在团队域以该目录为锚立项 → `deriveEntries` 重算，cwd 前缀命中新锚 → 会话自动升入项目卡（underAnchor :5144 吸走）→ 未立项卡若空则自然消失（entries 实时推导，0.1）。

**「以此目录立项」跳转预填（修订 UX D2-5：从「可选」提为 P2 必做）**：未立项卡 hover 菜单加「以此目录立项」→ `data-domain-jump="team"` 跳团队域并预填锚点（建团表单已有默认值机制 `teamCwdDefault()` :4774 可复用传参）。域纪律论证：readonly-banner 口径（:5240「项目页不产生第二写面」）**不被违反**——写面仍在团队域，项目卡只带路不落笔，不产生第二写面；抽屉收拢了未立项会话但 P1 无任何立项 affordance，用户得自己记得「去团队域建团」，升出主路径的最后一跳值得补上。原稿留开放问题 #5，按审查意见（跳转预填不越线、值得做）提为必做，仍尊重域纪律原文口径留用户复核。

## 附：本次调研未发现、但实现批需要知道的

1. **openPath 入参原生形态**（1.4）：组卡用 `group.anchor_dir` 原值；未立项卡分桶必须保留原始 cwd——这是 P1 唯一的隐性坑。
2. **归组规则的「三处独立实现」（修订 REL 建-9，原稿「三处消费同源」表述有误）**：deriveEntries（卡片归组）、`getSessionProject`（会话域项目徽标，:2406 附近）、第三列总览（overviewMini，:5238+）各自独立做归一前缀匹配——**getSessionProject 不消费 deriveEntries 产出**（直接读 S.projects）。P2-1 改 underAnyAnchor 时三处同批改，漏 getSessionProject 会导致会话域徽标与项目卡归组劈叉；P1-2 改分桶结构时同理别只改一处（entry 形状加字段是加法，不破坏既有消费）。
3. **多源（multi-relay）场景**：expo 端按 src 平铺 projects（ListScreen.tsx:1489-1494），index-005 当前单源视图——P2 附路径若落地，协议字段随 SNAPSHOT 自然多源可达，端上无需额外协调。
