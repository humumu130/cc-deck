# 团队模式输出物聚合归属设计（W-ARTAGG）

**推荐结论（一句话）**：输出物的**聚合归属锚定项目组（projects 域）**——005 项目域「输出物」Tab 做聚合主视图，聚合是**只读投影**（账本仍按 worker 会话 sid 记账，不搬家不双写）；Leader 会话**明确不做归属锚**（Leader 跨项目，其域内只留一个按项目分组的「跨项目汇总」只读入口）；团队域任务卡带产物徽标做过程视图。最小改动版零账本迁移（读时聚合），完整版登记时写 `project_gid` 归因字段。

---

## 0. 定调输入（Leader 补充约束，2026-10-09，设计前提）

1. **设计目标形态** = 新版应用壳（`web-console/index-005.html`，三域：会话/团队/项目）+ 完善后的团队模式。旧壳是过渡态，单独一节处理（§8）。
2. **Leader 是跨项目的**：一个常驻 Leader 同时管多个项目组（v8 矩阵式裁决稿 §1「一家公司」形态）。因此**全团队 worker 的输出物绝不能聚合挂到 Leader 会话名下**——否则 Leader 的输出面板堆满多项目产物，不可用。
3. **归属锚 = 项目/项目组**（projects 域），不是任何会话。Leader 侧至多做「跨项目汇总入口」（按项目分组的只读聚合），不是归属本体。
4. 设计必须含「旧壳→新壳过渡期」最小可用路径，不能只服务未来。

## 1. 问题定义

用户原话痛点：「我跟你（Leader）交互，底下的 worker，我还得一个一个去他们会话的面板里找输出物吗？太麻烦了。」

拆开是三个问题：

| # | 问题 | 现状 |
|---|------|------|
| Q1 | 全队交付物散在各 worker 会话卡里，**没有按团队/项目聚合的视图** | 产物挂各会话 `state.artifacts`，逐会话看 |
| Q2 | 看到了也难区分「哪个 worker 交的、哪个项目的、验收到哪了」 | 会话卡内产物行只有 path/size/时间，无项目维度 |
| Q3 | 归属语义不清：聚合之后，worker 个人输出物面板还留不留 | 未定义 |

## 2. 现状盘点（设计所依据的代码事实）

### 2.1 登记链路与账本

- **入口**：`~/.cc-deck/bin/deliver <path>` → POST `/api/deliver`。携带 `session_id`（env `CLAUDE_CODE_SESSION_ID` / hook 透传 `CC_DECK_SESSION_ID`）走 `deliverBySession` 精确归因；无身份时回落 `deliverByCwd`（cwd 前缀 + realpath 归一启发式，取最近活跃会话）。
- **账本**：主线 `~/.cc-deck/data/deliverables.json`（扁平 `[{sid, path, ts}]`，**keyed by worker 会话卡 id**，CAP 300）；w16 分支（feat/orphan-artifacts，#183）已升级为 `artifacts-index.json`（`{sid: [{path, name, size, delivered_at, unverified}]}`，keyed by 卡 id + 全局 CAP 300 + 旧账一次性迁移）。两代账本记账维度一致：**sid**。本设计按「账本 keyed by sid」抽象写，两代均适配。
- **双通道收录**：①产物目录自动收录——写进 `~/.cc-deck/artifacts/` 即交付声明（`mergeArtifact` 判前缀）；②项目内原地登记——`registerDeliverable`（/api/deliver）。两通道最终都落同一份账。
- **展示面**：产物挂会话卡，客户端会话详情「输出物」Tab 渲染；`restatArtifacts`（20s 轮询）保证「面板 = 磁盘现状」（#224，已删即消失）。**产物目录全局区**（`/api/artifacts` 列表）是现成的跨会话聚合面（不分会话，按目录/时间排）。
- **安全闸**：`validateDeliverablePath`（#72A0）取证先行、失败零落账。

### 2.2 组织形态：v8 矩阵式（词表注意）

`docs/v8-team-matrix.html`（裁决稿 v3.1，2026-09-26）是权威方向：**常驻组织（唯一 Leader + 两本账）+ 动态项目组**。旧 team-mode-design.md（2026-09-18）的「团队」实体与五段看板词表（待装机等）已被 v8 §2.4 词表迁移——**本设计全部落「项目组（project_group）」词表**，不复活旧 team 实体。

relay 已实现（`projects.ts`）：

- `ProjectGroup`：`anchor_dir`（锚点目录）、三态状态机（pending/active/parked/archived）、`headcount`（编制快照：`{session_id, role, engine, provider, model}[]`，`addMember/removeMember` 维护）。
- `findGroupByAnchor(anchorDir)`：cwd→项目组现成反查（排除 archived）。
- 任务板 `boards/<gid>.json`：`BoardEntry{text, status: todo|doing|done, owner_session, dispatch_id, depends_on, gate}`——**派单联动搬卡已有**（`moveEntryByDispatch`）。
- 派单台账（`org.ts` `DispatchEntry`）：append-only，**已带 `project_anchor` 字段**（M2 派单链路 `appendDispatch` 已写入，session-manager.ts:5158/5218）——「哪次派单产生哪个产物」可回溯。
- SNAPSHOT 已带 `projects: listGroups()`（ws-server.ts:939）——项目组列表已在下发通道内。

### 2.3 005 新壳三域现状（index-005.html，cc-deck-m1 worktree feat/matrix-team-m2）

|---|------|----------------|

## 3. 核心设计决策：两层归属语义

**「归属」拆成两层，分别回答「聚合挂哪」和「账记在哪」：**

| 层 | 锚 | 理由 |
|---|---|------|
| **记账归属**（写面） | worker 会话 sid（现状不动） | 登记动作、重启回放（`applyDeclaredDeliverables`）、存在性复查（re-stat）、#227 精确归因链全部锚 sid；改它牵一发动全身，且 sid 是「谁写的」这一事实的天然载体 |
| **聚合归属**（读面） | 项目组 gid（新增投影维度） | Leader 约束 §0.2/0.3：项目组是跨会话的编制单位，anchor_dir 是物理锚点；聚合视图 = 按 gid 过滤账本的投影，可随时重算，不产生第二事实源 |

一句话：**账还是那本账（sid 维度），聚合只是多戴的一副眼镜（gid 维度）**。这同时回答 Q3：个人会话输出物面板**保留**——它是记账锚点与写面；项目域聚合是只读投影，与 005 `readonly-banner`「不产生第二写面」原则同构。

## 4. 推荐方案 A：项目组归属锚 + 项目域聚合主视图

### 4.1 信息架构

```
项目域 #d-project（聚合归属本体）
└─ 「输出物」Tab（已有 Tab 位）= 该项目组全部交付物完整列表
   数据 = 聚合投影（§4.3 判定），只读，动作回原域

团队域 #d-team（过程视图）
└─ 看板任务卡右下角产物徽标（完整版）：「📎 3」→ 点开弹该项目组产物列表（跳链到项目域 Tab 或就地小弹层）

会话域 #d-session（个人明细，现状不动）
└─ 会话详情「输出物」Tab：worker 自己的登记明细（写面锚点）

Leader / 组织层（顶层入口，非归属）
└─ 「跨项目汇总」只读入口（完整版）：按项目组分组折叠的全量产物列表
   （每个分组头 = 项目名 + 计数 + 最近交付时间；展开才拉明细——Leader 域不堆数据）
```

**为什么项目域是本体而不是团队域**：① v8 词表迁移后「团队」收敛为「项目组」，项目域 = 锚点域（anchor_dir 目录即锚），产物路径天然带目录信息，归因零发明；② 005 项目域「输出物」Tab 位与 46 计数已在设计稿占位，等于产品语言已预定；③ 团队域详情 Tab 已有 4 个，且其主体是任务流不是产物流——产物徽标 + 跳链即可，不重复建列表。

### 4.2 交互（怎么区分谁交的、哪个项目、验收到哪）

项目域「输出物」Tab 列表行（自上而下按交付时间倒序）：

```
┌──────────────────────────────────────────────────────┐
│ 📄 release-check.md                    刚刚           │
│ docs/release-check.md · 12 KB                         │
│ ✦ worker-web（Claude · 公司电脑）    [状态：已完成]   │
│                                          → 查看来源    │
└──────────────────────────────────────────────────────┘
```

- **哪个 worker**：登记 sid → 会话卡取标题 + identity-cluster（engine badge + source badge，005 现成组件）→ headcount 反查 role（「worker-web」）。
- **哪个项目**：聚合键即 gid（Tab 本身在项目域内，天然按项目过滤）；跨项目汇总入口按 gid 分组。
- **验收状态**：最小版不显示；完整版经 `sid → 该会话 owner_session 匹配的任务卡 → 卡 status（todo/doing/done）`映射为「进行中/已完成」轻量口径（复用 `moveEntryByDispatch` 同一条会话-卡联动数据，不深度绑定验收单——产物↔验收单关联键现状不存在，不做无据绑定）。
- **点「查看来源」**：跳回产出会话卡的输出物 Tab（写面）——聚合视图永远给出路，不复制动作。
- **筛选**：Tab 内按 worker / 按时间两个轻筛（前端本地过滤即可，量级 ≤300）。

### 4.3 归属判定机制（本设计的机制核心）

**最小版：读时聚合（零账本改动，零迁移）**

relay 新增聚合查询（session-manager 或独立 `project-artifacts.ts`，纯函数），给定 gid 返回产物列表，判定三条**并联**（命中其一即归组）：

1. **path 前缀 ∈ anchor_dir**（主路径）：交付物路径以项目组 `anchor_dir` 为前缀。覆盖：项目内原地登记（docs/ 报告）、项目目录内 build 产物（APK/dmg）。**不受成员变动影响**——worker 出组/会话清理后，历史产物仍按目录归组，这是它做主路径的原因。
2. **sid ∈ headcount**（辅路径）：登记 sid 出现在该项目组编制快照（含 parked/archived 组——归档组产物仍可查，审计语义与板冻结保留一致）。覆盖：产物写在其目录不在 anchor 内的场景。
3. **dispatch 反查**（兜底）：派单台账 `project_anchor` 匹配 gid 的派单 → `session_id` 集合内的 sid 产物。覆盖：headcount 被收缩后的历史派单会话（编制快照只留当下，台账 append-only 留全史——两条腿互补）。

全局产物区（`~/.cc-deck/artifacts/`）条目路径不含 anchor，靠 2/3 归组；都命中不了 = 真全局产物（不属于任何项目），只出现在跨项目汇总入口，不硬塞进项目——**聚合不伪造归属**。

**完整版：写时归因（账本条目加可选字段）**

`/api/deliver` 请求已带 cwd / session_id → `findGroupByAnchor(cwd)`（或 sid→会话 cwd→anchor）归因，写入账本条目 `project_gid?: string`（DeliverableEntry / ArtifactsIndexEntry 均为可选键，旧数据无字段 = 回落读时聚合判定，**完全向后兼容**）。写时归因的价值：① headcount 后变的场景固化判定；② 聚合查询 O(1) 过滤不用三条并联；③ 全局产物区条目获得确定性归属。

推荐演进路径：**最小版先上（读时聚合），真实用一两周后再决定要不要写时归因**——若三并联判定在真实数据上误归/漏归率可接受，写时归因可以不做（少一处 schema 迁移）。

## 5. 备选方案 B：团队域项目组详情内嵌输出物分节

**形态**：项目组详情 Tab 扩为「对话/看板/成员/活动/**输出物**」5 Tab，聚合视图挂团队域。

- 优点：与用户动线契合——「我跟你（Leader）交互」的入口是团队域对话 Tab，看产出顺手切 Tab，不用跳项目域；编制/板/产物一屏可览。
- 缺点：① 与项目域「输出物」Tab 数据完全同源、UI 重复，双入口双维护；② 项目域 Tab 位已在设计稿占位（46 计数），弃之需要改设计稿口径；③ 轻立项/无编制场景（单 worker + Leader 兼管）没有像样的「团队」可看，项目域覆盖面更广（项目域按目录聚合，**普通会话、无组历史产物也能进**——团队域只覆盖有组的）。
- **裁定**：不作为独立方案，其合理内核（从团队动线看产出）由方案 A 完整版的「看板任务卡产物徽标 + 跳链」承接。若实跑后发现用户看产出的动线 80% 起点在团队域，把项目域 Tab 的渲染组件复用到团队域加 Tab 即可（数据层零改动，纯 UI 增强，随时可加）。

## 6. 备选方案 C：全局交付物流（组织级时间线）

**形态**：org 级单一长列表——全部项目组全部产物按时间倒序一条流，带项目筛选 chip。挂在 Leader 对话域或独立「动态」页。

- 优点：跨项目一览无余，适合「巡场」心态（今天全队交了什么）；实现最简（一个全表查询不分 gid）。
- 缺点：① **正是 Leader 约束排除的形态的变体**——全局流挂在 Leader 域时，Leader 输出面板被多项目产物淹没的问题只是换了个页面重演；② 单项目聚焦场景（装机验收某个功能的产物）要靠筛选，手机端筛选交互成本高；③ CAP 300 全局池下，活跃项目的历史产物被其他项目挤出视野，**项目内回看不可靠**——聚合视图的可回看性不该取决于别的项目多不多产。
- **裁定**：降级为方案 A 完整版的「跨项目汇总入口」呈现形态——按项目分组折叠（不是平铺一条流），数据 = 同一聚合查询外层套分组，Leader 域只做入口不做归属。分组折叠保住了「Leader 面板不被淹没」的约束，也保住单项目回看的可靠性。

## 8. 旧壳→新壳过渡期（当下最小可用）

旧壳（现网 web-console）没有项目域/团队域，只有会话列表 + 全局输出物区。过渡期不要求旧壳实现聚合，**用「现成面 + 纪律」兜住**：

1. **现成面：全局产物目录区**（`~/.cc-deck/artifacts/`，`/api/artifacts` 列表，三端已有）——这是旧壳唯一的跨会话聚合面。**约定强化（零代码）**：团队任务里**要给用户看的最终交付物**（验收单、汇总报告、装机包直链页等）在 deliver 登记之外**再写一份进产物目录**（或生成时就直接写这里）；项目内过程性交付物（docs/ 报告等）维持原路径登记不动。这符合现行交付约定（全局一次性产物写 artifacts/ 即收录），只是把「团队任务给用户看的产物」明确归入此列。
2. **纪律面：Leader 收口汇总（已是这样干的）**——Leader 回合收口时在对话里罗列本批交付物路径清单（现行任务书「交付」节的惯例）。单线交互下用户从 Leader 对话流直接看到产出，不逐个翻 worker 面板——这本来就是矩阵式单线的红利，明示为过渡期正式做法而非将就。
3. **通知面（可选小改，旧壳受益）**：完整版 notify 联动（§4.4）先做——`/api/deliver` 登记成功后 `notify.user`（「<会话名> 登记交付物 <文件名>」）。旧壳推送通道现成，用户手机能收到「有新交付物」的提醒，点进对应会话看。这是过渡期唯一值得写的代码（~20 行），且是新壳完整版的一部分，不做一次性投入。
4. **过渡期明确不做**：旧壳加项目域/聚合页——旧壳进入维护态，聚合视图是换壳动力之一，不给旧壳加新页面拉长双壳并行期。

**换壳完成即切换**：新壳项目域「输出物」Tab 上线后，上述约定 1 的「双写」不再需要（项目域按目录聚合已覆盖项目内交付物；产物目录区回归「全局一次性产物」本位）。

## 9. 边界与风险

| # | 风险 | 预案 |
|---|---|---|
| 1 | **读时聚合误归**：同仓库多项目组（anchor 相邻，如 cc-deck 与其 worktree 目录）path 前缀误命中 | `findGroupByAnchor` 已按 realpath 归一 + 一锚一组（createGroup 拒绝占用）；worktree 目录（`../cc-deck-wt/<member>`）不在 anchor 前缀内，天然不误归；单测覆盖相邻目录样例 |
| 2 | **headcount 变动漏历史**：读时聚合路径 2 依赖编制快照（只留当下） | 三并联中路径 1（目录）与路径 3（台账）都不受编制变动影响兜住；真固化需求 = 完整版写时归因 |
| 3 | **性能**：聚合查询逐条判定的代价 | 账本 CAP 300 全表已在内存，三判定是字符串前缀/集合查找，毫秒级；SNAPSHOT 计数做失效缓存即可，不引入定时器 |
| 4 | **全局产物区归属模糊**：artifacts/ 条目既可能是某项目的也可能是真全局的 | 判定命中即归组、不命中即「仅汇总入口」；完整版写时归因后登记时即固化——**宁可归不进（进汇总），不硬猜** |
| 5 | **SNAPSHOT 膨胀**：各组带产物计数，组多时帧变大 | 只加 count + 最新一条文件名（≤100 字节/组），明细走懒加载端点，不塞全量 |
| 6 | **与 #224「面板=磁盘现状」口径一致性**：聚合列表若显示已删条目会被用户骂（#224 原话教训） | 聚合读侧同样过滤 exists=false（复用 restat 结果），删除即从聚合视图消失 |
| 7 | **worker 会话被清理**：sid 消失后「查看来源」跳空 | 聚合行保留（账本仍在），来源跳链接 graying + 「会话已归档」提示；role 展示降级为「已归档会话」（headcount/台账留档可查） |

## 10. 已知取舍（明示）

- **验收状态只做轻口径**（任务卡 todo/doing/done 映射），不做产物↔验收单深度绑定——两者间关联键现状不存在，造键需要验收单侧同步动 schema，收益不成比例；等验收单与产物产生真实关联需求（如按验收单聚合证据物）再立项。
- **最小版先行、写时归因缓决**——三并联读时判定若实跑够准，schema 迁移就永远不做；设计给出的是演进路径而非一次性大方案。
- **轻立项单卡态**下的产物聚合与正经立项同口径（项目域不分区渲染）——单卡是渲染降级不是独立模型（v8 §4 原文），聚合视图同理。
