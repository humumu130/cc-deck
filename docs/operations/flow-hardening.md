# 需求→交付全链流程硬化（W-FLOW，2026-10-11）

> 定位：**机制设计 + 可执行硬闸**，不是方法论。六个实锤失败案例逐个归因、逐个堵漏。
> 配套脚本：`scripts/verify-receipt-claims.mjs`（回执真实性）、`scripts/check-deploy-complete.sh`（部署完整性）。
> 姊妹台账：[feedback-ledger.md](feedback-ledger.md)（用户反馈闭环台账）。
> 红线：每环**一个动作**能完成的检查。今天的问题不是没流程，是核验深度不够 + 盲区——解法是精准堵漏，不是层层加码。

## 1. 十环总览

```
需求 → 登记 → 派工 → 执行 → 回执 → 核验 → 真机 → 出包 → 用户验收 → 关单
```

| 环 | 责任者 | 一句话职责 | 硬闸 |
|---|---|---|---|
| 1 需求 | Leader | 接住用户原话，不转译不丢失 | 口径双发（任务单记原文+翻译） |
| 2 登记 | Leader | 每条需求 TaskCreate 入单，唯一事实源 | 无单不动工 |
| 3 派工 | Leader | 任务书带验收点+核验级别预判 | 任务书无「核验级别」字段不派 |
| 4 执行 | worker | 改动+自测+部署面同步 | check-deploy-complete（涉部署时） |
| 5 回执 | worker | 如实报：做了什么/怎么验的/什么没验 | 回执模板含「受限项」强制段 |
| 6 核验 | Leader | 机器先过，人看❌项+抽查实质 | verify-receipt-claims 三色表 |
| 7 真机 | Leader | L3/L4 项排期装机验证 | 不 completed 规则 |
| 8 出包 | Leader | 打包+环境矩阵自验 | 出包前自验清单（§4） |
| 9 用户验收 | 用户 | 验收单回填 | 双链发出（LAN+云通道） |
| 10 关单 | Leader | 按回填闭环台账与任务单 | ✗→修复单 / 未测→留 in_progress |

## 2. 核验分级制度（核心交付）

回执与核验的一切规则围绕一个问题：**这个改动域，什么样的验证才算数？**

### 2.1 四级定义与必做清单

| 级 | 改动域 | worker 必做 | Leader 必做 | 任务可否 completed |
|---|---|---|---|---|
| **L1** 纯逻辑 | relay 函数、脚本、无 UI 的纯计算 | tsc + 相关单测全绿；回执列断言数 | diff 抽查 + 复跑测试（或信任 CI 绿） | ✅ 可以（机器验证=真验证） |
| **L2** web UI | index-005.html、index.html、PWA | CDP 断言 + **双主题截图**落盘；回执给截图路径 | **必看截图**（不信「断言过」文字）；抽查 1 件实质（打开截图找断言对应的视觉证据） | ✅ 可以（截图=视觉证据落盘） |
| **L3** 壳层行为 | Tauri 窗口/菜单/拖拽/系统交互、WebView 外的行为 | CDP 能验的先验 + 回执明确列「装机复验点」清单 | 代码核验过；**任务保持 in_progress**；复验点写进验收单 | ❌ 只能标「代码核验过，真机待验」 |
| **L4** 跨端 | expo 手机端、真机安装链 | 构建/模拟器层自测 + 回执列装机验证点 | 同 L3；验收单标注「待装机验」 | ❌ 同 L3 |

### 2.2 硬规则（不可绕过）

1. **L3/L4 不 completed**：回执含 L3/L4 项时，Leader 核验结论只能是「代码核验过，真机待验」——任务进验收单等真机关单。这不是对 worker 的不信任，是 L3/L4 的验证链物理上缺最后一环。
2. **L2 必看图**：「CDP 断言 26 项 ALL PASS」不算核验完成——打开截图路径，肉眼确认断言对应的视觉效果。断言验的是 DOM 状态，用户看的是像素。
3. **核验级别在派工时预判**：任务书里每个验收点标 L1-L4。worker 回执按预判级别给证据；级别判断错了（如以为 L1 实际涉及 L3），核验环升级处理，不 retro-fit 回执。
4. **采样率按级分配**（解案例 4）：Leader 深核带宽只给高风险件——L3/L4 全核、L2 全看图+抽查实质、L1 diff 抽查。机器（verify-receipt-claims）先跑全量声明核验，Leader 带宽花在机器判不了的地方。

### 2.3 各级核验的机器可自动化程度

| 检查 | L1 | L2 | L3 | L4 | 谁做 |
|---|---|---|---|---|---|
| 文件确实改了 | ✅ 脚本 | ✅ 脚本 | ✅ 脚本 | ✅ 脚本 | verify-receipt-claims |
| 测试/断言数复跑 | ✅ 脚本(--deep) | ✅ 脚本(--deep) | — | — | 同上 |
| 截图落盘存在 | — | ✅ 脚本 | — | — | 同上 |
| 截图内容对不对 | — | 人眼 | — | — | Leader |
| 壳层行为真机 | — | — | 人手 | 人手 | Leader 装机 |

## 3. 十环逐环定义

### 环 1·需求（用户 → Leader）

- **输入**：用户消息（原话）。
- **动作**：不转译。任务单描述里同时记：用户原话关键句 + Leader 翻译后的工程口径。转译丢失是「做出来的不是要的」的第一现场。
- **防漏**：消息分诊四类（全局准则已有）：新任务入单 / 补充更新原单 / 问答不入单 / 顺手 30 秒立即做。

### 环 2·登记（Leader → 任务单）

- **输入**：分诊结果。
- **动作**：TaskCreate，含背景+验收点。任务单=唯一事实源。
- **防漏**：验收点随手写进任务描述（实现完最清楚哪里要验，出验收单时汇表——全局验收单流程已有此条，此处强调它同时是台账的种子数据）。

### 环 3·派工（Leader → worker）

- **输入**：任务单条目。
- **动作**：任务书必含四件：**改动域清单、验收点、核验级别预判（L1-L4）、回执要求**。
- **防漏**（案例 1 前置）：预判 L3 时任务书明写「headless 验不了的部分列装机复验点清单，不要试图用 CDP 断言替代」。
- **worktree 铁律不在此重复**（CLAUDE.md 已有）：多会话并行必须 worktree 隔离。

### 环 4·执行（worker）

- **输入**：任务书。
- **动作**：改动+自测。**涉 UI 部署面的改动，收尾必须跑 `scripts/check-deploy-complete.sh`**（部署面同步是 worker 的收尾步骤，不是 Leader 的补救步骤——案例 3 的教训：同步动作留给人肉记忆必漏）。
- **防漏**：改动域 = L 级判定域。worker 发现实际改动越出预判域（如任务书说改 relay 结果动了壳），回执里显式声明，核验级别相应升级。

### 环 5·回执（worker → Leader）

- **输入**：自测结果。
- **动作**：回执必含五段（现有惯例固化）：改动清单（文件+行号）/ 每件自测证据 / **受限项（如实报，强制段——没有就写「无」）** / 请 Leader 复核的点 / 沙盒配方（可复现）。
- **防漏**（案例 1、6）：受限项不许写成「应该没问题」——写「什么没验、为什么、验它需要什么条件」。回执里「留装机复验」四个字 = 该项自动进验收单（见环 7）。
- **核验**：`node scripts/verify-receipt-claims.mjs <回执路径>`——Leader 收回执第一动作，机器先过一遍。

### 环 6·核验（Leader）

- **输入**：回执 + verify-receipt-claims 三色表。
- **动作**（按序）：
  1. 跑脚本 → 看❌项（声明与实测不符的）；
  2. L2 件：打开截图路径逐张过目；
  3. 抽查 1-2 件实质（不是 grep 锚点——找断言对应的视觉/行为证据；案例 1 的教训：锚点存在≠功能实现）；
  4. L3/L4 项：标「代码核验过，真机待验」，转环 7。
- **防漏**（案例 4）：不追求逐件深核——机器核验兜住「声明不实」，Leader 带宽集中在机器判不了的「实质不对」。

### 环 7·真机（Leader）

- **输入**：核验环积累的 L3/L4 复验点 + 「留装机复验」项。
- **动作**：装机验证点**进验收单**（不是记在脑子里或回执里等以后）——验收单是真机验证项的唯一排队处。
- **防漏**（案例 2）：「留装机复验」而没有对应验收单行的 = 流程漏洞，关单环检查此项。

### 环 8·出包（Leader）

- **输入**：核验全绿 + 真机项已排期（允许出包，真机项在验收单等）。
- **动作**：§4 出包前自验清单 + 既有 release-guard.sh / check-bundle-sync.sh（发版闸已有，不重复）。
- **防漏**（案例 3、5）：**部署面完整性**（check-deploy-complete 全绿才算部署完成）+ **环境矩阵**（字号四档/窗口尺寸逐档截图）。

### 环 9·用户验收（用户）

- **输入**：包 + 验收单（双链）。
- **动作**：用户按表回填 ✓/✗/未测。
- **防漏**：验收单行 = 单一动作+单一可观察结果（全局验收单流程铁律，不重复）。L3/L4 项必须在表里占行——没有行 = 用户无法帮你关单。

### 环 10·关单（Leader）

- **输入**：验收回填。
- **动作**：✓ → 任务 completed + 台账状态翻「用户已确认」；✗ → 现象记入原任务（或新开修复任务）排查；未测 → 原任务留 in_progress 等补验。
- **防漏**（案例 2 终点）：**台账同步翻状态**（feedback-ledger.md）——台账里任何一行停在「已修待验」超过一个发版周期 = 主动追问用户，不许沉默搁置。

## 4. 出包前自验清单（Leader 必做，出包环硬闸）

既有闸（release-guard.sh：版本/烙印/bundle 同步/tsc/语法/bridge 测试；check-bundle-sync.sh：三处一致+工作区干净+重建对比）照旧跑，它们管「**产物对**」。本清单管「**体验对**」——产物正确不等于用户看到的效果正确（案例 3、5 都是产物对、体验错）：

- [ ] **部署面完整**：`scripts/check-deploy-complete.sh` 全绿（relay.mjs + web-console 双壳 + mobile 面 + 无脏副本），重启 relay 后再过一遍（同步文件不重启 = 运行面还是旧的）
- [ ] **环境矩阵逐档**：改动涉字号/间距/布局时，字号四档（紧凑/标准/宽松/特大——以实际档位为准）各截图过目；涉窗口尺寸时最小/默认/最大三档过
- [ ] **验收单可自动验项预演**：验收单里能在装机环境自动验的项（截图/CDP），装好包的环境里过一遍——验收单不是写给用户的第一版测试，Leader 先当第一个用户
- [ ] **本次批涉 L3/L4 项清点**：每项在验收单有行（无行=补行再发）

## 6. 本文档的维护

新实锤案例 → 照 §0 表格式追加行（案例/根因/堵哪个环/装置），装置不存在的设计装置。流程本身的重流程化倾向（检查项膨胀）按红线自检：**每环一个动作**，超出的合并或砍。
